# p_0.35.4 — Extension shell: panel, streaming, settings, trust

**Status:** done  
**Milestone:** [m_0.35_vscode_extension.md](../m_0.35_vscode_extension.md)  
**Linked design:** [35-vscode-extension.md](../../../design/v1.0/35-vscode-extension.md)

## Goals

A working VS Code extension that spawns the host and holds a streaming conversation, at Claude Code-class presentation.

## Scope

New tree `editors/vscode/` (TypeScript). One host child per window.

## Tasks

1. Project scaffold: `package.json` (engines, activation events, contributes), TypeScript build, ESLint; extension unit-test harness.  
2. **Host client**: spawn `anvil-host` as a child process, `initialize` handshake, line-framed JSON-RPC reader/writer with request/response correlation and notification dispatch; restart and crash handling; kill on `deactivate`.  
3. **Workspace trust**: refuse to start in an untrusted workspace, with an explanatory message.  
4. **Settings**: `provider`, `model`, `base_url`, `max_steps`, `store`; API key in **SecretStorage**, injected into the child env at spawn. Never write the key to settings or logs.  
5. **Chat panel**: webview with streaming assistant text (append chunks — not per-token), collapsible tool cards showing name + args + truncated result + error state, and a step/progress indicator.  
6. **Interrupt**: stop button → `cancel`.  
7. **Approval prompt**: render `approval.request` inline or as a modal with allow / allow-for-session / deny; render the `command`-kind preview as argv. (Diff-kind preview is rendered in p_0.35.5.)  
8. Errors: map `code` (`max_steps`, `provider`, `cancelled`, `max_wall_time`, `context_deadline`) to distinct UI states instead of one generic failure.  
9. Tests: extension unit tests against a fake host process; one integration test driving a stubbed session end to end.

## Tasks as delivered

**Layout.** `editors/vscode/`: `src/protocol.ts` (the whole contract, mirroring `proto.go` field for field), `src/hostClient.ts`, `src/session.ts`, `src/errors.ts`, `src/settings.ts`, `src/hostManager.ts`, `src/chatPanel.ts`, `src/extension.ts`; `media/` (the webview's `chat.js` / `chat.css` / icon); `scripts/build-host.mjs`; `test/` (unit, integration, fixtures, helpers).

**The `vscode` boundary is the test boundary.** `protocol.ts`, `hostClient.ts`, `session.ts` and `errors.ts` import nothing from `vscode`, so they are covered by Node tests that drive a real child process. `settings.ts`, `hostManager.ts`, `chatPanel.ts` and `extension.ts` do import it and are therefore only reachable from an extension host; they are kept thin on purpose, and the tests compensate by covering everything they delegate to.

**Test host.** `test/fixtures/fake-host.mjs` speaks the real protocol and scripts its runs (`chat`, `approval`, `slow`, `fail`, `silent`) from an env var. The tests run the real `HostClient` over real pipes against it, so a mis-framed notification or a wrong field name fails the suite.

Deviations from the tasks as written:

1. **A second calibration of tests.** Task 9 asked for a stub host, and the fake host was built first. But a stub can only pin the extension's *assumptions* about the Go side, so two further integration tests drive the **real** `anvil-host` binary (`test/integration/realHost.test.ts`), with the model call routed at `http://127.0.0.1:9/v1`. The run ends `done(status=error, code=provider)` offline and deterministically, which is enough to pin the handshake, `session.new`, the event stream, and the terminal envelope against the actual Go writer. They are skipped when the sidecar is not built.
2. **`ChatSession` takes a `Transport`, not a `HostClient`.** The state machine is where the interesting bugs are (a run stuck in `running`, a prompt left on screen after `done`), and driving it through a process to test it would have made those tests slow and flaky. `Transport` is the two methods the session actually calls; the extension passes the real client, the unit tests pass a table.
3. **Trust is enforced in two places.** The extension declares `capabilities.untrustedWorkspaces.supported: false`, so VS Code disables it in an untrusted folder; `HostManager.assertTrusted()` additionally runs at the top of the only code path that spawns a process, and the panel checks it to produce a readable message. The UI check is for the message; the assertion is the enforcement.
4. **`anvil.running` context key.** The stop command is contributed to the view title with `when: view == anvil.chatPanel && anvil.running`, which needs the extension to maintain that key. It is set from the panel's host-state events.
5. **A diff-kind preview is rendered after all.** Task 7 scoped p_0.35.4 to command-kind previews and left diff-kind to p_0.35.5, but the preview is already plain text in the protocol, so the panel colours it and shows it. That is not the diff-review surface (the p_0.35.5 acceptance item), which still shows the post-edit result through a review UI.
6. **The webview script is linted.** `media/chat.js` runs in a browser context, so it gets the browser globals plus `acquireVsCodeApi` and is checked like the rest of the tree. Everything it renders from the host — assistant text, tool arguments, results, diffs — goes through `textContent`, never `innerHTML`: tool output is arbitrary file content and command output, and it must not be able to add markup to the panel.

Client-facing details worth knowing:

- **The host is spawned lazily**, on the first prompt, not on activation — and killed on `deactivate`, on a workspace-folder change, and on a configuration change (the host reads its configuration at spawn).
- **The API key never crosses the pipe.** It is read from `SecretStorage` and placed in the child environment as `ANVIL_API_KEY`; provider / model / base URL travel in `session.new`. Setting or clearing the key restarts the host, because a running child holds the environment it was spawned with.
- **No `permission_mode` setting yet** — the panel runs `ask` and answers prompts. Modes are p_0.35.6, and the SDK-side plumbing already exists (p_0.35.3).
- **`approval.response` returning `-32004`** is a normal race (the run ended while the prompt was on screen) and is reported as "no longer pending", not as an error.

## Acceptance

- [x] Opening a trusted workspace and sending a prompt streams output from a real model. — **Not executed here**: this environment has no window, no extension host, and no model key. What is verified instead is the same path minus the UI: the real `anvil-host` binary and the extension's own client and session, in `test/integration/realHost.test.ts`, against a provider that refuses (the run streams `progress`, then `done(code=provider)`). Verifying it against a *working* model is a manual step in a real window.
- [x] Tool calls appear as cards; a mutating call prompts; deny returns an error the model reacts to. — `test/integration/conversation.test.ts`: the card pairing is asserted through `tool_call_id`, the prompt through `approval.request`, and deny through a `tool_result` with `is_error: true` followed by `done(status=finished)` — the model is told, and the turn continues rather than crashing. The *rendering* of the card is in `media/chat.js`, which no test here can run.
- [x] Stop interrupts a running turn. — `cancel` reaches the host and the run ends `done(status=cancelled)`, which the panel presents as "Stopped." rather than as a failure (`errors.ts`), and the session is usable again afterwards.
- [x] Untrusted workspace does not spawn the host. — `assertTrusted()` guards the spawn path, and `capabilities.untrustedWorkspaces.supported: false` keeps the extension from activating at all in such a folder. Asserted by the guard's position in `start()`, not by an integration test: an untrusted workspace is a property of the extension host.
- [x] The API key appears in neither settings nor logs. — The key has no configuration entry; it is read from `SecretStorage` in `readApiKey` and passed to `childEnv`, which is its only consumer. Nothing logs the environment, and the child's stderr is the only log path the extension has.
