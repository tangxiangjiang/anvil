# p_0.35.7 — Packaging and docs

**Status:** done  
**Milestone:** [m_0.35_vscode_extension.md](../m_0.35_vscode_extension.md)  
**Linked design:** [35-vscode-extension.md](../../../design/v1.0/35-vscode-extension.md)

## Goals

Make the extension installable by someone who did not build it.

## Scope

Cross-compiled sidecar, per-platform VSIX, runtime host resolution, provenance, version alignment, docs, packaging smoke test.

## Tasks

1. Build script (under `scripts/`) that cross-compiles `anvil-host` per platform and places it in the extension bundle.  
2. **Platform-targeted VSIX**: `win32-x64`, `linux-x64`, `darwin-x64`, `darwin-arm64` (extend as needed). Document the multi-target build.  
3. Host resolution at runtime: bundled binary → workspace/global setting override → `go build` fallback for contributors, with a clear error when none is found.  
4. Provenance check when spawning: verify the binary is the one shipped (path + hash), and document the trust model.  
5. Version alignment: extension version tracks the Anvil product minor; `initialize` asserts host/extension protocol compatibility and fails loudly on mismatch.  
6. Docs: extension README (install, settings, permissions, troubleshooting), root `README.md` section, and the 0.35 status row.  
7. Packaging smoke test: install the built VSIX into a clean VS Code profile and run one prompt.

## Tasks as delivered

1. **One build location.** `scripts/build-host.mjs` cross-compiles `source/cmd/anvil-host` with `GOOS`/`GOARCH`/`CGO_ENABLED=0` into `editors/vscode/bin/` — the same directory a developer's F5 window resolves the host from and the one `vsce package` picks up, so the binary that was run is the binary that is shipped. `--target <id>` builds one, `--all` builds every target in turn, and each build rewrites `bin/hosts.json` to describe the single binary now in the directory (a package carries one platform; a stale second binary is the thing the manifest exists to prevent). It also refuses to build when `internal/editorhost/proto.go` and `src/protocol.ts` name different protocol revisions, which is the compile-time half of task 5.
2. **Platform VSIX.** `scripts/package-vsix.mjs` compiles, builds the host for the target, and runs `@vscode/vsce` (a dev dependency, invoked through `node` because a `.cmd` shim needs a shell). Targets are `win32-x64`, `win32-arm64`, `linux-x64`, `linux-arm64`, `darwin-x64`, `darwin-arm64` — one more than the plan asked for on each of Windows and Linux, since the list is a table rather than code. Output is `anvil-vscode-<version>-<target>.vsix`; `npm run package:all` produces one per target. The target list lives in `src/hostBundle.ts` and the build script keeps a copy of it; `test/unit/hostBundle.test.ts` reads the manifest the script actually wrote and fails if a name in it is one the extension would not look for.
3. **Resolution order** is `hostBundle.ts`, `vscode`-free and unit-tested: an explicit `anvil.hostPath` first (resolved against the workspace when relative — the setting's default is now empty rather than `anvil-host`, so "not set" and "deliberately on PATH" are distinguishable), then the bundled `bin/anvil-host[.exe]` for this platform, then `anvil-host` on `PATH`. A spawn failure names which of the three was being looked for and what to do about it, because "could not start the host" alone does not say whether to reinstall the extension or fix a path. There is no `go build` fallback: a packaged extension has no toolchain, and a developer has `npm run build:host`, so a build-on-demand path would have been a third mechanism with no user.
4. **Provenance.** `bin/hosts.json` records file name, sha256, size, Go toolchain, protocol revision and build time; the extension hashes the bundled binary at spawn and refuses a mismatch or a bundled binary the manifest does not name. The check is skipped for a configured path or a `PATH` lookup, where there is nothing truthful to compare against — refusing those would break the developer loop while proving nothing. The trust model is written down in the extension README and in the design chapter's security section: it detects a broken or half-replaced package, not an attacker who can rewrite the manifest beside the binary.
5. **Version alignment.** `package.json` moves with the milestone (0.35.7). `initialize` still asserts the protocol revision and now fails with which binary answered, both revisions, and both ways out — a mismatch must not present as a hang. On top of that the host's version banner is compared with the extension's: a different *minor* is warned about in the panel (shipping a stale sidecar for one platform is the failure this phase makes easy), while a patch or newer build is not an error, because the wire contract is the protocol revision and refusing a newer sidecar would strand the user for nothing.
6. **Docs.** `editors/vscode/README.md` gained install-from-VSIX, source, packaging, provenance, and a troubleshooting table (wrong-platform package, checksum refusal, protocol mismatch, untrusted workspace, key/provider, no folder); the root `README.md` gained a layout row, a VS Code section with the packaging commands and the key-handling rule, a delivered 0.35 status line, and an honest "still deferred" line about marketplace publication.
7. **Packaging smoke test.** `scripts/smoke-packaged.mjs` extracts a built VSIX into a temporary directory, asserts the required files are there and that `src/`, the tests, the scripts, `node_modules/` and the workspace's own `.anvil/` state are not, verifies the packaged binary against the manifest inside the package, and then runs *that* binary out of the extracted tree, completes `initialize`/`initialized`/`shutdown` and asserts the protocol revision. A foreign-platform package has its tree and checksum checked and its binary deliberately not run. The one part a script cannot do — installing the VSIX in a window and sending a real prompt — is the manual pass below.

### What the extension package contains

Compiled JavaScript (`out/src/`), `media/`, the README, the LICENSE, `bin/anvil-host[.exe]` and `bin/hosts.json`. 25 files, ~9.7 MB, of which the sidecar is nearly all of it. `.vscodeignore` also drops source maps and the old `out/anvil-host*` build location.

## Acceptance

- A built VSIX installs and runs on a machine with no Go toolchain.  
- A protocol-version mismatch fails with an actionable message rather than a hang.  
- Root README and the roadmap index reflect 0.35.

**Verified here:** six targets cross-compile (Windows and Linux on x64, Windows and Linux on arm64, macOS on both architectures); the two VSIXes built during this phase (`win32-x64`, `linux-x64`) pass `smoke:vsix` — the Windows one end to end, the Linux one for tree and provenance, since a Linux binary cannot run on Windows; the packaged `anvil-host.exe` answers `initialize` with protocol 1 out of an extracted package with no Go toolchain involved. The protocol-mismatch message is pinned by `test/unit/hostClient.test.ts`, and the resolution order, the digest check and the version-drift rule by `test/unit/hostBundle.test.ts` (10 tests). Extension suite: 113 tests, all passing. Go: `go build ./... && go vet ./... && go test -count=1 ./...` green.

**Not verifiable here:** that the VSIX installs and streams from a real model in a window — that needs an editor and a key, and is the manual pass (`code --install-extension anvil-vscode-0.35.7-win32-x64.vsix`). `win32-arm64`, `linux-arm64`, `darwin-x64` and `darwin-arm64` are built but not run anywhere: their checks are the compile and the package tree, not a session.

## Non-goals

- Marketplace publication, auto-update, telemetry.
- Signing the VSIX, or any story for trusting a host binary other than the bundled one.
