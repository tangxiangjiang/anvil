# Milestone 0.47 — Editor polish

**Status:** done (2026-10-20)
**Product version:** 0.47.0

0.45 and 0.46 are not planned in this repository; this milestone deliberately starts at 0.47
and the gap is recorded here rather than left to inference.

0.44 finished the capability line. What is left between the product and a client people can
use all day is not another engine: it is capability the SDK already has that the editor host
never turned on (language servers, test and build commands), data the client already holds
that has no affordance (rewind, plans, the transcript), and a set of places where the product
is inconsistent with itself (one root per window, one rule scope, three version numbers).
0.47 is a polish line. It adds no engine and changes no public SDK shape; the design is
chapter [44](../../design/v1.0/44-editor-polish.md).

## Goals

1. **Wire what is designed.** A configured language server produces `lsp_*` tools; configured
   test and build commands produce `run_tests` and `build`. With nothing configured, every
   wire message is byte-for-byte what it is today.
2. **Give existing data an affordance.** Every user message offers rewind, expressed at the
   granularity the checkpoints actually have (a turn); a plan-mode answer can be opened as a
   document and approved or rejected; the transcript can be read in focus view, renders
   formulas, and exports to Markdown.
3. **Make the client usable without a mouse or a screen.** Live regions, roles, labels and a
   keyboard path cover a full ask → approve → finish cycle.
4. **State the boundaries.** Rules gain a user scope and protected paths; a multi-root window
   names its root instead of silently using the first folder; the version numbers in
   `package.json`, the host and the docs agree.

## Overall acceptance

1. With `anvil.lsp` and the test/build commands unset, `session.new` carries exactly the
   fields it carries today (pinned by an integration test), and no new tool appears.
2. A configured language server yields `lsp_*` tools that answer a definition/reference
   request; a server that cannot start does not fail the session.
3. A configured `test_command` yields `run_tests`, and `build_command` yields `build`.
4. Rewind offers fork-only, restore-only, and both; the two are reported separately; a run
   without a checkpoint offers no restore; the first message offers "new conversation".
5. A plan-mode answer opens as a read-only document; approval happens before any write tool
   is available; rejection stays in plan mode.
6. The focus view survives a webview reload; formulas render without a network request;
   `/export` writes Markdown that a Markdown preview opens.
7. A full ask → approve → finish cycle works with the keyboard alone, and the screen reader
   announces the completion and the approval request without per-token spam.
8. A user-level deny wins over a workspace allow; an allow rule never matches a protected
   path; the manager shows which file each rule came from.
9. A multi-root window chooses a root for a new conversation, shows it, and no code path
   falls back to `workspaceFolders[0]` silently.
10. `package.json`, the host's reported version and the documentation cutoffs agree.
11. `cd source && go build ./... && go vet ./... && go test ./...` green (run from Git Bash),
    `cd editors/vscode && npm test` green, and packaging plus the packaged smoke test green
    at the end of every phase.
12. The five webview documents share one visual grammar: a tool call is a row rather than a
    card, an edit is compared old beside new, and the manager panels draw sections with
    hairlines instead of frames (p_0.47.10, p_0.47.11).
13. A transcript row is marked by a state dot, the transcript's spacing is a rhythm rather
    than a per-rule accident, and the chat's text size is `anvil.chatFontSize`, applied to
    open conversations without restarting the host (p_0.47.12).
14. A run of transcript steps is joined by one vertical rail, a tool row is coloured and
    named for a reader (`Read`, `Edit`, `Bash`) with its path in the link colour, and the
    path opens the file at the line the call used (p_0.47.13).
15. A whole assistant reply is one rail, prose included; Thinking is a folded row with a grey
    dot and a chevron; and a finished row's `N lines of output` opens the full result in a
    read-only tab (p_0.47.14).
16. A stored conversation whose window contains no user turn opens at the turn that started
    the run, and a tool result whose call is not on screen draws its own row rather than
    printing the output as an error (p_0.47.15).
17. The transcript reads at a moderate density: a message and a row 16px apart, two messages
    20px, an output caption 4px under its row; `done` is green and `stopped` the warning
    colour; the 8px dots cover the rail; an opened call's IN and OUT sit in one hairline
    frame; and an answer that ends a turn closes on an end dot, `Summary` and its own first
    line, with the body below (p_0.47.16), in the live turn as well as in its replay
    (p_0.47.17).
18. A reply opens with a hollow start dot and the speaker's name and folds as one unit; the
    newest turn is open, earlier turns are closed with their conclusion on the header, and a
    turn the reader opened stays open (p_0.47.18).
19. An edit's long lines scroll by the side, not by the line: each side is one pane with a
    bar at its foot, the bars appear on hover, and the two panes move together (p_0.47.19).
20. While a turn runs, the status line shows an animated anvil and hammer, `Forging…` and a
    dim `esc to interrupt · Ns · step N/M`; the run's summary takes its place at the end
    (p_0.47.20).
21. The working mark is 18px with an orange hammer, its word turns through six forging verbs
    every three seconds (a host step text takes over), and the line holds a little room above
    the composer (p_0.47.21).
22. The working mark's drawing fills its view box (about 89% of each dimension), its spark's
    strokes are more than a pixel on screen, and the hammer still pivots on the anvil's face
    (p_0.47.22).
23. The root line and the token meter stay adjacent in that order whether or not a run is in
    flight, and the working line sits below them, nearest the composer (p_0.47.23).
24. The root line and the run's line scroll with the conversation as one 4px-rhythm footprint
    inside the transcript, its first line reserved so a run does not change its height; the
    conversation's context share rides on the root line, and the session's total sits inside
    the composer's actions row, ellipsised with its full text reachable (p_0.47.24).
25. The footprint's first line is exactly `max(1.5em, 18px)` tall whether or not a run is in
    flight and at every chat text size; its summary and its parenthetical each truncate in
    their own box; and the composer's select and buttons never shrink, so the total is the
    only thing that ellipsises (p_0.47.25).

## Non-goals

- `/btw`, browser automation, scheduled or looping runs, git worktrees, notebooks.
- A plugin marketplace, organization policy distribution, or a configuration service.
- Remote-SSH / container deployment of `anvil-host`.
- Structured plans and tool-call-level rewind.
- Multiple roots per window; cross-root checkpoints or search.
- Internationalization and RTL.
- Any change to the SDK's public API shape.
