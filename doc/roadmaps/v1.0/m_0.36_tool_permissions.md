# Milestone 0.36 — Tool permissions (rules, patterns, and a shell analyzer)

**Status:** in_progress  
**Product version:** 0.36.x

`p_0.36.1` is delivered; the problem statement below is the state this milestone was planned
against, kept as the record of why the three mechanisms are the ones being built.

## Goals

Make approval behave the way a mature coding agent's does. That behaviour is **three
deterministic mechanisms**, and none of them is a model decision:

1. **A rule table** — effects `deny > ask > allow`, matched against the *facts the approval
   card already shows*, authored by the user rather than decided per call.
2. **A shell analyzer** — a pure function that can *prove* a command read-only. It never
   guesses: what it cannot prove is asked about.
3. **The mode ladder** — `ask` / `accept_edits` / `plan` / `bypass` decides whether to
   **ask**, and does not rewrite the policy the user wrote.

Today Anvil has none of the three, so `ls` and `rm -rf /` raise the same prompt:

- The gate is one flat group set (`permission_groups`, `write,edit,shell,verify,web,mcp`),
  so "always allow" is all-or-nothing per group.
- The session allowlist remembers `(session, tool, scope)` — the granularity is the
  **tool**, not a command pattern, and it is in-memory only.
- File hooks match regexes/substrings, and the shell/write/edit denies are evaluated
  **inside the permission callback** — so any path that skips the callback skips them.
- There is no command analysis at all.

**Two defects this milestone also fixes**, both found while designing it:

- `.anvil/hooks.json` is loaded only under `SettingSourceProject`, and **neither the VS Code
  extension nor the CLI ever sets it** — so deny rules written in that file have never
  taken effect in either client.
- `bypass` installs no callback at all, which — once an `ask` rule exists — would mean the
  opposite of bypass (nobody to ask ⇒ deny). `bypass` should skip the *asking*, not the
  *policy*.

## Overall acceptance

1. With `{ "effect": "allow", "tool": "shell", "pattern": "git status:*" }`, `git status`
   runs without a prompt while `git status && rm -rf /` still prompts.
2. A `readonly` rule admits `ls`, `git status`, `git log --oneline` and
   `find . -name '*.go'`, and never admits `rm`, `git fetch`, `find . -delete`, `sed -i`,
   `ls > out`, or anything containing `$(…)` or a backtick.
3. A `deny` rule holds when **no** `Options.Permission` is installed, and holds in
   `bypass`.
4. An `apply_patch` touching two paths matches a path rule only when **every** path is
   covered.
5. A malformed `.anvil/permissions.json` fails `Create` naming the file, rather than being
   silently ignored.
6. `.anvil/hooks.json` deny rules take effect in the editor and the CLI (they never have).
7. `go test ./...` green in `source/`; the extension suite unchanged and green.

## Non-goals

- **Letting a model decide authorization.** The behaviour being copied is deterministic and
  auditable; a model in this path is neither.
- **OS-level enforcement** — containers, seccomp, filesystem isolation. That is
  [32](../../design/v1.0/32-sandbox-code-review.md)'s line. This milestone is the *policy*
  layer, not the *isolation* layer.
- **Rule inheritance** (user-level / enterprise managed settings). One workspace file.
- **A complete shell grammar.** `sh -c`, functions, aliases, and dynamic expansion are
  `cannot-prove` by design, not by omission.
- A rule marketplace, rule sharing, or per-rule telemetry.
