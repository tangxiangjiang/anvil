# p_0.42.4 — Declarative workflows

**Status:** planned (2026-10-19)
**Milestone:** [m_0.42_subagents_and_tasks.md](../m_0.42_subagents_and_tasks.md)
**Linked design:** [41-subagents-and-tasks.md](../../../design/v1.0/41-subagents-and-tasks.md),
[03-runtime-loop.md](../../../design/v1.0/03-runtime-loop.md)

## Goals

1. **Orchestration without an interpreter.** `run_workflow` evaluates a JSON DAG of subagents:
   dependency order, bounded concurrency, one level of fan-out, literal substitution.
2. **Refused before it spends anything.** A cycle, a duplicate id, an unknown dependency, an
   unknown field or a bad fan-out source is a tool error before the first child agent is created.
3. **One unit of work.** The workflow is one tool call; its result lists every step's status; a
   `background` workflow is one task in the table whose title is the workflow's name.
4. **The same child agent as every other phase.** A step is `spawn_agent`'s child: inherited
   permissions, narrowed tools, its own store file with the workflow call as its origin.

## Scope

`source/workflow.go` (new), `source/agent.go` (`buildRegistry` registration),
`source/internal/tools/{functool.go,groups.go}`, tests, and chapter 41's workflow section.

## Tasks

1. **The spec.** `run_workflow` parameters:

   ```json
   {
     "name": "review-and-fix",
     "max_parallel": 3,
     "background": false,
     "steps": [
       {"id": "scan", "prompt": "...", "tools": ["read", "search"], "model": "", "max_steps": 0},
       {"id": "fix", "depends_on": ["scan"], "prompt": "Fix {{scan.result}}", "tools": ["read", "edit", "verify"]},
       {"id": "check", "depends_on": ["fix"], "for_each": {"from": "scan", "path": "files"}, "prompt": "Check {{item}} ({{index}})", "max_parallel": 2}
     ]
   }
   ```

   - Top level: `name` (required), `steps` (1–32, required), `max_parallel` (1–8, default 3),
     `background` (default false).
   - Step: `id` (required, unique, `[A-Za-z0-9_-]{1,64}`), `prompt` (required), `tools`, `model`,
     `max_steps`, `depends_on`, `for_each`, `max_parallel` (1–8, default the workflow's).
   - Decoding uses `json.Decoder.DisallowUnknownFields`: a misspelled field is refused, not
     ignored, because the alternative is a workflow whose author believes a bound is in force.
   - `for_each` is `{"from": "<step id>", "path": "<key>"}`; `from` must be a step that appears
     earlier and is not itself a fan-out step (one level only).

2. **Validation before execution** (`source/workflow.go`):

   ```go
   func validateWorkflow(spec workflowSpec) error
   ```

   - unique ids; every `depends_on` and `for_each.from` names an existing earlier step;
   - no cycle (a DFS colouring, or a topological sort that reports the first id left over);
   - step count and fan-out bounds; `prompt` non-empty after trimming;
   - `{{id.result}}` references in a prompt name a step and no unknown `{{…}}` token is left (the
     only tokens are `x.result`, `item` and `index`).
   - On failure the tool result is `is_error: true`, lists every problem found (up to five), and
     no agent is created. The validation is a pure function and is tested without a provider.

3. **Execution** (`source/workflow.go`):

   - Ready steps run concurrently, bounded by `max_parallel`; the document's order breaks ties in
     the result listing and in which ready step starts first.
   - Each step creates its child through the same `subagentOptions`/`Create`/`Send`/`Wait` path
     as `spawn_agent`, with `description` = `<workflow name> / <step id>`, the workflow's name as
     the task title for background mode, and `ParentToolCallID` = the `run_workflow` call.
   - Substitution is literal and happens **once**, in the prompt string handed to the child:
     `{{id.result}}` → that step's final message; `{{item}}` / `{{index}}` → the fan-out element
     and its zero-based index. The result of the substitution is never re-scanned.
   - A step whose `depends_on` contains a failed or cancelled step is not run and is reported as
     `skipped`; steps already running finish. The workflow's status is `failed` if any step
     failed, `cancelled` if the workflow was cancelled, `finished` otherwise.
   - Each step counts against the tree's `MaxAgents`; a refusal fails that step (the workflow),
     not the host.
   - Cancellation: the workflow's context is the tool call's context for a foreground run, or the
     task's context for a background one; cancelling stops starting new steps, cancels running
     children, and returns `cancelled`.

4. **The result.** A readable block:

   ```text
   workflow review-and-fix: finished (3 steps, 2 failed-or-skipped if any)
   scan    finished  agent-…  List the files that mention Registry.Execute…
   fix     failed    agent-…  Fix the callers listed in …
   check   skipped   —        depends on fix, which failed

   fix: <the child's error, truncated to 2000 chars>
   ```

   Each step's final message is included for finished steps, truncated to 2000 characters with a
   `… [truncated; open agent-… for the full transcript]` tail naming the agent. The full messages
   are in each child's store file, which is the same rule a `spawn_agent` result follows.

5. **Background workflows.** `background: true` files the whole workflow as one `tasks` agent task
   (p_0.42.2): `Kind: agent`, title = the workflow name, output = the result block above. The
   tool returns the task id in the same shape as a background spawn.

6. **Registration.** In `buildRegistry`, when subagents are enabled and `depth+1 < MaxDepth`,
   register `run_workflow` beside `spawn_agent` as a `tools.FuncTool{Builtin: true}`; its group is
   `agent` (`groups.go` already names it). Internal (non-background) workflows share the depth
   rule: a step's child is at the same depth as a `spawn_agent` child, so a workflow cannot be
   used to get around the nesting limit.

7. **Docs.** Chapter 41's "Workflows" section is the contract; the honest boundary (orchestration,
   not a programming language) stays in the chapter and in the tool description.

## Acceptance

- [ ] A cycle, a duplicate id, a dependency on a later or unknown step, an unknown field and an
  unknown `{{token}}` each produce `is_error: true` listing the problem, and no child is created
  (a provider stub that counts requests sees zero).
- [ ] A linear three-step workflow runs `scan` → `fix` → `check`, and `{{scan.result}}` in `fix`'s
  prompt is the literal final message `scan` returned.
- [ ] Independent steps run concurrently up to `max_parallel` (a scripted provider observes at
  most N in flight), and the result lists them in document order.
- [ ] `for_each` over a JSON array runs one child per element with `{{item}}` and `{{index}}`
  substituted; a source that is not an array fails that step with a sentence naming the path.
- [ ] A failed step causes its dependents to be `skipped` and the workflow to be `failed`; already
  running independent steps finish.
- [ ] Cancelling the parent run cancels a foreground workflow's running steps and returns
  `cancelled`.
- [ ] A background workflow is one task whose title is the workflow name and whose output is the
  result block.
- [ ] At `MaxDepth`, `run_workflow` is absent from the child's tool list, the same as
  `spawn_agent`.
- [ ] `go test ./...` green; `gofmt`/`go vet` clean.

## Non-goals

- A JavaScript/Python workflow program, an expression language beyond literal tokens, conditionals,
  retries, or loops other than one `for_each`.
- Nested workflows (a workflow step that runs another workflow) and fan-out inside fan-out.
- Persisting a workflow definition in the workspace as a named, reusable file. The spec travels
  in the tool call; a project that wants reuse writes it into `AGENTS.md`, which is what the
  rules channel is for.
- Priority, deadlines, or scheduling of steps.
