# p_0.38.3 — Replay, and coming back to a session

**Status:** done  
**Milestone:** [m_0.38_session_identity.md](../m_0.38_session_identity.md)  
**Linked design:** [38-session-identity-and-replay.md](../../../design/v1.0/38-session-identity-and-replay.md), [35-vscode-extension.md](../../../design/v1.0/35-vscode-extension.md), [06-session-store.md](../../../design/v1.0/06-session-store.md), [08-security.md](../../../design/v1.0/08-security.md)

## Goals

1. **The stored conversation becomes readable.** A public reader over the records the store has
   held since 0.1, so a client can show a session it did not watch.
2. **The panel rebuilds the transcript.** Opening a session — or reloading the window onto one —
   fills the tab with what happened: the messages, the tool cards, and where each run ended.
3. **A reload does not lose the session.** The window comes back knowing which agent it was
   talking to, and re-attaches to it.
4. **The model's memory and the user's view agree.** The context already survives; this makes
   the visible half match it.
5. **Nothing new is exposed.** The reader returns what was already streamed to this panel and
   already written to this workspace's store — including the redaction that was applied before
   it was written, and nothing that was never written at all.

## Scope

`source/transcript.go` (new, public), `source/internal/editorhost/` (a method, its params and
result), `editors/vscode/src/` (`protocol.ts`, `hostManager.ts`, a new `transcript.ts`, a new
`reattach.ts`, `chatPanel.ts`), `editors/vscode/media/` (`chat.js`), the fake host, and the
tests and docs on both sides.

## Tasks

1. **The reader** — `anvil.LoadTranscript(cwd, agentID, opts)`: an ordered projection over
   `store.Load`, carrying each message's role and content, each tool call's id, name and
   **arguments**, and each run's boundaries with its status, steps and usage. Oldest first,
   capped, with what was dropped reported rather than silently cut.
2. **Not `historyFromRecords`.** That function folds records into model messages, discards run
   boundaries and applies the compression rule — three things a renderer must not inherit. The
   reader is a separate projection over the same load, and the design chapter says why.
3. **The host method** — `session.transcript`, keyed by agent id under the workspace root like
   `session.list`, so it answers after a reload when no session is open. Additive: no
   `ProtocolVersion` bump, no announced capability, and an older host answering `-32601` leaves
   the panel with no replay rather than an error.
4. **The mapping** — `src/transcript.ts` (new, no `vscode`) turns entries into the messages the
   panel already dispatches, so the replay reuses the existing renderers: the user message
   renderer, the Markdown renderer, the tool-card pair, and the run-end marker. A replayed tool
   card therefore gets p_0.38.2's review button for free.
5. **The re-attach** — the current agent id is remembered in `workspaceState` beside the mode,
   cleared when the conversation is cleared, and read on `ready`; the decision is a pure
   function so it can be tested without an extension host. Re-attaching reuses `resumeAgent`,
   which is what empties a reused tab before the replay fills it.
6. **No reasoning row.** Reasoning was never persisted; the replay shows none, and the docs say
   it is the one thing that does not come back.
7. **The version** — `editors/vscode/package.json` to `0.38.3` (the phase, as with 0.37.2 and
   0.36.2) and `editorhost.Version` to `0.38.0-dev` (the milestone). Both move together, because
   `versionDrift` compares *minor* lines: an extension bumped on its own would warn every user
   about a host that is perfectly fine. p_0.38.1 and p_0.38.2 are client-only phases of this same
   milestone and deliberately carry no bump of their own — the package this phase builds is the
   one that contains all three.
8. Tests and docs.

## Tasks as delivered

Five things the task list did not carry, and two acceptance items that needed saying better.

- **A `role: "user"` record is not always the user's turn.** This is the one that would have
  shipped as a defect, and it is the reason the mapping is a tested module rather than a loop
  inside `chatPanel.ts`. The loop writes its own notes to the model under the user's role — a
  vision note when attachments went out (`loop.go:243-248`), a loop-guard warning
  (`loopWarnMessage`, `loop.go:252-255`) — and sinks them with everything else, so a replay that
  trusted the role would put words in the user's mouth. What separates them is **position**: a
  run opens with the single message that started it (`loop.go:124` is the only place a run's own
  user message is sunk), so the first user record of a run is the turn and every later one is the
  loop's. The replay draws the first as a "you" bubble and the rest as a `note` line labelled
  *the loop put this into the conversation* — dropping them would hide a guard trip the user
  should see. **No store field was added**, and the rule does not depend on run ids being present:
  a `run_end` resets the flag, so a store written before run ids existed still reads correctly.
- **The run boundary needed a renderer of its own.** The live run's end arrives as a `done` and
  `finishRun` writes a status line; a replay has no `done`, and a transcript of three runs drawn
  without boundaries reads as one long turn. So the reader returns a `run_end` entry per persisted
  `run_end` record and the panel posts it as `{type:'runEnd', done}`, which `addRunEnd` draws as a
  centred marker. It shares `runSummary` with `finishRun` rather than reusing `finishRun` itself:
  the live path closes the *current* run and would report only the last of several replayed ones.
  The same renderer sweeps the cards still reading "running" **without** offering them a review —
  whether a call whose result never arrived actually landed is precisely what is not known, and
  p_0.38.2's rule is that a change which did not apply is not a change.
- **The replay is a second caller of `postEvent`, never of `onEvent`.** `onEvent` is where the
  change tracker takes a pre-image, and a pre-image read *now* filed under a historical call's id
  would list today's file contents under the present turn's changed files. Routing the replay
  through `postEvent` also means a replayed tool card is offered its review by the one place that
  decides reviews, so p_0.38.2's button works on a ten-minute-old card for free —
  `replayWiring.test.ts` asserts both halves.
- **A second client-side module, because the decision has three outcomes.** "Remember which
  session the window was in" reads like a boolean and is not: an id whose agent is gone must
  **clear the key**, which writes where doing nothing does not. `shouldReattach(stored, listed)`
  returns `'resume' | 'clear' | 'none'`, and its signature is the point — `listed` is
  `SessionInfo[] | undefined`, because a listing that could not be read (no host, a host that
  would not start, an untrusted workspace) says nothing about the agent and must not be mistaken
  for an empty one. Clearing there would forget a session that is perfectly intact.
- **The reader's limits are the store's, and the docs say so.** A call that **failed replays as
  completed**, because `is_error` is not a field of `store.Record` and was never written;
  reasoning has no row, because it was never written; an image-only turn replays as an empty user
  bubble, because the message record holds text and not parts; and a persisted `run_end` carries
  `RunID, Status, Steps, Usage` and **no `Err`**, so a replayed failure says how many steps it
  took and not why it stopped. None of these is a gap to be filled later by a better reader —
  each is a thing that is not on disk.
- **Said better:** acceptance item 3 says "more entries than the cap yields the most recent ones
  and reports how many were dropped", which is true of the *reader* and is what the Go test
  asserts. What the *tab* does with the count is one line in a note — the panel says how many
  earlier turns are not shown, rather than presenting a truncated conversation as the whole one.
  And acceptance item 4's "no entry ever carries … reasoning" is a claim about a field that does
  not exist rather than one the reader filters: `transcript_test.go` asserts every entry's kind is
  one of the two the reader can produce, so a third kind cannot appear unnoticed.

## Non-goals

- Replaying reasoning, checkpoints, or rewind.
- Paginating: the cap is a bound, not a cursor — no "load earlier" affordance in this phase.
- Persisting pre-images so a replayed diff is byte-exact.
- Replaying a session from another workspace, or listing across workspaces.
- Rebuilding the transcript on every event: replay happens when a session is opened or
  re-attached, and the live stream owns everything after that.
