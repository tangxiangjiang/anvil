# p_0.47.7 — One root per window

**Status:** done (2026-10-20)
**Milestone:** [m_0.47_editor_polish.md](../m_0.47_editor_polish.md)
**Linked design:** [44-editor-polish.md](../../../design/v1.0/44-editor-polish.md) §9

## Goals

1. **One resolver.** Every path decision goes through one function that names the window's
   root; no call site picks `workspaceFolders[0]` on its own.
2. **Multi-root is explicit.** A new conversation in a multi-root window asks which folder
   is the root, remembers the choice for the window, and shows it in the header.
3. **A started conversation does not switch roots.** The header says so instead of offering
   a control that would break checkpoints and paths.

## Scope

New `editors/vscode/src/workspaceRoot.ts`; replace the seven first-folder uses in `hub.ts`,
`hostManager.ts`, `editorContext.ts`, `changes.ts`, `chatPanel.ts`, and the MCP path helper;
`extension.ts` installs the resolver at activation; webview header; tests; README.

## Tasks

1. **Resolver.** Return `{folder, multi, chosenBy}` for the current window and a way to set
   the choice (`workspaceState`); single-root returns immediately without prompting.
2. **New conversations.** In a multi-root window, `QuickPick` before creating the session;
   cancel means no session; the chosen folder is passed as the session root.
3. **Replace call sites.** Point all seven at the resolver; `mcpFilePath` stops computing its
   own first folder.
4. **Header.** A persistent line naming the root, with a tooltip explaining the one-root
   model; no switch control on a started conversation.
5. **Tests.** A source assertion that no `workspaceFolders?.[0]` remains outside the
   resolver; picker behaviour (choose, cancel, remembered); single-root regression.
6. **Docs.** `editors/vscode/README.md` states the one-root-per-window limit and what to do
   with several roots (open another window).

## Decisions (before any change)

- **The resolver is the only reader of the folder list.** `workspaceRoot.ts`
  answers three questions: the window's root, the same as a URI for path
  arithmetic, and the root's facts for the header. Nothing else asks
  `workspace.workspaceFolders`; the resolver's own use is the one place the
  phase's grep is allowed to find.
- **The choice is per workspace file, shown per window.** It is stored in
  `workspaceState`, which VS Code scopes to the workspace rather than to a
  window; a second window on the same multi-root workspace opens with the
  remembered root already active, and its header says so without asking again.
  Window-only memory was rejected because a window reload would ask the same
  question again and the answer would always be the same.
- **A synchronous read is what path decisions use.** `workspaceState` is read
  once at activation, through the one context the module gets, and installed as
  the window's active root. Every later question — a diff URI, a mention, the
  MCP file path — is therefore synchronous, which is what those call sites need.
- **Cancelling is not an error.** `RootChoiceCancelled` exists so the panel can
  ignore it and the drop path can say one sentence; `HostManager.spawn` lets it
  propagate and creates no process, so "cancel creates nothing" is an ordering
  property rather than a cleanup path.
- **The header is a line, not a control.** One root per window means a started
  conversation has nothing to switch to; a select would promise a move the
  checkpoints and tool paths cannot follow.
- **A folder removed from the window clears the choice.** The thing that was
  chosen no longer exists, so the next question is asked instead of answering
  with a path outside the window.

## Implementation notes

### Resolver

`workspaceRoot.ts` exports `rootFolder`, `rootUri`, `rootInfo`, `isMultiRoot`,
`resolveWorkspaceRoot`, `initWorkspaceRoot` and `RootChoiceCancelled`. A
single-folder window returns immediately in both the synchronous and asynchronous
paths; a multi-root window answers from the active choice, else asks. Concurrent
callers share one in-flight picker (`choosing`), so two prompts cannot race to
write the state. A remembered entry for a folder this window does not contain is
ignored, and `onDidChangeWorkspaceFolders` clears the active root when its folder
is removed.

### Call sites

The seven first-folder reads became five imports: `changes.ts` and `chatPanel.ts`
(`fileUri`, the export default directory) use `rootUri()`; `chatPanel.ts`'s drop
path and `editorContext.ts` use `rootFolder()`, and the drop path awaits the
resolver so a file dropped in a multi-root window before its first conversation
still lands somewhere the person chose; `hub.ts`'s `mcpFilePath` uses `rootUri()`;
`hostManager.ts` awaits `resolveWorkspaceRoot` at spawn and passes it to the host
as `cwd`, which is the session root on the wire (`session.new` still carries no
`cwd`). The two user-facing sentences that said "workspace" where they meant the
root now say so.

### Header

The panel posts `{type: 'root', name, path, multi}` with everything a fresh
document cannot infer, and again from `onSession` — in a multi-root window the
root does not exist until the picker behind the first session has been answered.
`media/chat.js` writes the line with `textContent`: the folder's name in a
`code` element, its full path as the tooltip, and "one folder per window" only
when the window has more than one. The stylesheet gives it the same muted weight
as the status line.

### Tests

`npm test` 527 (from 521). The new file reads the sources as text: no
`workspaceFolders[0]` outside the resolver, the single-folder branch before the
picker, the shared in-flight promise, the cancel sentinel, the state write after
a pick, the remembered-folder preselect and its stale-entry filter, the resolver
before `new HostClient`, the header message and its text-only rendering, and the
activation ordering.

### What was not done

- **No root switcher, even on an idle window.** The choice changes only by
  starting a fresh window on the workspace, which re-reads the remembered
  folder. Adding "change the root" means deciding what happens to live
  conversations and their checkpoints, and that is the design this phase
  explicitly keeps out.
- **No per-conversation roots.** One host per window is the architecture; the
  root is the host's `cwd`, and two roots in one window would need two hosts and
  per-root panels.

### What was not walked

No part of this was seen in a real window: the picker, the remembered choice
surviving a reload, and the header's line all rest on the source assertions. The
manual pass — open a two-folder workspace, start a conversation, choose the
second folder, then dismiss the picker in a fresh window and watch nothing start
— is still worth doing.

## Non-goals

- Multiple hosts or checkpoints per window.
- Cross-root search, tasks, or MCP runtimes.
- Changing the host protocol (the root stays `cwd`).
