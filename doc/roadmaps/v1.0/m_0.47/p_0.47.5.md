# p_0.47.5 — Accessibility

**Status:** done (2026-10-20)
**Milestone:** [m_0.47_editor_polish.md](../m_0.47_editor_polish.md)
**Linked design:** [44-editor-polish.md](../../../design/v1.0/44-editor-polish.md) §7

## Goals

1. **A turn is followable by a screen reader.** Completion is announced politely; approval
   requests and errors assertively; streaming is throttled so it is not read token by token.
2. **Everything reachable by keyboard.** Composer → send → toolbar in that order; `Esc`
   closes; the slash menu works with arrows and Enter.
3. **Labels and roles.** The transcript is `role="log"`; icon-only controls have
   `aria-label`s; approval controls are a named group.

## Scope

`editors/vscode/media/chat.js`, `media/chat.css`, the panel documents' toolbar markup,
`test/unit`; a manual pass with a screen reader and both a dark and a high-contrast theme.

## Tasks

1. **Inventory first.** Record every existing `aria-*`, `role`, and keyboard handler, and
   list the gaps in the phase's implementation notes before changing anything.
2. **Live regions.** One `polite` region for turn completion and one `assertive` region for
   approvals/errors; update at most every 500 ms while streaming, with the final text sent
   once.
3. **Roles and labels.** `role="log"` on the transcript; `aria-label` on every icon button;
   `role="group"` + `aria-labelledby` on approval actions; visible focus styles checked in
   the dark and high-contrast themes.
4. **Keyboard.** Tab order, `Esc` behaviour, and arrow/Enter in the slash menu; no focus trap
   that strands the user in a closed dialog.
5. **Tests.** Source assertions for the live regions, the log role, and the labels; a small
   DOM test if the harness allows it.
6. **Manual.** One full ask → approve → finish cycle with the keyboard only and one with a
   screen reader; record the reader, version and themes used.

### Gaps

1. **The transcript is the live region.** `aria-live="polite"` sits on the element every
   streamed token mutates, so a reader is asked to read the answer token by token. There is
   no separate completion announcement.
2. **No assertive region.** An approval request, a run error (`addNotice`) and an error
   banner (`showBanner('error', …)`) all arrive silently.
3. **Approval controls are an unnamed group.** `.approval .buttons` (`chat.js:1465`) has no
   group role and the card's head has no id to label it with.
4. **Icon-only controls without a name.** `.chip-x` ("×", `chat.js:1656`) and the banner's
   `.dismiss` ("✕", `chat.js:2799`) carry only a `title`. The `@` attach button's visible
   name is the symbol itself.
5. **`#todos`'s label is not exposed.** `aria-label` on a generic `div` with no role is
   ignored, and the rows have no list structure.
6. **Buttons have no themed focus ring.** Only links, the textarea and the mode select draw
   one; everything else falls back to the user-agent ring, which is not drawn from
   `--vscode-focusBorder` and has no high-contrast treatment.
7. **Focus is dropped when a turn starts.** `setRunning(true)` disables the textarea, so the
   focused element disappears; an approval card then appears with nothing focused and no
   keyboard path to it except tabbing through the transcript.
8. **The slash palette exposes no list semantics.** It is operable with arrows and Enter,
   but a screen reader sees neither a list nor the current option (no `role`, no
   `aria-activedescendant`).

Gaps 1–7 are fixed below; gap 8 is not, and the reason is recorded with the other
limitations.

## Implementation notes

- **The transcript is a log, not a live region.** It keeps `role="log"` and gains an
  explicit `aria-live="off"` and the name *Conversation*. A log's implicit politeness is
  exactly wrong here: every streamed token mutates the element, so a reader would be asked
  to read the answer as it was typed. The two regions answer the two questions the
  transcript cannot: what was said, and what just happened.
- **Two regions, two urgencies.** `#srStatus` is `role="status" aria-live="polite"
  aria-atomic="false"`; `#srAlert` is `role="alert" aria-live="assertive" aria-atomic="true"`.
  The polite one is written by appending a node per announcement rather than replacing its
  text, because a live region announces the node that changed and a replacement would make
  the reader hear everything already said again; the region keeps the last four nodes, then
  drops from the front. The assertive one is replaced: it carries one sentence and is not a
  history.
- **What is said, and when.** A finished answer block is said whole from `endRound`, once,
  from the rendered body rather than the raw Markdown (no backticks read aloud). A child
  agent's block is not announced: it is read where it is drawn, in its card. A conversation
  being replaced ends its round silently, and a whole replay is bracketed by
  `replayStart`/`replayEnd` (a document-to-script message, not the host protocol) so
  opening a stored conversation does not read it aloud block by block. `finishRun` then
  says one of *Answer finished.*,
  *Turn stopped.*, or *Turn ended with an error.*, after the last block, so the two arrive in
  the order they happened. Host progress lines (`progress`) reach the polite region through
  `announceProgress`, throttled to one per `ANNOUNCE_INTERVAL_MS = 500`; a later line inside
  the window is dropped rather than queued, because a status line that is already stale is
  not worth hearing.
- **Assertive is a short list.** Exactly five uses: the approval request, a run error
  (`addNotice`), an error banner, a failed "remember" write, and the definition itself. The
  test counts them so a sixth is a decision rather than a drift. An approval is announced as
  the tool plus the preview's summary when there is one; the verdict (*Allowed.*, *Denied.*,
  *Allowed, keeping n of m parts.*, *no longer pending*) goes to the polite region.
- **Focus has an owner at every step.** `setRunning(true)` notes whether the textarea had
  focus before disabling it and moves focus to the send/stop button, which keeps the keyboard
  inside the composer and leaves <kbd>Esc</kbd> where it was. An approval card focuses its
  first answer when it is drawn — the turn is running, so nothing else owns the keyboard, and
  tabbing through the transcript is not a path a blocking question can depend on. Answering
  it disables the pressed button, so focus returns to the stop control rather than to the
  document; the check is made before the buttons are disabled, which is when the browser
  moves focus. There is no focus trap and no inert content, so no dialog can strand anyone.
- **Names and roles.** The send/stop button already had a dynamic `aria-label`; the chip's
  `×`, the banner's `✕` and the `@` button now have one, and `title` stays a tooltip. The
  approval buttons are `role="group"` labelled by the card's question, which is given an id
  from a counter (never from the host's request id). The task list is `role="list"` with
  `role="listitem"` rows, because its `aria-label` sat on a generic `div` where it was not
  exposed.
- **Focus styles are one rule per surface.** `:focus-visible` draws a one-pixel ring in
  `--vscode-focusBorder` on buttons, selects, textareas, disclosures and rendered links; the
  `vscode-high-contrast` and `vscode-high-contrast-light` body classes swap it for a
  two-pixel `--vscode-contrastActiveBorder` ring, which is the colour those themes publish
  for exactly this. Nothing sets `outline: none`.
- **`.sr-only` is clipped, not hidden.** `display: none` and `visibility: hidden` remove the
  text from the accessibility tree, which is the one thing a live region may not be; the
  class keeps a one-pixel box on screen.
- **Tests.** `npm test` is 517 green (from 508): the new `test/unit/accessibility.test.ts`
  (9 tests) reads `chatPanel.ts`, `chat.js` and `chat.css` as text, since no webview runs
  here. One existing test changed with the markup: `todoList.test.ts` looked for the exact
  opening tag of `#todos`, which now carries `role="list"`.

### What was not done

- **The slash palette has no list semantics.** It is fully operable from the composer
  (arrows, <kbd>Enter</kbd>, <kbd>Tab</kbd>, <kbd>Esc</kbd>), which is the phase's
  requirement, but a screen reader is not told it is a list or which row is current. Doing
  that properly means a combobox: `aria-activedescendant` must point into a list the focused
  element owns, and the focused element is a `<textarea>` outside the palette. That is a
  different control, not a label, and it is left for a phase that owns the composer's
  semantics rather than guessed at here.
- **The other webview documents keep the user-agent focus ring.** Review, permissions, MCP
  and tasks were inventoried and their buttons all carry visible text, so they have names;
  only their textareas and selects draw a themed ring. The stylesheet change is per document
  and this phase scoped its CSS work to the chat view.
- **No automated accessibility CI.** A non-goal of the phase; the source assertions are the
  substitute.

### What was not walked

No part of this phase was seen in a running window. There is no screen reader, no dark
theme and no high-contrast theme in this environment, so the following rest on the source
assertions: that the polite region is actually read once per block and not per token, that
the assertive region interrupts as intended, that focus lands on the approval card without
moving the reader's place in a way that confuses, that the two-pixel ring is visible on the
real dark themes, and that a keyboard-only <kbd>Enter</kbd> → <kbd>Tab</kbd> →
<kbd>Enter</kbd> cycle reaches *Allow* and the completion announcement. The manual pass —
one ask → approve → finish with the keyboard, one with a screen reader, in a dark and a
high-contrast theme, recording the reader and its version — is still worth doing.
