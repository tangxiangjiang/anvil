# p_0.47.6 — User-scope rules and protected paths

**Status:** done (2026-10-20)
**Milestone:** [m_0.47_editor_polish.md](../m_0.47_editor_polish.md)
**Linked design:** [44-editor-polish.md](../../../design/v1.0/44-editor-polish.md) §8

## Goals

1. **Rules have a user scope.** `~/.anvil/permissions.json` is loaded and merged with the
   workspace file.
2. **Severity decides, not file order.** `deny > ask > allow`; a workspace rule cannot
   weaken a user-level deny.
3. **Protected paths cannot be auto-approved.** An allow rule never matches `.git/`,
   `~/.anvil/`, or `.anvil/checkpoints/`; the decision is labelled in the approval record.

## Scope

`source/internal/permissions/` (load, merge, match, report), `source/options.go` if a path
needs to be configurable, `source/internal/editorhost/` (permissions.get/add/set),
`editors/vscode/src/permissionsPanel.ts` and its media; tests; chapter 37.

## Tasks

1. **Loading.** Read `~/.anvil/permissions.json` (missing file is empty, malformed file is a
   reported problem, never a silent ignore) and keep the workspace file as it is.
2. **Merging.** Build one set with provenance; conflicts resolve by severity; a user deny is
   absolute. Document the precedence in the package comment and in chapter 37.
3. **Protected paths.** A fixed list plus an optional user-level setting; the matcher marks
   a decision as protected and allow rules skip it. `bypass`/`dontAsk` still act but the
   approval record says `protected`.
4. **Protocol and manager.** `permissions.get` reports `user_path` and each rule's source;
   `permissions.add`/`set` name their target file; the panel shows user and workspace
   sections separately and keeps the read-only-on-malformed contract.
5. **Tests.** Table tests for every precedence pair across scopes; protected-path tests per
   rule shape; provenance strings; the manager's two-layer rendering.
6. **Docs.** Chapter 37 gains a "Scopes and protected paths" section; the extension README
   documents both files.

## Non-goals

- Organization policy distribution or a remote configuration service.
- More than two scopes, or per-project overrides inside the user file.
- Matching on tool arguments beyond what the existing rule shapes already support.

## Depends-on

- p_0.36.x (rule shapes and the analyzer), p_0.37.x (modes), p_0.41.x (the manager).

The gaps, in the order they are fixed below:

1. No user-level file exists, so a preference has to be copied into every repository.
2. `Decision.Index` counts a position in the merged list, so it is not a line a reader can find in any file; with two files it would be wrong in both.
3. Severity is applied inside one list; there is no rule that a workspace allow cannot weaken a user deny, because there is no second scope to test it against.
4. Nothing marks a path as one an `allow` rule may not cover.
5. `permissions.get` cannot report a user file, a rule's source or a protected path; `permissions.add` has no target other than the workspace file.
6. The manager draws one layer; the two-layer rendering and the create-the-user-file step do not exist.
7. `~/.anvil` has no test-time override, so any code that reads it would make `go test` depend on the developer's own home.

## Decisions (before any change)

- **One home resolver.** The user file is `$ANVIL_HOME/permissions.json` when
  `ANVIL_HOME` is set, else `~/.anvil/permissions.json`. The environment override is
  the same one tests need, and it keeps `go test` from reading the developer's
  machine-wide policy. `~/.anvil` already exists (MCP OAuth tokens), so this adds
  no new directory concept.
- **Two file shapes, not one.** The workspace file keeps `{version, defaultMode,
  rules}`; the user file is `{version, protected, rules}`. A workspace may not
  declare protected paths (a repository cannot add paths it is allowed to write
  without asking), and a user file may not declare a starting mode (the mode of a
  session is the session's, not the machine's). Both parsers refuse unknown keys,
  so neither silently accepts the other's shape.
- **Merge order is user, workspace, code; severity still decides.** `deny > ask >
  allow` across the whole set. Within one effect the first rule in that order wins,
  which is the old "first in the file" rule extended by one layer. Every compiled
  rule keeps its own file and its own one-based index, so a citation names a line a
  reader can open (`user permissions.json rule 2`, `.anvil/permissions.json rule 1`,
  `session rules rule 3` for rules passed in `Options.PermissionRules`).
- **Protected paths are checked at evaluation, not at writing.** An `allow` rule is
  skipped when the call touches a protected path; `deny` and `ask` still decide.
  The fixed list is `.git/` (any segment), `.anvil/checkpoints/` under the
  workspace, and `~/.anvil/`. The user file adds globs. The fact is reported as
  `protected` on the decision, the approval card and the tool result — including
  where `bypass` allowed the call — so the record says why no allow could have
  covered it.
- **The rule report is one list with sources.** `permissions.get` keeps one
  `rules` array in merge order, each entry carrying `source`; the manager groups by
  it. A same-severity conflict therefore keeps both rules and shows both sources,
  rather than the merge dropping one.
- **A malformed user file is as fatal as a malformed workspace file at session
  start**, and just as read-only in the manager. The manager does not need a
  session, so it stays reachable to fix it.
- **`permissions.set` targets one layer per call** (`source`: `workspace` default,
  or `user`). A save of the user layer may create the file only when the client
  says so with `create`, which is the "person asks to create it" step; the
  workspace layer keeps today's create-on-save behaviour.

## Implementation notes

### Loading and merging

`internal/permissions` gained `AnvilHome()`, `UserPath()`, `LoadUser` and
`ParseUser`. `ANVIL_HOME` is the override; both test packages set it in
`TestMain`, and `isolateHome` in the host tests sets it per test — without that,
every host test would share one policy file, which the first round of tests
showed by leaking a rule between cases.

`Merge` composes user, workspace and code sets; each compiled rule carries its
own `Source` and one-based `Index`, and `Decision.Ref()` renders the citation
from those two fields. `Source.Read()` re-composes both files per call and keeps
the last good set when a file stops parsing — the session-start path is the one
that refuses, and `buildPermissionRules` now does that for the user file with
the same `load permissions`-style error as the workspace's.

One correction came out of the merge tests: `Merge` returned nil whenever the
combined set had no rules, which would have dropped a workspace file that only
declares `defaultMode`, and a user file that only adds protected globs. It now
returns nil only when there is nothing at all; a mode-only or globs-only file
survives, which is also what `Source.Read` needs to install the protection.

### Protected paths

`Protection{Root, Home, AnvilHome, Extra}` is installed on the merged set by
both the session and the manager's evaluation. `Evaluate` computes the
protected paths first, then skips `Allow` rules when any is present, and always
sets `Decision.Protected` — matched or not, so a call the mode decided still
says why no allow could have. The fixed list is any `.git` segment, the
workspace's `.anvil/checkpoints/`, and the Anvil home in full. User globs are
anchored exactly as a path rule's pattern is (`secrets/**` is the root's
directory, `**/secrets/**` is any depth), so the manager's help text says the
fixed list is already there and does not invite duplicates.

`PermissionRuleOptionsIn` builds the "always allow" options from the same
protection, so a card over `.git/config` offers none; the host's card builder now
calls it instead of the unprotected variant, which keeps chapter 36's promise
that every offered option decides the call.

### Protocol and host

`permissions.get` reports `user_path`, `user_exists`, `user_problem`,
`protected`, and `source` on every rule; a workspace file that will not parse
still lists the user layer, and the other way round. `permissions.add`/`set`
validate `source` and return `{path, source, index}`. A pending approval settled
by an append is evaluated across both scopes (`EvaluatePermissionRulesAcross`),
so a user deny or a protected path prevents a false `approved`. `permissions.set`
on the user layer refuses `default_mode`, on the workspace layer refuses
non-empty `protected`, and refuses to write over a malformed user file; only the
user layer has `create`.

`protected` travels on `ApprovalRequestParams` and on `EventParams` (and through
the runtime's own event mirror), which is what the card and the tool card read.

### Manager

`permissionsPanel.ts` splits the merged list by `source` — a rule without one is
the workspace's, which is every rule an older host sends — and posts
`userRules`/`workspaceRules`, the user path and existence, the user problem and
the protected globs. The document draws one section per file. Each section has
its own dirty flag, Save and status, so a broken user file does not freeze the
workspace's section. A missing user file is read-only with a single "Create user
file" button that sends `{source: 'user', create: true, rules: [], protected:
[]}`; saving without it is refused by the host too. Open JSON names its layer,
and the hub opens the user file where the host says it is.

The approval card shows "Protected path — no always-allow rule can cover it"
beside the paths; the tool card shows `protected path:` even when no rule
decided it. Both use `textContent`.

### What was not done

- **Two sections, not two documents.** They share one document because one file's
  rules cannot be understood without the other's: severity decides across both,
  and the panel has to show a conflict between files. A separate user-file
  manager would have made the merge invisible exactly where it matters.
- **No per-project overrides inside the user file.** The phase's non-goal; a
  repository that wants different rules still writes its own file.
- **Protected paths are not checked for shell calls.** A shell rule matches the
  command line, and `.git/config` in a command string is not a path the card
  showed. Chapter 37 records this as the honest limit rather than pretending the
  command was inspected.

### What was not walked

No part of the manager was seen in a running window: this environment has no
extension host. The two-section layout, the create button's transition from an
empty read-only section to an editable one, and the card's protected line rest
on the source assertions and on the Go tests' wire checks. The manual pass —
open both files, create the user file, write a deny and watch a workspace allow
lose to it, then ask to write `.git/config` and confirm the card explains
itself — is still worth doing in a real window.
