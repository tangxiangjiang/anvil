# p_0.47.6 — User-scope rules and protected paths

**Status:** planned (2026-10-20)
**Milestone:** [m_0.47_editor_polish.md](../m_0.47_editor_polish.md)
**Linked design:** [44-editor-polish.md](../../../design/v1.0/44-editor-polish.md) §8

## Goals

1. **Rules have a user scope.** `~/.anvil/permissions.json` is loaded and merged with the
   workspace file.
2. **Severity decides, not file order.** `deny > ask > allow`; a workspace rule cannot
   weaken a user-level deny.
3. **Protected paths cannot be auto-approved.** An allow rule never matches `.git/`,
   `~/.anvil/`, or `.anvil/checkpoints/`; the decision is labelled in the approval record.

## Scope

`source/internal/permissions/` (load, merge, match, report), `source/options.go` if a path
needs to be configurable, `source/internal/editorhost/` (permissions.get/add/set),
`editors/vscode/src/permissionsPanel.ts` and its media; tests; chapter 37.

## Tasks

1. **Loading.** Read `~/.anvil/permissions.json` (missing file is empty, malformed file is a
   reported problem, never a silent ignore) and keep the workspace file as it is.
2. **Merging.** Build one set with provenance; conflicts resolve by severity; a user deny is
   absolute. Document the precedence in the package comment and in chapter 37.
3. **Protected paths.** A fixed list plus an optional user-level setting; the matcher marks
   a decision as protected and allow rules skip it. `bypass`/`dontAsk` still act but the
   approval record says `protected`.
4. **Protocol and manager.** `permissions.get` reports `user_path` and each rule's source;
   `permissions.add`/`set` name their target file; the panel shows user and workspace
   sections separately and keeps the read-only-on-malformed contract.
5. **Tests.** Table tests for every precedence pair across scopes; protected-path tests per
   rule shape; provenance strings; the manager's two-layer rendering.
6. **Docs.** Chapter 37 gains a "Scopes and protected paths" section; the extension README
   documents both files.

## Acceptance

- [ ] A user deny beats a workspace allow for the same tool and argument.
- [ ] Same-severity conflicts keep both rules and report both sources.
- [ ] An allow rule never matches a protected path in any mode.
- [ ] A malformed user file is reported and read-only; it is not replaced.
- [ ] Rule reports stay line-traceable (`user rule 2`, `.anvil/permissions.json rule 1`).
- [ ] Go tests and `npm test` green.

## Non-goals

- Organization policy distribution or a remote configuration service.
- More than two scopes, or per-project overrides inside the user file.
- Matching on tool arguments beyond what the existing rule shapes already support.
