# Milestone 0.46 — anvil-web Delivery polish

**Status:** in_progress
**Product version:** 0.46.x

0.33 shipped the Delivery surfaces and 0.39 made them drive real jobs. What neither milestone
addressed is whether an operator can trust the console: today a mis-click destroys the whole
planning record, 24 native dialogs are reachable, a slow response can repaint a page the user has
already left, and the four sections open differently. This milestone is the polish pass — no new
capability, and no change to any scheduler or daemon semantics.

The measured starting point (`source/internal/web/static/`):

| File | Size | Note |
|---|---|---|
| `js/features/delivery.js` | 237 KB / ~6 000 lines | four surfaces, a wizard, an AI dock, a canvas drag engine and ~40 modal builders in one object literal |
| `css/app.css` | 59 KB | single stylesheet, dark theme only |
| `js/features/clusters.js` | 52 KB | re-implements the helpers Delivery already has |

Two properties of the current shape drive every phase below: **every mutation re-fetches the whole
snapshot and re-renders the whole subtree** (`await this.reload()` appears 52 times), and
**rendering is `innerHTML` string concatenation with `esc()` called by hand** (correct today, one
omission away from stored XSS, and no test would catch it).

## Goals

1. **A destructive action costs more than a click.** The one-click full-store delete is already
   removed (see *Changed on the way in*); the remaining destructive paths (delete milestone,
   delete design, delete version, seal a major) each state what they remove.
2. **No native dialogs.** `alert` / `confirm` / `prompt` disappear from the web UI in favour of the
   in-app notice and modal that already exist.
3. **Every async action is single-flight and says it is running.** A second click on a job-enqueuing
   button is a no-op, not a second job.
4. **A response never paints a route it did not start in.** Render is guarded by a token.
5. **The four sections share one information architecture** — one generation scope, breadcrumbs on
   every detail view, loading and empty states that were designed.
6. **The front end can absorb the fixes** — module boundaries, one definition per helper, and tests
   over the pure functions.
7. **The console can be worked in, not only read.** A real assistant (p_0.46.6), a session surface an
   operator can type into and watch (p_0.46.7), bulk and keyboard operation (p_0.46.8), and a console
   that explains itself (p_0.46.9).
8. **No assistant writes as a side effect of talking.** A suggestion becomes a record only through an
   explicit accept.

## Extension: from "can look" to "can operate" (p_0.46.6 – p_0.46.12)

The phases above make the console *safe*. An audit after they landed found the larger gap: several
surfaces only look finished, and an operator who tries to do real work hits a stub, a mock, or a
capability that exists in the SDK and not in the client. Concretely, discovered by reading the code
rather than by using it:

| Finding | Evidence |
|---|---|
| Three AI assistants wrote to the database on Send | fixed in p_0.46.1 (see *Changed on the way in*) |
| The remaining four AI assistants are local string templates | `"(mock polish) Clarify acceptance: "` in roadmap.js, test.js, modals.js, wizard.js |
| The web backend has no AI endpoint at all | `delivery_api.go`'s 15 routes are CRUD/jobs/campaigns only |
| No LLM call path exists for web | design 23 states agentd is not an LLM proxy; anvil-web inherits that |

So 0.46 is extended from "polish" to "operable": the four phases below close the gap between a
surface that renders and a surface that does the job. They are additive — p_0.46.1–p_0.46.5 are
done and unchanged.

## Changed on the way in (not part of any phase)

`Reset demo data` was a test affordance and has been removed from the UI, the API and the store:

- `POST /api/v1/delivery/reset` deleted (`delivery_api.go`)
- `Store.Reset()` deleted (`delivery/store.go`) — it issued `DELETE FROM` on all 16 `delivery_*` tables
- the button, its handler and `Features.delivery.reset()` deleted (`delivery.js`), and the now-constant
  `headActions` removed with them
- `api.v1.deliveryReset()` deleted (`api.js`)

The seeded first-run data (`EnsureSeed` → `seedDemo`) is untouched: a brand-new install still opens
on a populated example.

**The mock assistants no longer write.** Three surfaces saved on Send without confirmation: the Design
assistant appended `· (AI mock) <your text>` into the ADR Decision and, when a version was cited, into
that version's Gate; the milestone and version assistants appended the same into Completion criteria.
The Gate case was the dangerous one — every checkbox in a Design Version Gate blocks real phase jobs,
so a mock reply could add an unchecked box that stops a milestone from starting.

Those three now draft only: the reply states that nothing was saved, shows the draft against the field
it would land in, and leaves applying it as an explicit edit-and-save. Left as they were, because they
already require a second explicit action: Test cases (Save cases), Polish (writes a textarea), and the
major/milestone assists (write form fields). p_0.46.6 replaces all seven with a real assistant on the
same invariant.

Order is not arbitrary. **p_0.46.1 is the bleeding edge** — it is small, independent of everything
else, and stops the two things that make the console feel unsafe. **p_0.46.3 lands before
p_0.46.4** so the information-architecture work is one focused diff per surface instead of a rewrite;
it can run in parallel with p_0.46.1 because the two touch disjoint concerns.

**p_0.46.6 gated the rest of the extension.** An AI endpoint is what makes the Workbench worth
building (p_0.46.7), and both of them are what an operator actually uses — so p_0.46.8 and p_0.46.9
follow rather than lead. Doing the lists first would optimise a surface nobody can start work from.

**p_0.46.10–12 close the three structural gaps the audit found**, and each is placed after the phase
that builds the thing it extends rather than being deferred to an imaginary 0.47:

- Nothing persisted a job's events. `jobHub.publishEvent` keeps a 200-frame in-memory ring and the
  database keeps one string (`job_last_event`), so a failed job cannot be diagnosed from the console
  at all — p_0.46.10. It lands after p_0.46.7 because the event renderer is shared, and it is the
  highest-value of the three: "why did it fail" is the question asked most often.
- Nothing recorded who did what. A plan that a team hands to agents has to be able to say who
  approved it — also p_0.46.10, in the same schema change.
- A transition could be forced through an incomplete Gate. The console warns; it does not refuse.
  p_0.46.11 makes the refusal structural and, more importantly, makes the reason visible *before* the
  click. This is what keeps a handover honest rather than merely documented.
- The console assumed a wide, stable desktop. p_0.46.12 does not chase mobile parity; it makes the two
  things an operator does away from a desk (see state, stop a runaway job) work on a phone and survive
  a dropped connection.

## Overall acceptance

1. `grep -rn "alert(\|confirm(\|prompt(" source/internal/web/static/js` returns nothing.
2. Every destructive action names what it removes and requires explicit confirmation before the
   request is sent.
3. A navigation performed while a mutation is in flight produces no paint into the new route.
4. Every job-enqueuing button is single-flight: a double-click enqueues exactly one job.
5. A gate-check toggle repaints one strip, not the page.
6. The same generation context is visible and changeable from all four sections, and every detail
   view has a breadcrumb back up.
7. No file in `static/js/` exceeds ~1 200 lines, and `esc` / `badge` / `lifecycleLabel` are defined
   exactly once.
8. The pure functions named in p_0.46.5 have tests that run in CI, and removing an `esc()` from a
   sampled builder fails one.
9. No assistant surface writes to the store as a side effect of a chat message. A suggestion
   becomes a record only through an explicit accept, and the accepted value is what the model
   returned, not the operator's prompt with a label.
10. An operator can start a session on a Worker, see it stream, answer an approval, and stop it,
    from anvil-web — the same path the VS Code client has — without touching a CLI.
11. A multi-item action (create N cases, drive N milestones) is possible without repeating one
    form N times, and every destructive one of those still confirms.
12. A job that ran last week can be opened and read: its events, its error, its duration — the console
    can answer "why did this fail" without a shell.
13. Every mutation is attributable: who changed a requirement, who approved a design, who sealed a
    generation, and when.
14. A search box finds a word inside a requirement's completion criteria, not only in a title.
15. A transition that would be structurally incomplete is refused by the server and explained by the
    button before it is clicked, from one shared implementation.
16. At 375 px an operator can see fleet state and stop a running job; a dropped connection is visible
    and resumes without losing or duplicating an event.

## Non-goals

- A framework rewrite (React/Vue). The current shape is fine once it is modular and tested.
- Light theme, theming system, i18n.
- Mobile layout beyond the existing `@media` breakpoints.
- Real-time multi-user collaboration or presence.
- Replacing the canvas drag editor; it works and is not where the pain is.
- Any change to scheduler, agentd or the Delivery schema. p_0.46.1–p_0.46.5 and p_0.46.8–p_0.46.9 are
  presentation and client behaviour only; p_0.46.6 / p_0.46.7 add **one web-side endpoint each**
  (assist, workbench sessions) and no schema change.
- Deterministic markdown export, GraphPatch apply, delivery retrieval — unchanged from 0.33 / 0.39.
- An IDE in the browser: no diff review, hunk acceptance, checkpoints or notebook editing. Those are
  the VS Code client's (0.35–0.40) and duplicating them would be a second implementation to keep in
  sync.
- Autonomy: nothing the assistant proposes is applied without an accept, and no agent acts on the
  planning documents without a human starting it.
