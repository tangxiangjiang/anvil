# p_0.36.2 — Remember the pattern, and say why

**Status:** done  
**Milestone:** [m_0.36_tool_permissions.md](../m_0.36_tool_permissions.md)  
**Linked design:** [36-tool-permissions.md](../../../design/v1.0/36-tool-permissions.md), [35-vscode-extension.md](../../../design/v1.0/35-vscode-extension.md)

## Goals

The half of "intelligent authorization" that is about the *conversation with the user*
rather than the decision:

1. **Remembering a pattern, not a tool.** The approval card's "always allow" gains the
   choices a rule file can express — this exact command, this prefix, anything read-only —
   instead of today's all-or-nothing per tool.
2. **Saying why.** When a call is not prompted, the client can say which rule allowed it
   (`allowed by rule 3: shell git status:*`); when it is denied, the deny's `reason`.
3. **Authoring the file.** A command to open/create `.anvil/permissions.json`, validated
   against the same loader the SDK uses, so a rule the UI writes is a rule the SDK accepts.

This phase is where the protocol and `editors/vscode/src/` change; `p_0.36.1` deliberately
wrote none of it.

## Scope

`source/internal/editorhost/` (protocol + session + approvals), the SDK surface the host
needs to answer "what does the file say" and "would this rule decide this call"
(`source/permissions.go`, `source/permissionrules.go`, `source/options.go`, `source/types.go`,
`source/agent.go`, `source/internal/tools/`, `source/internal/permissions/`,
`source/internal/runtime/`), `editors/vscode/src/`, `editors/vscode/media/`, its tests, and
the docs.

## Tasks

1. Protocol: a way to read and amend the effective rule set, and to carry the deciding
   rule on the approval event and on a tool call that was not prompted.
2. Extension: the three remember-options on the approval card; the "allowed by" line on a
   tool card; a rules file command with validation; a settings toggle for
   `load_permissions`.
3. Tests: protocol round trip against a stub host; the option-to-rule mapping; a rule
   written by the UI is one `permissions.Load` accepts.
4. Docs.

## Tasks as delivered

Recorded because the phase needed SDK surface the plan did not name, and because four
decisions were made while building the card.

- **The deciding rule travels on the SDK's own events, not composed by the host.** The host
  imports the public `anvil` package only (`internal/editorhost/independence_test.go`), so it
  cannot look up "which rule allowed this `tool_result`" — the rule is attached where the
  decision is made: `anvil.Event.Rule` (`source/types.go`, filled in
  `internal/runtime/loop.go`) and `PermissionRequest.Rule` (`source/options.go`, filled in
  `internal/tools/tools.go`). That is why the scope grew past `source/internal/editorhost/`:
  the alternative was a second evaluator in the host, which is how an explanation starts
  disagreeing with the decision it explains.
- **The file is read per call, not once per session.** `permissions.Source`
  (`source/internal/permissions/source.go`) re-reads `.anvil/permissions.json` and appends the
  caller's `Options.PermissionRules` after it; `Registry.SetPermissionRulesSource` is what the
  agent installs when `LoadPermissions` is on. Without it "always allow" would cover the
  *next* call and not the one the user was looking at, and a hand edit would not take effect
  until the session was reopened. The trade is a `stat` + read per tool call, and a file that
  has become unreadable now **falls back to the last set that read cleanly** rather than
  refusing every call in the session — a malformed file at *startup* stays a hard error
  (p_0.36.1's contract), because that is a policy the user asked to be governed by.
- **`permissions.add` evaluates, it does not assume.** The rule is appended, the file as it
  now stands is evaluated against the pending call, and the approval is answered only when the
  deciding effect is `allow`. A rule that loses to a `deny`, or to an `ask` earlier in the
  file, is still written — the user asked for that rule — and reported as not having settled
  the call, with `decided_by` naming what did. `TestARuleThatLosesToAnAskDoesNotSettleTheCall`.
- **Every offered option is proven against the call it is offered for.**
  `anvil.PermissionRuleOptions(tool, args)` builds the candidate shapes and keeps only those
  whose rule actually decides *this* call (evaluated through the same `decisionFor` a real
  decision uses). So a compound line — `git status && rm -rf /` — offers nothing at all, and a
  factless mutating call is not offered "allow every `shell` call": that is the all-or-nothing
  memory this rule table exists to replace. The prefix is the leading run of tokenised
  arguments before the first option, capped at three tokens, built from `shellcmd.Lex` output
  so it can only ever be a prefix the matcher recognises.
- **An empty `remember` still leaves a way forward.** The card falls back to a single
  session-scoped "always allow for this session" button — the pre-0.36 `allow_session` — and
  offers it *only* when there are no rule buttons. It does not compete with them, and the case
  where no rule can be written (a compound line; a session with `load_permissions` off) is not
  left with nothing.
- **A malformed file is a result on read and a refusal on write.** `permissions.get` returns
  the problem with its place rather than an error, because "half-edited" is one of the states
  of a file somebody is working in; `permissions.add` refuses to append to a file it cannot
  read (`CodeHostError` naming `path:line:col`) rather than replacing policy it cannot parse;
  and the extension's command opens the file, places a zero-width diagnostic at the position,
  selects it, and says `path:4:12: message` in the panel.
- **The release line moved to 0.36, in one move.** `editors/vscode/package.json` goes to
  `0.36.0` and `editorhost.Version` to `0.36.0-dev` in this phase, because it is the phase that
  changes the extension. They have to move together: `versionDrift` compares *minor* lines, so
  bumping the extension alone would make every spawn report the bundled sidecar as stale.
- **The webview never derives a label from a pattern.** The button text comes from the host's
  `kind`, and the pattern is displayed verbatim as what will land in the file. A static test
  (`test/unit/permissionKinds.test.ts`) pins the card's label table to the SDK's
  `PermissionOption*` constants, catches a renamed protocol field across the two languages, and
  catches a `kind` the host invents — both failures are silent at runtime.

## What a client implements against

- `permissions.get` → `{path, exists, rules[{index, effect, tool, pattern, reason, describe}],
  problem?}`. `path` is absolute so the file can be opened before it exists; `index` is
  one-based and is the number a denial quotes; `describe` is the SDK's own sentence for the
  rule, so a list and a denial spell it alike.
- `permissions.add` → `{rule, request_id?}`; answers `{path, index, rules, decided_by?,
  approved?}`. An empty `effect` means allow. With a `request_id` that no longer names a
  pending approval, `-32004` and **nothing is written**; for a session created with
  `load_permissions: false`, `-32600` (a rule written into a file that session does not read
  would not be in force); for a rule with no `tool`, `-32602`; for a file that will not
  compile, `-32000` naming `path:line:col`.
- `approval.request` gained `rule` (the rule that insisted on asking; absent when the mode
  gate alone is the reason) and `remember[]` (the proven "always allow" choices).
- `event` gained `rule` on a tool result: how a call that never prompted says why it did not.
  Absent means no rule decided it — which is *not* the same as "a rule allowed it".
- `session.new` / `session.resume` take `load_permissions` / `load_hooks`, defaulting to on;
  the extension exposes the former as `anvil.permissions`. Nothing else in the protocol moved,
  and `ProtocolVersion` stays **1** (every addition is a new optional field or a new method).
- `initialized`'s `capabilities[]` now includes `"permissions"`.

## Acceptance

- [x] Choosing "always allow commands starting with `git status`" writes a prefix rule that
  survives a reload and is visible in the file. (`TestAddPermissionRuleWritesARuleTheLoaderAccepts`
  parses what was written with the SDK's own loader;
  `TestPermissionRuleOptionsAreProvenAgainstTheCall` pins the prefix choice to
  `git status:*`; the integration test asserts the panel's exact `permissions.add` params.)
- [x] Choosing "always allow read-only commands" writes `readonly` and does not admit a
  mutating command. (`TestEveryOfferedOptionDecidesTheCall` evaluates each offered option
  against its call; the `readonly` rule is the analyzer's, and p_0.36.1's property test is
  what keeps it honest.)
- [x] A tool call allowed without a prompt names the rule that allowed it; a denied call shows
  the rule's `reason`. (`TestToolResultCarriesTheRuleThatAllowedIt`,
  `TestAToolResultNamesTheRuleThatAllowedIt`; the deny's text already carried the file, the
  position, the rule and the reason since p_0.36.1.)
- [x] A malformed rules file is reported where it is edited, with its path, and does not take
  the session down with a bare error. (`TestPermissionsGetReportsAMalformedFileWithoutFailing`,
  `TestPermissionsAddRefusesAMalformedFile`, `test/unit/rulesFile.test.ts` for the one-based →
  zero-based position, and the command's diagnostic in `chatPanel.ts`.)
- [x] `npm test` (171) and `go test ./...` green; `npm run smoke:vsix` green.

## Non-goals

- Editing rules from a graphical rule builder; the file is the interface, the UI only
  inserts well-formed entries.
- Sync, sharing, and per-user rules (a workspace file only).
- Any change to the decision order itself — that is `p_0.36.1`'s contract, and this phase
  consumes it.
