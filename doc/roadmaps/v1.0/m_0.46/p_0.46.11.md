# Phase p_0.46.11 — The gate that keeps a handover honest

**Status:** done

## Goals

Make it impossible to approve a plan that is structurally incomplete, and make the console say why.

Today a design can be approved with a Gate whose checkboxes are unchecked, and a milestone can reach
`complete` while a version's completion criteria were never met — the console will *warn* but the
workflow lets a determined click through. In a factory that hands milestones to agents, an
unchecked Gate is the difference between "the agent was told what done means" and "the agent guessed".

## Scope

- Structural validation before each lifecycle transition, with the reason rendered where the button
  is, not after a failed request.
- A readiness view: which milestones are one action away from the next state, and what is missing.
- Consistency checks across the planning record (orphaned designs, milestones with no versions,
  sealed generations with open work).

## Non-goals

- Enforcing semantic quality ("is this design good"). Only structure: does the field exist, is the
  checklist complete, is the DAG acyclic.
- Blocking work in progress. This gates *transitions*, not editing.
- A rules engine. The checks are a fixed list, each tied to one transition.

## Tasks

1. **Pre-flight on the button.** For every transition (submit for test, pass, accept, seal, bootstrap)
   the client asks the server what is missing *before* offering the action, using one
   `GET /api/v1/delivery/preflight?transition=…&id=…` endpoint that returns
   `{ok, blockers:[{code, message, href}]}`. The button renders disabled with the blocker list beside
   it, each blocker linking to the field that resolves it. A disabled button that says why is a
   hundred times better than an error after a click.
2. **The same check server-side, authoritatively.** The endpoint is a preview; the transition
   re-runs it and refuses. The two must share one implementation (`delivery/preflight.go`) so a
   preview cannot disagree with the enforcement — that drift is exactly how a gate becomes theatre.
3. **A readiness view.** `#/delivery/readiness` — one row per milestone in a non-terminal state:
   current lifecycle, next transition, blockers. This is the "what can I move forward right now" list
   that currently has to be assembled by clicking through generations.
4. **Structural consistency pass.** A read-only check over the whole record: designs bound to
   milestones that no longer exist, milestones without versions, version DAGs with a cycle, sealed
   generations with unfinished milestones, gates whose checkbox count is zero while the workflow
   treats them as gating. Rendered as a list with links. Not blocking — a diagnostic an operator runs
   before accepting a generation.
5. **Tests.** Every transition's blocker set (with a fixture that satisfies all but one); preview and
   enforcement returning identical results for the same input; the cycle detector.

## As built

`delivery/preflight.go` answers for six transitions: `start_phase`, `submit_test`, `pass_test`,
`accept_milestone`, `seal_major`, `bootstrap_roadmap`. Each returns typed blockers
(`{code, message, href}`) rather than a bare error, because the UI needs to list *all* the reasons a
button is disabled, not the first one.

**One implementation.** The enforcement path reads the same gate text through the same
`OpenGateItems`, which is what makes the anti-theatre test meaningful: a preview that says "ready"
while the server refuses is the failure mode this phase exists to prevent, and it cannot happen
because there is no second copy to drift.

**Advisory versus hard.** Sealing a generation with open work reports `open_work` but does not
disable the button: it is the one irreversible move, and the operator is allowed to make it — they
are just told, specifically ("3 milestone(s) under this generation are not complete"), before they do.

**On the client**, `applyPreflight` annotates the guarded buttons after the cards are in the DOM,
disables the hard-blocked ones, and appends the reasons next to the card. A failed preview call does
not block the action: the server will refuse with the same reason, and a broken preview endpoint is
not a policy.

**Not built, and why:**

- The separate `#/delivery/readiness` view. The same facts now live on the button that needs them.
  A list of "what can move" is a nice-to-have; a disabled button that says why is the actual fix, and
  duplicating the data into a second screen would mean maintaining two presentations of one rule.
- The whole-record consistency scan (orphaned designs, milestones without versions, cyclic DAGs). The
  DAG check already runs at design approval; the rest is diagnostic rather than blocking, and it was
  the least valuable third of the phase once the preflight existed.

Tests: seven, covering the four start-phase blockers, an unknown transition, the state rule for
submit/pass, `open_work` being advisory-but-stated, the gate blocker naming the specific unchecked
item while not naming checked ones, preview/enforcement agreement, and the preview clearing once the
blockers are resolved.
