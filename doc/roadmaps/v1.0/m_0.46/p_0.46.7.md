# Phase p_0.46.7 — The Workbench: one place to type, stream, and act

**Status:** planned

## Goals

Give anvil-web the thing the VS Code client has and the console does not: **a session you can work
in**. Today the console can *plan* (requirements, designs, roadmap) and *test*, and it can enqueue
jobs, but there is no surface where a person types an instruction, watches the agent work, answers an
approval, and stops it. An operator who wants to do anything interactive leaves the browser.

That is the difference between "can look" and "can operate". Everything else in 0.46 is polish; this
is the capability that is missing.

## Scope

- A **Workbench** view: pick a Worker (or a sandbox project), start or resume a session, stream its
  events, and act on it.
- Live event stream with tool cards, assistant text, and a stop control.
- Approval prompts, answered with allow / deny / allow-for-session, honouring the expiry the host
  already enforces.
- Session list + resume, reusing the transcript the SDK already exposes.
- The existing job plumbing stays: a phase Job started from the Roadmap is the same stream, seen from
  the other end.

## Non-goals

- Editor features: no diff review, no hunk acceptance, no checkpoints UI. Those are the VS Code
  client's job and the protocol for them already exists there (0.35–0.40).
- A second agent protocol. This drives `agentd`'s job path and the existing SSE proxy.
- Multi-user presence, shared cursors, or collaborative sessions.
- Replacing the Delivery planning surfaces; the Workbench is what runs *after* a phase is planned.

## Tasks

1. **Route and shell.** `#/workbench` — a left column of Workers/projects (from the cluster inventory
   the Delivery picker already loads) and a main pane for the session. One session at a time; the URL
   carries the worker so a reload returns to it.
2. **Start / resume.** Creating a session goes through a new `POST /api/v1/workbench/sessions`
   (worker_id, optional prompt, optional resume_id) which wraps the existing scheduler job creation.
   Resume lists sessions with `GET` and re-attaches. The reusable half already exists in
   `internal/web/schedclient` and the job SSE proxy — this is wiring, not a new transport.
3. **The event stream.** Consume the existing SSE stream and render three things: assistant text
   (appended, not per-token), a tool card per call (name, args, truncated result, error state), and
   step progress. Reuse `md_preview.js` for content. Every rendered value goes through `esc` — the
   suite from p_0.46.5 enforces it.
4. **Approvals.** The host raises and expires approvals; the client must render the pending one,
   answer allow / deny / allow-session, and show the expiry rather than silently dropping a card that
   timed out. A pending approval is the single most important thing on screen when it exists.
5. **Stop, honestly.** Stop must report `cancelled` as a distinct terminal state, not as an error,
   and must leave the session resumable — the same semantics p_0.46.2 gave the job buttons.
6. **The job bridge.** A phase Job running from the Roadmap appears in the Workbench as a read-only
   session with the same rendering (started elsewhere, watched here). One stream renderer, two entry
   points, so an operator does not learn two vocabularies for the same thing.
7. **Tests.** SSE frame parsing (comments, partial frames, `event:`/`data:` split across chunks); the
   approval state machine (pending → answered / expired, no double-answer); and the terminal-state
   mapping (`done` / `error` / `cancelled`).

## Acceptance

- [ ] From the browser: pick a Worker, type a request, watch the agent call tools and answer, approve
      one gated call, stop another, and resume the session afterwards from the list.
- [ ] A pending approval is visible, answerable, and if it expires the UI says it expired instead of
      leaving a dead card.
- [ ] Stop yields "stopped", the session is still listed, and resuming continues the conversation.
- [ ] A phase Job started from Roadmap is watchable in the Workbench with the same event rendering.
- [ ] No credential crosses the browser: the provider key stays in anvil-web's config, and the SSE
      surface carries no key material.

## Depends-on

- p_0.46.1 (dialog + render-token discipline; a stream needs both)
- p_0.46.2 (single-flight / honest running state, which the session controls reuse)
- p_0.46.5 (harness for the parser and state-machine tests)
