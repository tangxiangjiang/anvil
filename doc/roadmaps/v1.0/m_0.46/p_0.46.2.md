# Phase p_0.46.2 — Single-flight actions, optimistic patches, sticky job bar

**Status:** done

## Goals

Make the console feel fast and honest while work is happening: an action cannot fire twice, a
toggle does not repaint the world, and a running job is visible from wherever the operator is
scrolled to.

## Scope

- A `withAction` helper: disable, relabel, single-flight, restore, report.
- A local-patch path for the toggles that do not need a full reload.
- A sticky job status bar fed by the existing SSE stream.

## Non-goals

- Any change to the API. Every call keeps its current shape; only the client's handling changes.
- Incremental snapshot diffing / column-oriented updates. The patch path covers toggles only;
  everything else still reconciles with a full reload.
- Push-based (WebSocket) status. The existing SSE proxy is the transport.

## Tasks

1. **`withAction(btn, { label, key }, fn)`.** A shared helper that records the button's original
   label and disabled state, disables it, swaps in a running label (`Saving…`, `Starting…`), sets a
   module-level in-flight flag keyed by `key` so a second invocation with the same key returns
   immediately, awaits `fn`, routes a thrown error to `showNotice`, and always restores the button.
   Keyed rather than per-button, because several buttons can drive the same action (a milestone's
   Start in the card and in the toolbar).
2. **Apply to the job-enqueuing actions first.** Start / Pause / Stop (`bindMilestoneCardControls`),
   Run / Fix / Regress (`bindTestCardControls`, `bindTestCampaignJobStreams`) and Polish ▶
   (`openPolishModal`'s handler). These are the ones where a double-click costs a duplicate job.
   Then sweep the remaining mutating handlers.
3. **Optimistic patch.** `applyLocal(mutator)` mutates `this.data` and repaints only the owning strip
   for: design-version gate checks (`data-gate-check`), milestone acceptance checks
   (`data-accept-check`) and todo-style single-field toggles. `reload()` stays the reconciliation path
   when the server can disagree — a failed patch falls back to reload and a notice.
4. **Sticky job bar.** One row rendered under `.del-head` from the active job state that
   `watchDeliveryJobSSE` already tracks: kind (`phase` / `campaign:run` / `polish:<id>`), the
   milestone or phase it belongs to, the last event text, and a Stop control. It replaces the
   per-card snippet while a job is running and disappears when none is.
5. **Collapse the error paths.** The 52 copies of
   `try { … await this.reload(); this.render(); } catch (e) { … }` become calls into the helper, so
   the catch branch is written once and cannot drift.

## Acceptance

- [ ] Double-clicking Start on a milestone enqueues exactly one phase job (verify by job count).
- [ ] Every mutating button shows a running label and is disabled until its request settles.
- [ ] A failed action restores the button, shows a notice, and leaves the page consistent with the
      server (reload reconciliation).
- [ ] Toggling a gate checkbox repaints one strip: a `render()` call counter stays at 1 for the
      toggle (a full `render()` would increment it).
- [ ] A running job is visible in the sticky bar from any scroll position in Roadmap and Test, and
      the bar disappears when the job ends.
