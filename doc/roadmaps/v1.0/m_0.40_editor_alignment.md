# Milestone 0.40 — Editor alignment

**Status:** in_progress
**Product version:** 0.40.x

0.35–0.38 built a chat tab, a permission ladder, a mode ladder, and a session you can name and
replay. The client those chapters used as the bar does more than that, and the gap is now the
thing a user notices first: **one conversation at a time, no way to manage them, no way to accept
part of a change, and no way to go back.**

The gap is smaller than the phase count suggests, because most of the capability already exists
and is simply switched off. MCP file configuration is parsed by the SDK; web search and fetch are
implemented from 0.15 and gated by the `web` group from 0.36; the approval channel can already
carry a rewritten call. What is missing is a client that turns them on, and a panel architecture
that can hold more than one conversation.

## Goals

1. **Several conversations, side by side.** The protocol has always keyed every notification by
   `session_id`; the client holds one session and one panel. Making the panel per tab is the
   architecture every later phase stands on.
2. **A session a person can manage.** Rename it, delete it, find it. A rename is one appended
   `meta` record — the store stays append-only — and a delete removes one file.
3. **A change can be accepted in parts.** The preview already carries the whole before text and
   the whole after text, and `approval.response` can already rewrite the call. Hunk-by-hunk
   acceptance is the first use of a channel that has existed since 0.35.
4. **A way back.** A checkpoint is the workspace before a run, captured at the one seam every tool
   call passes through; restoring it puts those files back.
5. **The capabilities the SDK already has.** MCP servers from the workspace file, web search and
   fetch, live usage — switched on in the client and stated honestly where they are not.
6. **The input layer.** Escape, drag-drop, an image picker, prompt history, copy, a status bar.

Order is not arbitrary. **p_0.40.1 is the foundation**: every later phase touches a panel, and a
panel that is one-per-window cannot carry per-tab state without a rewrite. p_0.40.2–p_0.40.5 are
the session and change surfaces and are independent of each other once the tabs exist.
p_0.40.6–p_0.40.10 are additions that touch one setting, one tool, or one interaction each.

## Overall acceptance

1. Two chat tabs run at once, each with its own session, events, approvals and mode; an approval in
   one tab is never shown or answered in the other. A reload restores both tabs to the sessions
   they held.
2. A session can be renamed to a person's own words and the sidebar shows that name across
   reloads; it can be deleted after confirmation; a QuickPick finds a session by a word in its
   title or its id.
3. An `edit_file` preview with several hunks can be accepted in part, and the file on disk contains
   exactly the accepted hunks — with CRLF preserved in a CRLF file. Rejecting all of them leaves the
   file untouched and reports a refusal to the model.
4. After a run that edited files, restoring that run's checkpoint returns each file to its
   pre-run content, and deletes files the run created.
5. A session can be forked at a run boundary; the fork opens in a new tab carrying the records up
   to that point.
6. A `.cursor/mcp.json` in the workspace is honoured when enabled, and the panel lists what will
   load. Web search works with a key set through SecretStorage and is absent otherwise.
7. `go test ./...` green in `source/`; `npm test` green in `editors/vscode/`; `npm run package:vsix`
   and `npm run smoke:vsix` green.

## Non-goals

- Sub-agents or a multi-agent graph; the SDK has no such concept.
- Anthropic thinking blocks and a configurable output cap; the provider line is OpenAI-compatible.
- Checkpoints for a shell command's redirection.
- MCP OAuth, remote transports beyond the SDK's, and marketplace publishing.
- Remote / SSH / dev-container targets; cross-window session sync.
- Automatic compaction; notebook cell editing; multi-root in one panel.
