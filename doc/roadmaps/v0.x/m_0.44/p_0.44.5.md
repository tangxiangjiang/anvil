# p_0.44.5 — The extension sees the state

**Status:** done (2026-10-20)
**Milestone:** [m_0.44_mcp_management.md](../m_0.44_mcp_management.md)
**Linked design:** [44-mcp-management.md](../../../design/v0.x/44-mcp-management.md) §4, §7

## Goals

1. **The wire is typed.** New methods and the `mcp.status` notification get protocol types,
   `HostManager` calls, and a `Hub` event a panel can subscribe to.
2. **The chat card tells the truth.** It draws the state word, tool count and error; a host
   that predates `runtime` still renders the configuration-only card.
3. **The state machine is testable without a real host.** The fake host can script connecting,
   connected, failed and auth-required transitions.

## Scope

`editors/vscode/src/protocol.ts`, `hostManager.ts`, `hub.ts`, `mcp.ts`, `chatPanel.ts`,
`media/chat.js`, `media/chat.css`, and the MCP tests and fixture.

## Tasks

1. **Protocol.** Method constants, params/results for every host method from p_0.44.4,
   `McpServerInfo` fields, `McpProblem`, and `Notify.McpStatus`. Keep the old fields readable.
2. **Host manager and hub.** One method per RPC, delegating through the existing trust gate.
   `HostManager` routes `mcp.status` to a window-level listener; `Hub` exposes
   `onMcpStatus(listener)` and unsubscribes on dispose. The listing stays uncached.
3. **Pure helpers.** `src/mcp.ts` gains `stateLabel(state)`, `isActionable(server)` and
   `hasRuntime(result)`, so the card and the panel interpret states identically.
4. **Chat card.** `reportMcp` passes status fields; `showMcp` draws a dot/word, tool count and
   an error line; the card is still text-only. When `runtime` is absent, the old rendering is
   used unchanged.
5. **Fake host.** `FAKE_HOST_MCP` accepts `name:transport:state`; `FAKE_HOST_MCP_AUTH` makes a
   server start `auth_required` and flip to `connected` after `mcp.authenticate`; the handler
   emits `mcp.status`. Implement the management methods with recorded params.
6. **Tests.** Unit source assertions (old "must not mention status" test rewritten and citing
   chapter 43), integration tests pinning the exact params of each new method and the
   notification path, and the configuration-only fallback.

## Implementation notes

- **`mcp.status` is intercepted before the router.** `SessionRouter.route` drops any
  notification that names no session — that rule is what keeps one tab from seeing another's
  run — and a status names a server, not a conversation. `HostManager.route` therefore returns
  early for `Notify.McpStatus` and fans it out to a `Set` of window-level listeners;
  `onMcpStatus` hands back a `Disposable`, and a listener that throws is logged rather than
  allowed to cost the others their notification or the reader its stream.
- **A status names the source set it belongs to.** `setting_sources` is on the notification as
  well as on the listing, so a panel showing one layer set does not paint another set's server
  onto its card. `reportMcp` records the set it asked about and drops a status that names a
  different one; a status with no set at all is accepted, because a host that cannot say which
  runtime it is reporting from is more useful heard than ignored.
- **The card updates in place.** The row builder (`mcpRow`) is shared by the listing and the
  update, so the two cannot draw one server differently. `updateMcp` finds the row by
  `dataset.name`, replaces it, and moves the error line with it; a server the card has no row
  for — one the manager added in another tab — gets a row appended rather than being dropped.
  A card drawn from a legacy host has `dataset.runtime = 0` and is never touched: its rows have
  no dot and no state span by construction, so there is nothing a status could legitimately add.
- **Legacy shape stays exactly as it was.** The row is not an empty dot plus an empty word:
  those spans are simply not created, because a `gap`-spaced empty span would shift a row the
  pre-0.44 card drew. The listing from a host with no `runtime` therefore renders as the
  configuration view it always was.
- **The pre-0.44 unit assertion was rewritten, deliberately.** It required `showMcp` never to
  mention a state, which chapter 43 reverses: the host now observes one, and the card draws it.
  The test now pins the shape of the degradation instead — `msg.runtime === true`, a state only
  then, and the old fields unchanged.
- **Fixture.** `FAKE_HOST_MCP` entries take a third field, `name:transport:state`; the default
  state is `connected`, so `FAKE_HOST_MCP_AUTH` from the plan is just `docs:http:auth_required`
  and no second knob was added. A runtime host answers a malformed file with `problem` in the
  result; `FAKE_HOST_MCP_LEGACY=1` makes it a 0.40.6 host — no `runtime` flag, no state, the
  management methods `-32601`, and the malformed file an RPC error again, which is exactly the
  pair the extension has to survive. `mcp.authenticate` answers with the URL and completes in a
  timer, so the notification path is exercised the way the real host's callback goroutine is.
- **What is not covered by a test.** The `HostManager` → `Hub` → `ChatPanel` → webview path
  needs a running extension host; the fixture tests the wire and the unit tests pin the wiring
  by reading the sources, the same way every other notification in this extension is covered.
