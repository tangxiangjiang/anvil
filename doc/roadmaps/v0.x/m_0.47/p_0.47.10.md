## Goals

The first real use of the panel found the transcript tiring to read: every tool call was a
bordered box with its own widget background, a succeeded call added a green left edge to it,
and the output sat in a second tinted box inside the first. A page of work therefore read as a
wall of frames rather than as a record of what happened. This phase changes what the
transcript looks like and nothing about what it does.

1. **A tool call is a row, not a card.** One muted line — caret, name, hint, state — that
   opens onto quiet, inset output.
2. **Reasoning reads as the same kind of row.** The Thinking block uses the tool row's
   padding, caret and hover; it is no longer drawn as a different species.
3. **Prose has room to breathe.** A 1.6 line height, muted labels set in sentence case, and
   a quieter rhythm in Markdown.
4. **An edit is shown old beside new.** The `edit_file` card's short comparison becomes two
   columns with the editor's own inserted/removed line colours, falling back to one column
   when the reading column is narrow.
5. **Nothing else changes.** The protocol, the host, the anchor, the 24-row cap, focus view,
   approvals, spawn nesting and the accessibility contract stay as they are.

## Scope

`editors/vscode/media/chat.js`, `editors/vscode/media/chat.css`, a new
`editors/vscode/media/tokens.css`, the `<head>` of
`editors/vscode/src/chatPanel.ts` (one stylesheet link), and the unit tests that pin the
renderer and the stylesheet (`toolCardReview.test.ts`, `chatLayout.test.ts`,
`accessibility.test.ts`). The design chapters named above and the milestone page are updated
by this phase.

## Tasks

1. **Shared tokens.** `media/tokens.css` declares the visual grammar's constants; the chat
   stylesheet aliases its `--anvil-*` names to them.
2. **De-card the rows.** `.tool` loses its border, background and radius; `.tool > summary`
   becomes a hoverable one-line row; the pane and its sections are inset behind a hairline.
   Thinking adopts the same summary and an inset body.
3. **Calm the type.** `.msg .who` drops uppercase and letter-spacing, the bodies move to a
   1.6 line height, Markdown spacing opens up, and the composer and status line follow.
4. **Pair the diff.** `renderEditDiff` builds normalized rows with both line numbers and
   renders two cells per paired row; `pairDiffRows` is a pure function beside the diff.
5. **Narrow fallback.** `syncDiffWidth` toggles `body.diff-narrow` from one rAF-throttled
   `resize` listener, because `chat.css` may not contain an at-rule.
6. **Tests.** The pinned literals stay; new assertions cover pairing, line numbers, the grid,
   the narrow rules, the de-carded rows and the high-contrast cue.
7. **Verify.** Extension compile, lint and tests; the Go triple from Git Bash; VSIX packaging
   and the packaged smoke test.

## Decisions (before any change)

- **A row, not a card.** The border was doing no work that the summary's alignment does not
  do better: the name is the anchor, the hint is the subject, the state is the outcome. A
  hairline behind the opened output keeps the nesting legible without drawing a frame around
  every call in a long turn.
- **Done is not green.** A finished call is the normal case; colouring it made a successful
  run look like a page of notifications. Only failure and the stopped state carry colour,
  and stopped is italic grey because the transcript does not know whether that call landed.
- **Paired rows are the cap.** The 24-row limit counts what the reader sees, so a replacement
  row stays one row however many source lines it replaces. The card's height does not change
  when a change is paired.
- **The narrow fallback is a body class.** `chatLayout.test.ts` parses the stylesheet by
  splitting on `}`, so an at-rule would silently turn selectors into garbage. The markup is
  identical in both modes and CSS decides which cell is visible; no card is re-rendered when
  the tab is resized.
- **Approval previews stay unified.** They are the surface that decides what is applied, and
  a per-line pairing there would invite reading it as the diff editor it is not. Only the
  `edit_file` card's short comparison (read, not decided) is side by side.
- **The old side of a replayed anchor is approximate.** `editAnchor` locates the new text on
  disk, so the before-context on replay is inferred. This is the same approximation as
  before; the new side is now exact as well, which is the improvement.

## Implementation notes

### Tokens and the stylesheet

`media/tokens.css` declares `--ui-gap`, `--ui-gap-tight`, `--ui-radius`, `--ui-radius-sm`,
`--ui-line`, `--ui-line-tight`, `--ui-mono`, `--ui-hairline` and `--ui-muted`, and nothing
else. `chat.css` keeps its `--anvil-*` names because tests read them (`--anvil-gap` and
`--anvil-radius` alias the `--ui-*` values; `--anvil-read-width` and `--anvil-composer-h`
stay literal, the latter because a test requires a real length). The `chatPanel.ts` head
links `tokens.css` before `chat.css`.

### Rows

`.tool` is transparent and borderless. `summary` is a 3px/4px padded row with a hover
background, a caret at 0.45 opacity and baseline alignment; `.name` is mono at weight 500,
`.hint` ellipsizes, `.state` is 0.85em muted. `.pane` is inset 18px; each `.section pre`
carries a one-pixel left hairline and no background of its own. `.approval pre` keeps its old
declarations verbatim. Thinking's summary matches the tool row, and its body is the same
inset hairline in muted text.

### The diff

`renderEditDiff` normalizes every source line to
`{kind, text, sign, oldLine?, newLine?}` — anchor context first, then the LCS rows with the
two counters, then anchor context with `oldNo + i` and `newNo + i`. `pairDiffRows` slices the
raw list at each context row, collects the deletions and insertions of a change block, and
zips them by position; leftovers become one-sided rows. The renderer emits
`pre.diff.side[.numbered] > div.row.kind > span.cell.old|new(.empty) > span.ln? + span.code`.
The render loop names each side `row`, so the two pinned literals
(`el('span', 'ln', String(row.line))` and `el('span', 'code', …)`) are unchanged.

Colours come from `--vscode-diffEditor-insertedLineBackground` and
`--vscode-diffEditor-removedLineBackground`, falling back to the editor's text backgrounds and
then to a faint green/red. In high contrast the cell also gets a 2px left border, because a
tinted background is not a reliable cue there.

### The width

`syncDiffWidth` measures the transcript's content width (client width minus its inline
padding), not the window's, because the reading column is capped at 52em. Under 620px it adds
`diff-narrow` to the body. The first call is synchronous; later calls are queued through
`requestAnimationFrame` from one `resize` listener. It reads `atBottom()` before toggling and
calls `scrollIfPinned()` after, so a reader at the bottom stays there when rows stack.

### Verification

- `cd editors/vscode && npm run compile && npm run lint && npm test`: clean; **536 passing,
  0 failing** (the baseline was 530, so six tests were added: four in
  `chatLayout.test.ts` and `accessibility.test.ts`, and the pairing pair in
  `toolCardReview.test.ts`).
- `cd source && go build ./... && go vet ./... && go test -count=1 ./...` from Git Bash:
  green.
- `npm run package:vsix` → `anvil-vscode-0.47.0-win32-x64.vsix` (69 files, 10.81 MB);
  `npm run smoke:vsix` → packaged `anvil-host` answered for win32-x64, protocol 1.

### What was not walked

No real window, screen reader or theme in this environment. The 620px threshold, the look of
two independent horizontal scroll areas on long lines, the editor's actual inserted/removed
line backgrounds in light, dark, high-contrast and high-contrast-light, and the scroll
behaviour while resizing are manual checks. Replaying a long conversation through the new
renderer was exercised only as source-level tests.

## Non-goals

- Changing the protocol, the SDK, `EditAnchor`, or how a preview is computed.
- A side-by-side approval preview, partial acceptance, or a new diff editor surface.
- Per-card JavaScript layout, container queries, or a stylesheet rewrite that introduces
  at-rules.
- A version bump or any non-visual behaviour change.
