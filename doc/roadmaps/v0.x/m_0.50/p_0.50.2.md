# p_0.50.2 — Complex: three stages as a workflow

**Status:** done
**Milestone:** [m_0.50_agent_modes.md](../m_0.50_agent_modes.md)
**Linked design:** [50-agent-modes.md](../../../design/v0.x/50-agent-modes.md) §5

## Goals

Express Decision → Analyze → Worker as a workflow the SDK builds and `executeWorkflow` runs.
Three fields on a step — `role`, `effort`, `result_schema` — and two validated schemas make
Analyze's output something a Worker consumes rather than interprets; item-level `depends_on`
lets a roadmap order its own work. No new scheduler.

## Scope

`source/workflow.go` (`workflowStep.Role/Effort/ResultSchema/BriefFromItem`; schema
validation on a step's final message; item dependencies in `runFanOut`),
`source/mode_complex.go` (new: `Options.Complex` stage config, the built spec, `Send` in Complex
mode, the rendered result), `source/mode_schemas.go` (new: `decision`, `roadmap` validators),
`complex_test.go`, `schemas_test.go`, `workflow_test.go`, `source/internal/prompt/prompt.go`
(the schema text in Decision's and Analyze's L3), `source/eval` (one tier-2 Complex task).

## Tasks

1. **Step fields.** `role` → child `Options.Role`; `effort` → child `Options.Effort`;
   `result_schema` → a named validator run on the step's final message; `brief_from_item` →
   the fan-out child is created through `delegate`'s path with the item as its brief.
   Unknown values refused at validation, as every other field is.
2. **Schema failure fails the step.** A message that does not parse as JSON, or parses and
   fails the validator, fails the step with the errors in its outcome; dependants do not run.
3. **The two validators.** `decision` (§5.3: `summary`, `chosen` naming an option, ≥1
   option) and `roadmap` (1–16 items, each a valid brief minus `tools`/`effort`, unique ids,
   acyclic known `depends_on`). `roadmap` reuses `validateBrief` per item and the workflow's
   own cycle check on the items.
4. **Item dependencies.** `runFanOut` honours `depends_on` between items: an item waits for
   the ids it names, under the existing `max_parallel`. Today's fan-outs have no `depends_on`
   and run exactly as before (a test pins the order of a dependency-free fan-out).
5. **`Options.Complex`.** Per-stage `{Model, Effort, Tools, MaxSteps}` with the §5.2 defaults
   (Decision high / Analyze medium / Worker low; Decision and Analyze read-only). The
   container fills model and effort; the SDK fills nothing from any file.
6. **`Send` in Complex mode.** Builds the three-step spec, runs it through `executeWorkflow`
   in the foreground, and returns a `Run` whose stream carries the workflow's `SubagentEvent`s
   and whose final message is the rendered result (stage status, decision `summary`, one
   acceptance report per item). Refused with a clear error in plan mode.
7. **Budget.** A roadmap whose item count plus two exceeds the tree's remaining agent budget
   is refused by Analyze's validator before any Worker starts.
8. **Eval.** One tier-2 Complex task: a two-item roadmap with a dependency; gates
   `Completed`, `Agents == 4` exactly, and records `Steps`.
9. **Verify.** Go suite from Git Bash; the script.

### Gate

- 命令：`cd source && go test -count=1 ./ -run 'TestComplex|TestSchema|TestWorkflowItemDeps|TestWorkflowStepFields' && ./scripts/eval.sh`
- 通过条件：`TestSchemaDecision`/`TestSchemaRoadmap` 各含至少 6 个拒绝用例（缺必填、`chosen` 不在 options、17 个 item、重复 id、环、`files` 越界）与 2 个接受用例；`TestWorkflowSchemaFailureStopsDependants` 证明 Analyze 产物不合格时 `work` 步未运行且预算 `used == 2`；`TestWorkflowItemDeps` 证明 item B 在 item A 结束后才开始（用通道时序断言），且无 `depends_on` 的 fan-out 顺序与 0.42 一致；`TestComplexSend` 证明一次 `Send` 产生 `decide`/`analyze`/`work` 三个 `SubagentEvent` 根节点与两个 `Depth == 2` 的 Worker；`TestComplexPlanModeRefused` 返回错误且不创建 agent；`TestComplexBudget` 证明 budget 为 3 时两 item 的 roadmap 在 Analyze 校验阶段被拒；eval 新任务 `Agents == 4`。
- 失败条件：任一断言不成立；一个不合格的 Analyze 产物仍启动了 Worker；item 依赖被忽略（B 与 A 并发）；无依赖 fan-out 的顺序改变；eval 任一受控字段劣化。
- 基线条目：`baseline.json` 新增 Complex 任务（`Agents == 4`）；`invariants` 100%。

## Delivery status

Implemented: the step fields `role`, `effort`, `result_schema` and `brief_from_item` (validated
with every other field); schema validation on a step's final message, so a failing message fails
the step and its dependants are skipped; the `decision` and `roadmap` validators; item-level
dependencies in a fan-out; `Options.Complex` (per-stage model, effort, tools, steps; Decision
high, Analyze medium, Worker low; Decision and Analyze read-only); `Send` in Complex mode; plan
mode and image attachments refused before anything starts; and the Worker stage created through
`delegate`'s path (`workerOptions`), so its file allowlist and acceptance report apply.

**Deviations and decisions the design did not state.**
- **Item order is read from the items.** The design says the roadmap's `depends_on` becomes the
  fan-out's ordering but not how `for_each` learns it. A fan-out whose items are JSON objects
  with a `depends_on` list now runs them in that order; items without one take the old path
  unchanged (`TestWorkflowFanOutWithoutDepsIsUnchanged`). The scheduler checks the order it is
  handed, so a cyclic fan-out fails at once instead of waiting on itself, whatever the schema did.
- **A skipped item fails its step.** An item whose dependency did not finish is skipped, and the
  step reports failed: a step that did not do all its work did not finish.
- **The user's message is a literal prompt.** The Decision step's prompt is the user's text, and
  `{{...}}` in it must not be read as a token, so a step built by the SDK can be marked literal;
  a workflow written by a model cannot.
- **Stage children are at depth 1, not 2.** The gate says two Workers at `Depth == 2`. Every
  child of a workflow is a child of the root agent, as `run_workflow` has always created them,
  and `Complex` reuses that. `MaxDepth` still bounds nesting; the stage tree is flat.
- **The root's own events.** A Complex run's stream carries one assistant message and `done`
  (the rendered workflow), not a model loop: the stages are the children, and their events
  reach `Subagents.OnEvent`.
- **`Score.Agents` is now real.** It counts distinct child agents that emitted an event. Existing
  tasks with children moved from 0 to their child count (a baseline change in `agents` only, not
  gated); `complex_two_items` gates `agents=` at exactly 4.
- **Not done:** Complex does not yet take a `WithDirective`; it ignores it.

## Non-goals

- A reviewer stage; a re-plan loop; retrying a stage.
- Background Complex runs (the workflow's `background` is available; `Send` uses foreground).
- Host or editor rendering beyond what a workflow already gets.
