# p_0.51.1 — Protected-path policy and shell analyzer

**Status:** done

## Goals

Define an explainable protected-path policy and a deterministic analyzer that identifies shell
commands whose lexical operands may name those paths before execution.

## Scope

- Define protected path sources, normalization, precedence, and conservative ambiguity handling.
- Analyze direct file operands, redirections, chained commands, shell/interpreter wrappers,
  relative paths, quoting, and Windows/POSIX path forms.
- Return structured path candidates plus a known/indeterminate state and stable problem reason.
- Keep command analysis side-effect free and independent of approval UI.

## Tasks

- [x] Specify the protected-path matching and normalization contract.
- [x] Implement tokenization/classification with an explicit unknown result.
- [x] Build table-driven unit and fuzz/regression fixtures for supported command forms.
- [x] Document which constructs intentionally require conservative approval.

## Acceptance

- [x] Unit tests extract conservative path candidates from redirections, pipelines, command
  chains, PowerShell/cmd forms, `sh -c`-style wrappers, and quoted paths.
- [x] Tests prove `..`, absolute paths, separators, and platform case behavior reach the
  existing protection matcher without the analyzer resolving symlinks or reading the filesystem.
- [x] Unknown or malformed commands return an explicit ambiguous result, never a safe result.
- [x] Commands with no path candidates preserve ordinary permission behavior; a literal path
  candidate such as `echo .git` may conservatively require confirmation.
- [x] Run `cd source && go test ./...`.

## Non-goals

- Approval prompts or VS Code UI.
- Complete semantic interpretation of arbitrary shell programs.
- Executing a command to discover what it would modify.

## Depends-on

- Existing workspace path resolution and permission-rule primitives.
