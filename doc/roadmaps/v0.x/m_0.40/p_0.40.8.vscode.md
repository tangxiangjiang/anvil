# p_0.40.8 — Usage on the stream, and a context meter

**Status:** done (2026-10-19)
**Milestone:** [m_0.40_editor_alignment.vscode.md](../m_0.40_editor_alignment.vscode.md)
**Linked design:** [40-editor-alignment.vscode.md](../../../design/v0.x/40-editor-alignment.vscode.md), [07-streaming-and-errors.md](../../../design/v0.x/07-streaming-and-errors.md)

## Goals

1. **A client learns token usage during the run, not only after it.** The terminal event carries the
   run's `Usage`.
2. **The meter is honest.** A percentage needs a context window; nothing in the catalog defines
   one, so it comes from a setting and is absent when unset.

## Scope

`source/agent_types.go` (the event), `source/agent.go` (emission), `source/internal/runtime/loop.go`,
`source/internal/editorhost/` (projection), `editors/vscode/src/` (protocol, settings, panel),
`editors/vscode/media/` (meter), tests.

## Tasks

1. **The event.** `runtime.Event` and `anvil.Event` gain `Usage *Usage`. The loop sets it on every
   terminal emission — the `done`, the max-steps, provider and loop-stop errors, and the cancel
   path — from the accumulator of the responses that actually completed. No other event carries a
   count: a per-chunk number would be invented. `agent.go` projects it with `usageInfo`, which is
   nil in, nil out, and which now also builds `RunResult.Usage` so the two cannot disagree.
2. **The host.** `EventParams` gains `usage`, projected only when the SDK set it and omitted
   otherwise, so an old client sees the payload it always saw. The end-of-run figure remains the
   `done` notification, which already carried `RunResult.Usage`. `projectDone` shares the same
   `usageWire` projection.
3. **The setting.** `anvil.contextWindow` (number, default 0, minimum 0). `readSettings` treats a
   non-finite or non-positive value as 0 — unknown — and carries it beside the session config
   without ever sending it to the host.
4. **The client.** `media/meter.js` holds the arithmetic: it adds each finished run's usage to the
   session's input/output totals, remembers the last run, and formats one line. A run with no usage
   adds nothing, because unknown is not zero. `chat.js` draws the text, `finishRun` and `addRunEnd`
   record the terminal envelope (a live `done` or a replayed `run_end`), `clearTranscript` resets
   it, and the panel reports the window on `ready` and again when a settings change restarts the
   host. The fraction appears only when the window is positive.
5. Tests and docs.

## Acceptance

- [x] A completed run's terminal event carries non-zero usage, and the host payload includes it.
  (`TestTerminalEventCarriesUsage`, `TestLoopPutsUsageOnTheTerminalEvent`,
  `TestProjectEventCarriesUsageOnATerminalEvent`; the pre-existing
  `TestPromptStreamsEventsToDone` still pins the `done` notification's usage.)
- [x] A client that ignores the field (the existing tests) is unaffected.
  (`TestProjectEventCarriesUsageOnATerminalEvent` asserts a nil usage is omitted from the JSON; the
  whole `npm test` suite passes unchanged.)
- [x] With `contextWindow` unset the meter shows counts only; with it set the fraction is shown.
  (`test/unit/usageMeter.test.ts`: `one run shows its input and output, with no fraction unasked`,
  `a window turns the last run into a fraction of it`.)
- [x] The meter survives the session (cumulative) and resets for a new session.
  (`the session totals accumulate, and the last run stays the last`; `clearTranscript` calls
  `resetUsage`, and `finishRun`/`addRunEnd` each record exactly one terminal envelope.)
- [x] `go test ./...` green; `npm test` green (331 tests).

## Non-goals

- A per-model context-window table, or reading one from a provider response.
- A cost estimate in currency.
- Usage for a replayed transcript (the store's `run_end` usage already covers what it has).
