# p_0.40.9 — The task list

**Status:** done (2026-10-19)
**Milestone:** [m_0.40_editor_alignment.vscode.md](../m_0.40_editor_alignment.vscode.md)
**Linked design:** [40-editor-alignment.vscode.md](../../../design/v0.x/40-editor-alignment.vscode.md), [04-tools-and-sandbox.md](../../../design/v0.x/04-tools-and-sandbox.md)

## Goals

1. **The model's plan is visible.** A built-in `todo_write` tool replaces the list; the panel renders
   it below the composer.
2. **The list is part of the conversation.** The call is persisted and replayed like any other tool
   call, so a reopened session shows the list it showed live.
3. **The tool does nothing else.** No files, no shell, no network.

## Scope

`source/internal/tools/` (the tool), `source/types.go` (event and item type), `source/agent.go`
(projection), the default tool set, `source/internal/editorhost/` (projection), `editors/vscode/src/`
(protocol, replay), `editors/vscode/media/` (the block), tests and docs.

## Tasks

1. **The tool.** `todo_write` takes `{items: [{text, status}]}` with `status` one of `pending`,
   `in_progress`, `done`. It trims each text, rejects an empty text or an unknown status with the
   row index in the message, returns `N item(s)`, and stores the list on its `tools.Result`. It is
   registered in the default set and exempt from the permission gate — including when a permission
   group names it — because it touches nothing a permission protects. A workspace rule that denies
   it explicitly is still honoured.
2. **The event.** `anvil.TodoItem`, the `EventTodo` type, and `Event.Items`. The runtime emits
   `type: "todo"` after the `tool_result` of a successful `todo_write`, carrying the complete list.
   A failed call emits nothing.
3. **Persistence.** The call is an ordinary tool message. `replayOf` synthesises the same `todo`
   event from the stored arguments, applying the tool's own validation, so a refused call replays
   as a card with no list rather than as a plan that never existed.
4. **The panel.** A block below the composer, one row per item with a mark for its status; every
   `todo` event replaces the block; an empty list hides it; `clearTranscript` clears it with the
   conversation. Rows are built with `textContent`.
5. Tests and docs.

## Acceptance

- [x] `todo_write` updates the list and returns the item count; an invalid status is a tool error.
  (`TestTodoWriteStoresTheList`, `TestTodoWriteSaysOneItem`, `TestTodoWriteRejectsAnUnknownStatus`,
  `TestTodoWriteRejectsEmptyText`.)
- [x] The event carries the full list; the panel replaces its checklist on each call rather than
  appending. (`TestLoopEmitsTheTodoList`, `TestLoopDoesNotEmitTodosForAFailedCall`;
  `test/unit/todoList.test.ts` asserts `todoBlock.textContent = ''` before the rows are built and
  that `clearTranscript` calls `setTodos([])`.)
- [x] A replayed session ends with the checklist from its last `todo_write`.
  (`test/unit/transcript.test.ts`: `a stored todo_write replays as the checklist it left on
  screen`; a refused call and an empty list each have their own case.)
- [x] An empty list hides the block. (`setTodos` hides the block at zero rows; the wire test
  `TestProjectEventCarriesTodoItems` pins `[]` rather than an omitted field.)
- [x] `go test ./...` green; `npm test` green (338 tests).

## Non-goals

- A user-authored todo list, or editing items in the panel.
- Nesting, priorities, due dates, or assignment.
- Sub-agents; this is a checklist, not a delegation mechanism.
