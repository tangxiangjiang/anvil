# Milestone 0.48 — LLM calls: effort, retry, stop reasons

**Status:** done
**Product version:** 0.48.0

The request the SDK sends to a model has not changed shape since 0.43 added a cache flag. It
says nothing about how hard the model should think, gives up on the first 429, and cannot tell
an answer that finished from one the provider cut off. This milestone adds those three things
as SDK interfaces — `Options.Effort`, `Options.Retry`, `Response.StopReason` — and nothing that
decides which model gets which value: that is the container's configuration, passed in through
`Options`. The design is chapter [48](../../design/v0.x/48-llm-effort-and-retry.md).

It also resolves a test that would otherwise block the first phase:
`TestOpenAIStreamRequestCarriesNoReasoning` forbids `reasoning_effort` in the request body
because it was written to catch chain-of-thought going back upstream. Chapter 46 §2 separates
the two meanings; the test becomes two tests, one stricter than today and one new.

## Goals

1. **Effort.** `Options.Effort` in three named levels, carried on `llm.Request`, sent as
   `reasoning_effort` (OpenAI-compatible) or `thinking.budget_tokens` (Anthropic); an empty
   effort sends today's request byte for byte. A provider that rejects the field is reported
   as `request_rejected`, never silently downgraded.
2. **Retry.** `llm.WithRetry` around the completer: exponential backoff with jitter, honouring
   `Retry-After`; retried only when nothing reached the user; usage counted once; a `retry`
   event on the stream.
3. **Stop reasons.** `Response.StopReason` from both wires, a `truncated` event and
   `Result.Truncated`, `Request.MaxOutputTokens`, and `HTTPError.Kind` mapped to codes a
   container can switch on.
4. **Measured.** Every phase's gate compares against the 0.47 baseline; the eval harness
   records `Retries` from this milestone on.

The phases are independent of each other and ordered by how much a container wants each:
effort is the capability the requirement names; retry is the one that changes a default; stop
reasons are what makes a truncated answer visible, which effort `high` makes more likely.

## Overall acceptance

1. With `Effort` empty, both adapters' request bodies are byte-identical to 0.47's (golden
   files).
2. With `Effort` set, `reasoning_effort` / `thinking` appears with the configured value and no
   message in `messages[]` carries reasoning text, for a history whose assistant turns had
   reasoning streamed.
3. A 429 followed by a 200 yields one `Response`, one usage count, one `retry` event; a 400
   yields zero retries; a stream that already emitted a delta is not retried; a cancelled
   context stops at once.
4. `StopReason` is `length` for a cut answer on both wires and the run carries
   `Truncated: true`; `MaxOutputTokens` reaches both wires.
5. `./scripts/eval.sh` is not worse than the 0.47 baseline on every gated field, and the
   `invariants` suite is 100%.
6. `cd source && go build ./... && go vet ./... && go test -count=1 ./...` green (run from
   Git Bash) at the end of every phase.

## Delivered with known limits

- `Options.Effort` on Anthropic still sends only `thinking.enabled` with `budget_tokens`, which the
  documentation says Claude 4.7 and later reject (they take `thinking.adaptive` with
  `output_config.effort`). Choosing the form per model is a separate phase, not yet planned; until
  then effort is for models that accept a budget. Nothing sets effort by default.
- Chapter 48 §3.4 is settled by the provider's documentation, not by the live probe: the gateway
  the probe ran against is more lenient than Anthropic's own validation. See p_0.48.1.
- Retry is on by default (three attempts). A caller that wants today's behaviour sets
  `Options.Retry.MaxAttempts` to 1.
- A 429 that is not retried is now `provider_busy`, not `provider`.

## Non-goals

- A model table, a per-model effort default, or reading any config file. `Options` is the
  interface; the host and worker fill it.
- Host protocol fields, worker `llm` block fields, CLI flags, VS Code settings. Those are
  container phases that follow this milestone.
- Automatic continuation after `length`.
- Retrying tools, subagents or workflow steps.
