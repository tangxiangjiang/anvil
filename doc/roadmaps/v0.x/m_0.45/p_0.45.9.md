# Phase p_0.45.9 — The Workbench: one place to type, stream, and act

**Status:** done

## Goals

Give anvil-web the thing the VS Code client has and the console does not: **a session you can work
in**. Today the console can *plan* (requirements, designs, roadmap) and *test*, and it can enqueue
jobs, but there is no surface where a person types an instruction, watches the agent work, answers an
approval, and stops it. An operator who wants to do anything interactive leaves the browser.

That is the difference between "can look" and "can operate". Everything else in 0.45 is polish; this
is the capability that is missing.

## Scope

- A **Workbench** view: pick a Worker (or a sandbox project), start or resume a session, stream its
  events, and act on it.
- Live event stream with tool cards, assistant text, and a stop control.
- Approval prompts, answered with allow / deny / allow-for-session, honouring the expiry the host
  already enforces.
- Session list + resume, reusing the transcript the SDK already exposes.
- The existing job plumbing stays: a phase Job started from the Roadmap is the same stream, seen from
  the other end.

## Non-goals

- Editor features: no diff review, no hunk acceptance, no checkpoints UI. Those are the VS Code
  client's job and the protocol for them already exists there (0.35–0.40).
- A second agent protocol. This drives `agentd`'s job path and the existing SSE proxy.
- Multi-user presence, shared cursors, or collaborative sessions.
- Replacing the Delivery planning surfaces; the Workbench is what runs *after* a phase is planned.

## Tasks

1. **Route and shell.** `#/workbench` — a left column of Workers/projects (from the cluster inventory
   the Delivery picker already loads) and a main pane for the session. One session at a time; the URL
   carries the worker so a reload returns to it.
2. **Start / resume.** Creating a session goes through a new `POST /api/v1/workbench/sessions`
   (worker_id, optional prompt, optional resume_id) which wraps the existing scheduler job creation.
   Resume lists sessions with `GET` and re-attaches. The reusable half already exists in
   `internal/web/schedclient` and the job SSE proxy — this is wiring, not a new transport.
3. **The event stream.** Consume the existing SSE stream and render three things: assistant text
   (appended, not per-token), a tool card per call (name, args, truncated result, error state), and
   step progress. Reuse `md_preview.js` for content. Every rendered value goes through `esc` — the
   suite from p_0.45.7 enforces it.
4. **Approvals.** The host raises and expires approvals; the client must render the pending one,
   answer allow / deny / allow-session, and show the expiry rather than silently dropping a card that
   timed out. A pending approval is the single most important thing on screen when it exists.
5. **Stop, honestly.** Stop must report `cancelled` as a distinct terminal state, not as an error,
   and must leave the session resumable — the same semantics p_0.45.4 gave the job buttons.
6. **The job bridge.** A phase Job running from the Roadmap appears in the Workbench as a read-only
   session with the same rendering (started elsewhere, watched here). One stream renderer, two entry
   points, so an operator does not learn two vocabularies for the same thing.
7. **Tests.** SSE frame parsing (comments, partial frames, `event:`/`data:` split across chunks); the
   approval state machine (pending → answered / expired, no double-answer); and the terminal-state
   mapping (`done` / `error` / `cancelled`).

## Acceptance

- [~] From the browser: pick a Worker, type a request, watch the agent call tools and answer, stop it,
      and re-attach to it from the list. The "approve one gated call" half is not achievable on the job
      path — see *As built*.
- [x] The surface states that approvals are not delivered by this path, rather than showing a card
      that could never be answered.
- [x] Stop yields "stopped", the session is still listed, and the terminal event carries the agent id
      the next resume needs.
- [~] Deferred to p_0.45.12: the event renderer is written to be shared, but the bridge that lists a
      Non-Workbench job in this view lands with the persisted event table, which is what makes a Job
      addressable after the process that ran it is gone.
- [x] No credential crosses the browser: the provider key stays in anvil-web's config, and the SSE
      surface carries no key material.

## As built — and the one goal that had to be dropped

**Approvals are not implementable on this path, and the phase says so instead of pretending.**
Task 4 planned "approvals", and the plan assumed the job protocol carried them. Reading the code
showed it does not: `daemon.JobEventBody` has no approval event, and neither the scheduler's job API
nor `internal/worker` has a channel to answer one (grep for approval/permission in both packages
returns only plugin-policy config). A gated tool call inside a Worker job is therefore decided by the
worker's own options, not by a person in the console. An approval card here could never be delivered,
so the surface states the limit (`approval_supported:false` in the session payload) rather than
showing a dead card.

Making approvals real needs a new event kind on the job protocol plus a response channel in
`internal/worker` — an SDK/scheduler change, and out of this milestone's "no scheduler change" bound.
It is recorded here so the next milestone inherits the finding instead of re-discovering it.

Everything else in the phase is built:

- `internal/web/workbench_api.go`: `POST/GET /api/v1/workbench/sessions`,
  `GET …/{id}/events` (SSE), `POST …/{id}/cancel`. Sessions live in a hub; the durable record of a
  session is the worker's own transcript, keyed by the agent id in the terminal event.
- **Replay-then-live** streams: a client joining mid-flight receives every event so far and then
  follows, so a reload lands on the same conversation. The ring is 500 frames and a finished session
  is dropped after 30 minutes — p_0.45.12 replaces both with a persisted table.
- **One session per worker.** Two agents on one checkout damages it the way two writers damage a
  transcript; the server refuses with the id of the live session.
- `js/features/workbench.js`: worker picker from the cluster inventory Delivery already reads, a
  session list, a stream that renders assistant text (appended, not per-token), a collapsing tool
  card with args and truncated output, step progress, todo items, and a terminal banner that
  distinguishes finished / failed / stopped.
- Stop asks the scheduler first and falls back to the local cancel, and reports `cancelled` as
  "Stopped." rather than as an error.

**Tests.** Seven server-side (refusals, one-session-per-worker, replay order, cancel reaching the
scheduler, list shape, no-fleet failure, SSE frame shape) and five client-side over the frame
splitter (heartbeat comments, non-JSON payload, event-name reset, a frame split across reads).
