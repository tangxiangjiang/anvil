# Phase p_0.45.10 — Bulk and keyboard operation on the lists

**Status:** done

## Goals

Remove the "one form per item" tax. Several surfaces are only usable at a scale of handfuls, which
is the wrong shape for a planning console that inherits a real backlog.

The concrete cases, all reachable today: drafting ten test cases means ten chats; moving five
milestones means five Start clicks and five waits; reviewing a generation's gates means opening one
version at a time.

## Scope

- Multi-select on the milestone list, the test-case list and the design-version list.
- Batch actions on the selections, each of which already exists as a single-item action.
- Keyboard operation: arrow navigation within a list, Enter to open, `x` to toggle selection.
- Paste-a-list to create cases in bulk.

## Non-goals

- A spreadsheet/grid editor. The forms stay forms.
- Bulk *destructive* actions beyond what already confirms per item — a batch delete would need its own
  typed confirmation naming the count, and that is deliberately left out of this phase.
- Drag-to-reorder beyond what the version cards already do.

## Tasks

1. **Selection model, one implementation.** A shared `selection.js` with range (Shift), toggle (Ctrl /
   Cmd), select-all, and an escape-to-clear, used by all three lists. Selection survives a re-render
   by id, not by DOM position.
2. **Selection action bar.** When the selection is non-empty, a bar replaces the list header showing
   `N selected` and the applicable batch actions. This is also where a partial failure is reported:
   "3 of 5 started; 2 already running" rather than one aggregate error.
3. **Batch start / pause / stop** over selected milestones, driven through the existing single-item
   endpoints in order with per-item results. Sequential on purpose — the scheduler serialises anyway,
   and a burst of parallel patches against one milestone is how duplicate jobs happen.
4. **Batch case creation** from a pasted list: one case per line, `---` splits a multi-line body,
   editable before save. This is the non-chat path to the same result p_0.45.8's assistant proposes.
5. **Keyboard pass.** Arrow keys move a list cursor, Enter opens, Space toggles selection, Escape
   clears, `/` focuses search. Bindings are announced in the help dialog so they are discoverable.
6. **Tests.** The selection reducer (range across a filtered list, toggle after a re-render,
   select-all under a filter) — a pure function, so it goes in the p_0.45.7 harness.

## Acceptance

- [x] `runBatch` runs one request per item, sequentially, and reports each outcome: "3 succeeded,
      2 failed:" followed by the id and reason of each failure.
- [x] The reducer holds a Set of ids on the feature, not in the DOM, so a re-render keeps it. The
      succeeded ids are pruned after a batch so a second batch cannot fire at them.
- [x] "Paste cases" on the test card: one case per line, `---` for a multi-line body, live count,
      one save. `parseCasePaste` is tested over both shapes.
- [x] The roadmap milestone, test-case, and design-version lists use the same binding: arrows move,
      Space / `x` toggles, Shift+Space extends, Enter opens, Escape clears, Cmd/Ctrl-A selects the
      visible list, and `/` focuses search. The mapping is in each surface's help sheet and selection
      count/state is announced to assistive technology.
- [x] The batch actions are start / pause / stop / submit for test. None destroys.

## As built

**`js/shared/selection.js`** — one reducer for every list that supports selection. A `Set` of ids plus
an anchor, so it survives a re-render by identity. The corners are the reason it is shared and tested:
a range across a *filtered* view walks the visible order, an anchor that has been filtered out starts a
fresh selection rather than picking something arbitrary, `selectAll` respects the filter, and `prune`
drops ids whose rows no longer exist so a second batch cannot fire at a deleted item.

`decodeKey` is a pure mapping from a key event to a command, so every list answers the same keys and
the mapping is tested as data rather than by synthesising events. A bare `a` does not select all —
only Cmd/Ctrl-A does, because a bare letter fires while typing.

**Batch actions.** `runBatch` runs one request per item **sequentially**: the scheduler serialises
anyway, and a burst of parallel patches against one milestone is how duplicate jobs happen. Partial
failure is reported per item, not as one aggregate error.

**Paste-cases.** The non-chat path to the same result the assistant proposes. Writing the test for it
found a real defect: the implementation only split on `---`, while the button promised one case per
line. Both shapes are supported now, and the separator is only honoured when the text actually
contains one.

**The ratchet shrank.** Widening the "numeric expression" rule (`.length`, `.major` and similar are
numbers by construction, not debt) removed 108 baseline entries — 348 → 240. The ratchet's
"can only shrink" half is what caught that the baseline needed recording.

**Completion evidence.** Roadmap milestones, test cases, and Design Versions now share the same DOM
adapter over the reducer. Rebinding prunes ids deleted by a refresh while preserving live ids; batch
milestone actions use stable data order, one list-wide single-flight claim, per-item results, and keep
only failed ids selected. Test-case creation is bounded and transactional server-side, so an invalid
bulk request cannot leave an unreported partial insert.
