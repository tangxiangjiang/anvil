# Phase p_0.45.12 — Keep the work: history, audit and search

**Status:** done

## Goals

Make the console able to answer "what happened?" — which today it cannot, about anything.

The audit behind this phase:

- **Job events are not stored.** `jobHub.publishEvent` keeps a 200-frame in-memory ring
  (`delivery_jobs.go:71`) and the database keeps exactly one string: `job_last_event`. When a job
  finishes, its transcript is gone. The only trace of a run is its terminal status, so a failed phase
  job cannot be diagnosed from the console at all.
- **No audit trail.** Nothing records who edited a requirement, approved a design, sealed a
  generation, or deleted a milestone. `delivery_trash` keeps a deleted major but not who deleted it or
  when, and the restore path cannot say what changed in between.
- **Search is per-surface and shallow.** Projects filter by name/key (`reqs.js:394`), designs filter
  by status (`designs.js:134`), and there is no search across milestones, versions, cases, bugs, or
  the *content* of any of them.

## Scope

- A persisted event log per job, readable after the job ends.
- An append-only audit record for every mutating API call.
- One cross-surface search over the planning record.

## Non-goals

- Full-text search over Agent transcripts. That is the worker's store (`06-session-store.md`); this is
  about the planning record in anvil-web.
- Log shipping, metrics, alerting. That is an ops concern outside the console.
- Editing or deleting history. The records are append-only by design; corrections are new records.

## Tasks

1. **`delivery_job_events`.** One row per `JobEventBody` (`job_id`, `seq`, `type`, `text`, `name`,
   `args`, `content`, `is_error`, `ts`), written from `jobHub.publishEvent` alongside the in-memory
   ring rather than instead of it. Retention: a row cap per job and a job cap per workspace, pruned on
   write, because this table grows at event rate and the console must not become the reason the disk
   fills. The ring stays as the fast path for a live subscriber.
2. **A job history surface.** `#/delivery/jobs` — every job with kind, milestone/phase bind, status,
   duration, token usage, and an expandable transcript rendered with the same event renderer
   p_0.45.9 builds. This is the missing "why did it fail" view, and it is the single most likely
   thing an operator opens after a red card.
3. **`delivery_audit`.** Append-only: `actor`, `action`, `entity_kind`, `entity_id`, `summary`,
   `before`/`after` (truncated), `request_id`, `ts`. Written by one middleware over the mutating
   routes rather than by each handler, so a new endpoint cannot forget it. Rendered on the entity's
   detail page as a reverse-chronological list — "Approved by alice, 12:04" answers the question
   people actually ask about a plan.
4. **Cross-surface search.** One box in the shell header, `GET /api/v1/search?q=` returning typed
   results (requirement / milestone / version / design / case / bug) with a match excerpt, each
   linking to its surface. Matching runs over titles *and* body fields (`problem`, `goals`,
   `success`, ADR sections, case bodies) — a search that only finds titles is not a search of a
   planning document. Backed by the SQLite FTS the delivery database already sits in.
5. **Trash provenance.** Extend the trash record with who/when and the entity snapshot, so a restore
   can state what it is bringing back and what it will overwrite.
6. **Tests.** Event persistence order and the retention prune; the audit middleware writing exactly
   one row per mutating call (and none for reads); search ranking and excerpt around the match.

## As built

**Storage** (`delivery/job_events.go`, `delivery/audit.go`):

- `delivery_jobs` (header) + `delivery_job_events` (append-only transcript). Pruning happens **at the
  write**, not in a background sweep: this is the only writer, so a bound enforced here cannot drift
  from what was written. Two bounds — 2 000 events kept per job (the tail, because the failure is at
  the end) and 500 jobs per workspace.
- `delivery_audit` is append-only and written by `auditDelivery`, one middleware wrapping the whole
  `/api/v1/delivery` route group. A handler that forgets is exactly how an audit trail becomes a
  half-truth, and there are 15 mutating routes with more coming, so the middleware is the only shape
  that stays true. Entity inference from the path is deliberately shallow — `PATCH designs id=des_7`
  plus the actor plus the request body — because a deeper claim would need each handler's knowledge,
  which is what doing it centrally avoided.
- Reads are not audited. `TestAuditMiddlewareRecordsMutations` asserts a GET produces no row.
- The body is captured and **restored** before the handler runs; a middleware that consumes a body
  breaks every POST behind it.

**Surfaces:**

- `#/jobs` (`js/features/jobhistory.js`) — the history list with status/duration/event count, and an
  expandable transcript rendered with the Workbench's vocabulary so a live run and a week-old run read
  the same.
- The global search box in the sidebar (`app.js`), debounced and sequence-guarded so a slow response
  cannot overwrite a later keystroke's results. `delivery_search` is a content-bearing FTS5 table
  (`unicode61`, title-weighted BM25) populated once for existing databases and then maintained by
  source-table triggers. It indexes requirement prose, ADR/design-version sections, milestone
  acceptance/test notes, case and bug bodies, persisted job history and audit mutation bodies.
  Deletion, retention pruning and trash restore run in the same transaction as trigger maintenance.
- Search input is not passed through as FTS syntax. The server extracts at most 12 bounded Unicode
  letter/number tokens from at most 160 runes, quotes them, joins them with `AND`, binds MATCH/scope/
  limit parameters, and returns at most 50 rows. Punctuation-only input is empty; operators and
  malformed FTS syntax are literalized; overlong input is `413`. Ranking is title-first BM25 with a
  deterministic recency/kind/id tie-break. Excerpts contain escaped-safe `‹match›` markers and fall
  back to the highlighted title. There is no snapshot/substring fallback.
- Scope filtering uses the persisted workspace id, then project id, then requirement id. Search
  results do not index or return job arguments, audit actor/request ids, worker metadata or database
  scope keys.
- The Workbench now begins, appends to, and finishes a persisted job, so its sessions appear in the
  same history.

Audit lists are rendered lazily on requirement, requirement-version, milestone and design details.
Trash list rows expose the persisted `deleted_by`, `deleted_at` and summary; delete stamps provenance
from the authenticated actor before returning the response.
