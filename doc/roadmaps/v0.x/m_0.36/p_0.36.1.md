# p_0.36.1 — The rule engine and the shell analyzer (SDK, plus the loading switch)

**Status:** done  
**Milestone:** [m_0.36_tool_permissions.md](../m_0.36_tool_permissions.md)  
**Linked design:** [36-tool-permissions.md](../../../design/v1.0/36-tool-permissions.md), [08-security.md](../../../design/v1.0/08-security.md), [14-hooks-skills.md](../../../design/v1.0/14-hooks-skills.md)

## Goals

Three things, all of them in Go and all of them unit-testable without a model:

1. A **rule set** loaded from the workspace file `.anvil/permissions.json`, evaluated in
   `Registry.Execute` **before** the permission callback.
2. A **shell analyzer** that returns one of `read-only` / `not-read-only` / `cannot-prove`,
   where only `read-only` may ever be auto-allowed.
3. The **loading switch** that makes the workspace policy files real in the editor and the
   CLI — which also fixes `.anvil/hooks.json` having never been loaded by either.

No UI. No protocol revision. `editors/vscode/src/` is untouched, and the extension suite
must stay at its current 160 tests — that is part of what this phase proves.

## Tasks

1. **`internal/shellcmd`** — `Split` (quote-aware separator split), `Lex` (literal token
   split), `Analyze(command, goos) Verdict`.
2. **`internal/permissions`** — `Rule` / `Set` / `Load` / `Evaluate`, over the neutral
   `CallFacts{Tool, Command, Paths}` struct, with its own glob matcher.
3. **`Registry`** — `SetPermissionRules`, and the `Execute` insertion point
   (`deny` never asks, `allow` never asks, `ask` always asks, no callback + `ask` ⇒ deny).
4. **`Preview.Paths`** — the per-file list `apply_patch` already has in hand, instead of
   re-splitting its comma-joined `Path` in the matcher.
5. **Move the shell/write/edit file-hook denies into `SetPreExec`**, so a rule `allow`
   cannot skip them.
6. **`LocalOptions.LoadHooks` / `LoadPermissions`**, and the host + CLI defaults.
7. **`bypass` installs an always-allow callback** rather than none.
8. **Tests and docs.**

## Tasks as delivered

Recorded because six details differ from the plan above, or were not in it.

- **`Set.Rules()` was added and is how the two rule sources are composed.** The plan had the
  agent compile `options.PermissionRules` and the file separately; delivery compiles each,
  concatenates `Rules()` with the file's first, and compiles the result once more. That keeps
  one validation path and one ordering rule, at the price of one accessor.
- **Path rules exist for `write_file` / `edit_file` / `apply_patch` and nothing else.** The
  plan's pattern table said "a tool that touches files" takes a path glob; in delivery the
  facts decide, and only those three calls carry a `Paths` fact. A read — `read_file`, `grep`,
  `glob` — carries none, so a path-shaped pattern on one matches nothing and the call is
  asked about, while `{"effect":"ask","tool":"read_file"}` fires on every read. Widening this
  means widening the approval card in the same move, so it belongs to `p_0.36.2` (ch36 states
  the boundary; `TestPathRuleDoesNotMatchARead` pins it).
- **The last row of the pattern table is the tool name, not an "argument summary".** There is
  no argument summary in `CallFacts`: a call with neither a command nor paths globs its
  `pattern` against the tool name, which makes it a second spelling of the tool-name glob.
  `run_tests` and `build` therefore match by name, as the plan intended, but for the stated
  reason rather than the one first written down.
- **`Lex` allows exactly one unquoted brace, `{}`.** The plan refused every unquoted brace
  metacharacter, which made `find . -exec rm {} +` `cannot-prove`. bash expands a brace only
  when it holds a comma or a range, so the exact token `{}` is kept and `{-delete,}` is still
  refused — the latter would expand and rewrite a *later* argument, and a matcher comparing
  the line as written would then match something the shell never runs.
- **On Windows a backslash is a path separator, not an escape.** `dir C:\a` is `read-only`
  rather than `cannot-prove`; `%`, `^`, and `!` remain refused. The plan named only the last
  three.
- **`bypass` pays for a preview it discards.** An empty group set falls back to `IsMutating`,
  so a mutating call still reaches the `ask` branch, and because `bypass` now installs an
  always-allow callback rather than none, `Execute` builds the preview for it. Before this
  phase the whole block was skipped for want of a callback. Accepted: a wasted in-memory dry
  run per mutating call, in a mode that is not a default, in exchange for `deny` holding
  there. ch36 records it under the matching-facts section.

Worth recording, because a client implements against it:

- A denied call is a **tool error** whose text names the rule: `shell denied by
  .anvil/permissions.json rule 4 (deny shell "rm -rf:*"): no destructive commands`. The file
  name, the 1-based rule position, the rule as written, and its reason are all there, so a
  client can point at the line to edit without a second lookup.
- An `ask` rule with no callback denies with `<tool> denied: <the same reference> asks for
  confirmation and no approval channel is installed`.
- The file's rules are numbered and ordered as the file lists them, and a caller's own
  `PermissionRules` are appended after them — so the number in a message is the number in the
  file, and `Options.PermissionRules` cannot silently shadow a rule the user can read.

## Acceptance

- [x] A `deny` rule produces a tool error the model can react to, with no callback installed
  and no side effect on the workspace. (`TestRuleDenyHoldsWithNoCallback` — the file is
  asserted absent, not just the error.)
- [x] An `allow` rule executes with **zero** callback invocations; an `ask` rule consults the
  callback even for a tool the mode would not gate, and fails closed when there is none.
  (`TestRuleAllowRunsWithoutAsking`, `TestRuleAskForcesAPromptForAnUngatedTool`,
  `TestRuleAskWithoutACallbackDenies`.)
- [x] A prefix rule matches on token boundaries and never across a separator: `git status:*`
  matches `git status` and not `git status && rm -rf /` nor `git statusx`.
  (`TestRulePrefixDoesNotCoverACompoundCommand`, plus the matcher table.)
- [x] `readonly` never matches a command containing a redirection, a substitution, a glob the
  analyzer cannot resolve, or a command outside its allowlist. (`internal/shellcmd`, the table
  cases and the property test.)
- [x] A path rule for `apply_patch` matches only when every touched path is covered; an empty
  path list never matches. (`TestRulePathGlobMustCoverEveryPath`,
  `TestUnknownPathsNeverMatchAPathRule`.)
- [x] A rule `allow` that meets an `.anvil/hooks.json` deny is still denied.
  (`TestRuleAllowCannotUndoAHookDeny`.)
- [x] Missing `.anvil/permissions.json` changes nothing; a malformed one fails `Create`.
  (`TestNoRuleFileChangesNothing`, `TestMalformedRuleFileFailsCreate`, and at the host,
  `TestMalformedPolicyFailsTheSession`.)
- [x] `go build ./... && go vet ./... && go test -count=1 ./...` green in `source/`;
  `internal/editorhost/independence_test.go` still green; `npm test` still 160 green.

## Non-goals

- Persisting approvals, per-hunk policy, and any rule that the user cannot read in a file.
- Any `src/` change, any `ProtocolVersion` bump, any webview change.
- Windows-specific shell analysis beyond refusing to prove: `cmd /C` metacharacters
  (`%VAR%`, `^`, `!`) are `cannot-prove`.
