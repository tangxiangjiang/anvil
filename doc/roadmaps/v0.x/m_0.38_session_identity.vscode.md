# Milestone 0.38 — Session identity, and a transcript that survives a reload

**Status:** done  
**Product version:** 0.38.x

0.35 gave the editor a chat tab and an activity-bar list of past sessions. 0.36 and 0.37 gave
those sessions a policy and a mode. What none of them gave a session is **an identity a person
can recognise** — and what 0.35 explicitly declined to give it is **a transcript it can
rebuild**. Both omissions are now the thing users hit first.

All three phases are delivered — `p_0.38.1` the title, `p_0.38.2` the reviewable card, `p_0.38.3`
the reader, the replay and the re-attach. The problem statement below is the state this milestone
was planned against, kept as the record of why these are the changes being made.

One thing the milestone deliberately did **not** build, recorded so the omission stays a
decision rather than an oversight: the reader draws a conversation, and three things a live turn
has cannot be drawn from it because they were never written down — reasoning, whether a tool
call failed, and the model's own reason for a run that stopped early. Each is a fact about
`store.Record`, not a gap in the projection, and the design chapter lists them together so the
next reader does not rediscover them one at a time.

## Goals

1. **A session has a name.** The store has held every user and assistant message since 0.1 —
   `persistMessage` writes each one as it is produced — but the listing projects only `meta`
   and `run_end`, so a row is `agent-7948a2d9` and nothing else. The first user message is the
   name: it is already on disk, it needs no model call, it is deterministic and testable, and a
   machine with no API key can still list a readable session. It is the same signal every other
   agent client uses.

2. **A finished edit can be reviewed from its card.** Today only a *pending approval* carries a
   before and an after. A call that ran without a prompt — under `accept_edits`, under
   `bypass`, because a rule allowed it, or because the workspace has no permissions file at all
   — leaves a card that names the tool and prints its arguments, and no way to see what
   changed. That is exactly backwards: the edit nobody was asked about is the one worth being
   able to look at afterwards. The change a call carried is in the call's own arguments.

3. **The conversation survives a reload — and so does knowing which conversation it was.** The
   model's context already survives: `Resume` rebuilds it from the store, and a test pins that
   it does. The panel has no reader and no reattach, and after a reload it does not even know
   which agent it was talking to. Replay was a documented non-goal of 0.35 — *"the SDK exposes
   no transcript reader, so the tab marks the resume instead of printing a history it does not
   have"* — and this milestone reverses it by building the reader rather than by pretending.

The milestone is therefore not "add a few fields to a listing". It is: **a session becomes
something a person can identify, inspect and come back to.**

Order matters and is not arbitrary: **p_0.38.2 is the foundation of p_0.38.3.** A replayed tool
card is rendered by the same renderers a live one is, so the review affordance written against
live events is reused verbatim by the replay, and p_0.38.3 adds no card code at all. p_0.38.1
is independent of both and lands first because it is small, low-risk, and immediately visible
on every session already in the store.

## Overall acceptance

1. A session whose first user message was `看一下这是个什么工程` is listed under that text,
   on one line, cut at 80 runes; a session with no user message is still listed under its
   shortened agent id, and every row's tooltip still carries the full id.
2. A tool card for a call that changed a file offers a review, and the review opens VS Code's
   diff editor with the change that call carried — including for a call that never prompted.
   A replayed card from an older session offers the same review and opens the same surface.
3. After a window reload, the panel re-attaches to the session that was open, and its
   transcript comes back: the user's and the assistant's messages rendered as they were, the
   tool calls rebuilt as cards, and each run's end marked with its status and tokens.
4. Nothing replayed was ever shown that the live stream had not already shown. Reasoning is the
   one thing that does not come back, because it was never stored.
5. `go test ./...` green in `source/`; `npm test` green in `editors/vscode/`; `npm run
   package:vsix` and `npm run smoke:vsix` green.

## Non-goals

- **A model-generated title.** A classifier or a summarising call produces a better sentence
  than a truncation, and it is what the client this is modelled on does. It also costs a model
  call per new session, needs somewhere durable to put the answer, and needs a fallback for
  when it fails — all to replace a string that is already on disk. Not planned.
- **Persisting pre-images so a replayed diff is byte-exact.** It would mean a store schema
  change and would write copies of the user's files that nobody asked to keep. A replayed card
  shows the change the call carried; a live one shows it against the file.
- **A review affordance for shell writes.** A command that redirects into a file is invisible
  to the change tracker, so its card offers nothing rather than something invented.
- **Replaying reasoning.** It is emitted as a stream and never persisted; no reader can return
  it. Unchanged from 0.35, restated here because "replay" now exists and this is what it does
  not include.
- **Paginating the transcript**, editing a replayed conversation, or forking one.
- **Checkpoints / rewind.** A transcript is a record, not a cursor.
