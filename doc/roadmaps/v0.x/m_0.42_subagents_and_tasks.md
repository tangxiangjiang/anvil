# Milestone 0.42 — Subagents, background tasks, and workflows

**Status:** done (2026-10-19)
**Product version:** 0.42.x

0.40 listed "子代理（subagents）" as a non-goal because the SDK had no concept of an agent inside
an agent: one `Agent` runs one `Run`, tools are synchronous functions on that run's loop, and every
event travels on that run's channel. 0.41 finished the permission surface. The most visible
structural gap to Claude Code is now the one those two facts create: **there is no way to hand a
piece of work to a second agent, and no way for work to outlive the tool call that started it**.

This milestone closes it as an architecture extension, not a wiring change: a subagent is an
ordinary second `Agent` created by a tool; a background task is a table the parent agent owns; a
workflow is a declarative DAG over subagents. The design is chapter
[42](../../design/v0.x/42-subagents-and-tasks.md).

## Goals

1. **Agent-in-agent.** `spawn_agent` creates, briefs and waits on a child agent with a narrowed
   tool set, inherited permissions and its own store file. Depth, budget and failure are explicit.
2. **Identity everywhere.** The store, the session list, the permission request and the event
   stream can all say *which* agent is acting, so a child is accountable and replayable rather
   than an anonymous second conversation.
3. **Work that outlives a call.** `shell` can run in the background; subagents can run in the
   background; one task table lists both; `task_output`, `task_cancel` and `Agent.Tasks()` expose
   them to the model and to an embedder.
4. **A `/tasks` surface.** Host RPCs and notifications, a panel, a composer `/tasks` command, a
   status-bar item and a nested session tree — the same state, drawn where a person looks.
5. **Declarative workflows.** `run_workflow` evaluates a JSON DAG of subagents with dependency
   order, bounded fan-out and literal substitution — orchestration without a scripting sandbox.

## Overall acceptance

1. A session can spawn a child agent by name; the child runs in the same workspace with the
   inherited permission callback, and its final message is the tool result. A child that fails is
   a tool error, not a dead parent run.
2. A child appears in the store with its parent's id, the parent's run and the spawn call, and in
   `session.list` with `subagent: true`; deleting the parent deletes the child.
3. In `ask`, a child's `write_file` opens an approval card that names the child; "always allow"
   answered there covers the same tool in the parent.
4. `spawn_agent` at the depth limit does not exist in that child's tool list; the budget refuses
   the ninth spawn of one run tree with a sentence, not a crash.
5. A foreground child's `assistant`/`tool_call`/`tool_result` events reach the host tagged with
   the child's agent id and the spawn call id, and the editor draws them under the spawn card.
6. `shell` with `run_in_background` returns a task id; `task_output` reads it; `task_cancel`
   kills the process tree; `Agent.Tasks()` lists shell and agent tasks together.
7. `session.close` cancels running tasks; the Tasks panel shows them as cancelled with the reason.
8. `tasks.list`, `tasks.output`, `tasks.cancel` and the `task` notification work against a real
   host; `/tasks` opens the panel and is never sent to the model.
9. `run_workflow` refuses a cycle, a duplicate id or a missing dependency before starting an
   agent; a valid DAG runs in dependency order and fans out within its bound.
10. `cd source && go test ./...` green; `cd editors/vscode && npm test` green; packaging and the
    packaged smoke test green.

## Non-goals

See chapter [42 § Non-goals](../../design/v0.x/42-subagents-and-tasks.md#non-goals). In summary:
no workflow interpreter/sandbox, no cross-workspace or worktree children, no plugin/caller tool
inheritance, no task persistence across host restarts, no automatic retry or scheduling, no
subagent-specific permission modes.
