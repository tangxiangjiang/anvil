# p_0.46.2 — Rewind to here

**Status:** done (2026-10-20)
**Milestone:** [m_0.46_editor_polish.md](../m_0.46_editor_polish.md)
**Linked design:** [46-editor-polish.md](../../../design/v0.x/46-editor-polish.md) §4

## Goals

1. **One entry per user message.** "Rewind to here" offers fork-only, restore-only, or both,
   and says the granularity is a turn.
2. **The two undos stay separate.** A fork does not touch files; a restore does not change the
   conversation. The combined action forks first, then restores in the new session, and
   reports each result.
3. **Availability is read, not assumed.** The file action appears only when
   `checkpoint.list` has a checkpoint for that run.

## Scope

`editors/vscode/src/chatPanel.ts`, `src/commands.ts`, `media/chat.js`, `media/chat.css`,
`test/unit`, `test/integration`.

## Tasks

1. **Menu.** On each user message, a "Rewind to here" control with three actions; disable
   (with a reason) when the previous run is unknown, and hide the restore action when no
   checkpoint exists.
2. **Handler.** `rewind` message → optional `session.fork` at the previous run, optional
   `checkpoint.restore` for this run, in that order; post one result naming what happened and
   what failed.
3. **Slash.** `/rewind` opens the same control for the last user message.
4. **Copy.** "This turn" in the labels, and a one-line explanation that a checkpoint is taken
   before the turn rather than before each tool call.
5. **Tests.** Wire order (fork before restore), a run with no checkpoint, and the first
   message.

## Acceptance

- [x] Fork-only leaves the workspace untouched; restore-only leaves the conversation intact.
- [x] Both: the new conversation is forked from the previous run, and the file restore runs
      against the same root.
- [x] First message offers "new conversation" rather than a fork that cannot work.
- [x] No per-tool rewind affordance exists anywhere.
- [x] `npm test` green.

## Non-goals

- Tool-call-level checkpoints.
- An undo stack across sessions.
- Automatic replay after a rewind.

## Depends-on

- p_0.38.x (checkpoints, fork), p_0.40.x (restore in the client).

## Implementation notes

- **The combined restore is not asked of the fork.** Chapter 44's table said "restore in the
  new session", which the code cannot do: a fork copies stored records, while checkpoints
  live under the agent id (`<cwd>/.anvil/checkpoints/<agent>/<run>`). The handler therefore
  forks first, then restores through the conversation that owns the checkpoint. Both open on
  the same workspace root, so the files land where they were; the design chapter was corrected
  rather than the code made to fit the sentence.
- **Availability is pushed, not guessed.** The extension sends `rewindState` for every run it
  replays and every run it watches end, with an empty list when the run captured nothing.
  The menu keeps three states apart: "not answered yet" (checking), "answered with nothing"
  (says the turn changed no files), and "answered with paths" (offers restore and both). A
  host without `checkpoint.list` answers `-32601`, which lands in the empty case rather than
  a failed replay.
- **The first message clears in place.** There is no stored empty conversation to open, so a
  branch before the first turn is `/clear`'s behaviour. The outcome is reported as a banner,
  because the reset has taken away the message the menu belonged to.
- **One confirmation, both halves.** The modal covers the whole action and comes before
  either host call; a fork alone does not ask, because it writes no file.
- **What was not walked.** No VS Code window was driven by hand. The webview wiring is pinned
  from source (control on the message, the three labels, the three availability states), the
  order and the two wire calls over a real child process, and the first-message plan as pure
  data. A manual pass is still worth doing for the menu's focus behaviour in a real window.
