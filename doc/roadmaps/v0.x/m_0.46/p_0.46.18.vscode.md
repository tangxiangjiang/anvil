# p_0.46.18 — A reply has a beginning, and it folds

**Status:** done (2026-10-20)
**Milestone:** [m_0.46_editor_polish.vscode.md](../m_0.46_editor_polish.vscode.md)
**Linked design:** [46-editor-polish.vscode.md](../../../design/v0.x/46-editor-polish.vscode.md) §21,
[35-vscode-extension.vscode.md](../../../design/v0.x/35-vscode-extension.vscode.md) (the chat view)

## Goals

A reply now ends with an end dot and a `Summary`. It has no visible beginning: the first
thing a reader sees is a stack of rounds, each repeating the speaker's name, and every turn
of a saved conversation is open — a long session opens as a wall of history.

1. **A reply begins with a marker.** A hollow dot in the ending's colour, the speaker's name,
   and a chevron form a header at the start of every turn. The rail begins under the dot, so
   the reply is bookended: hollow at the start, filled at the end.
2. **A reply folds.** The whole turn — its rounds, Thinking, tool rows, output captions,
   approvals and result notes — is one `<details>` under that header. Folding is native:
   the chevron, the keyboard and the screen reader all come with the element.
3. **The newest reply is open, the history is closed.** A new turn closes the one before it,
   unless the reader opened that one by hand. A replay of a stored conversation therefore
   leaves only its last turn open, and every earlier turn folded.
4. **The folded face says what the turn concluded.** The header carries the answer's first
   line — the same line the end Summary uses as its title — so a column of folded replies
   reads as a list of conclusions instead of a column of identical names.
5. **The speaker is said once.** A round inside a reply no longer repeats `anvil` above its
   prose; the header names the speaker for the whole turn, and the end dot names its ending.

## Scope

`editors/vscode/media/chat.js` (reply construction, routing, folding) and `media/chat.css`
(the header, the body rhythm, the hidden repeated label); `test/unit/chatLayout.test.ts` and a
new `test/unit/replies.test.ts`. The milestone page and the design chapter record the change.
No protocol field, no host change, no setting, no new message type.

## Tasks

1. **Wrap a turn.** `ensureReply()` builds `<details class="reply" open>` with a
   `<summary class="reply-head">` holding the start dot, `anvil`, the hint and the chevron,
   and a `.reply-body` that repeats the transcript's 12px column.
2. **Route the turn's blocks.** `append` sends a block into the open reply; with no reply
   open, the blocks that begin a turn — an assistant round, a tool row, an approval, a result
   note — create one, and the rest of the conversation's furniture stays in the transcript.
   A user message closes the reply first and is appended after it.
3. **Fold on the turn boundary.** `addUser` closes the current reply unless the reader
   pinned it (`data-pinned` set by a click on the header). A reply created open therefore
   stays open only until the next turn; a replay leaves its last turn open.
4. **Mark the start.** An 8px hollow ring in the end colour at the rail's 9px, with a
   generated line from the dot to the body; the chevron turns when the reply opens.
5. **Name the folded reply.** `markSummary` writes its title into the header's hint, and the
   stylesheet hides the hint while the reply is open.
6. **Drop the repeated label.** Inside a reply body, an assistant round's `.who` is hidden;
   the summary's own header is the exception and keeps its display.
7. **Keep spawns flat.** A child's conversation inside a spawn card is a transcript already
   behind a fold; it is not wrapped a second time.
8. **Tests.** Source assertions for the wrapper, the routing, the pin and the hint; layout
   assertions for the header, the dot, the body rhythm and the hidden label.
9. **Verify.** Compile, lint and tests; the Go triple from Git Bash; VSIX packaging and the
   packaged smoke test.

## Decisions (before any change)

- **The wrapper is the phase.** p_0.46.16 listed "a wrapper element per reply" as a
  non-goal, because the rail needed no wrapper and a flat body was simpler. Folding needs the
  wrapper: `display: none` of arbitrary siblings cannot be done from CSS, and a script that
  hides each block would be a second, weaker `<details>`. The element is the browser's, so
  the keyboard, the focus ring and the accessibility tree are correct by construction.
- **Only the main transcript folds.** A spawn card's pane already holds a child conversation
  behind its own fold; wrapping it again would nest two disclosure controls around one
  transcript, and the child's rounds would lose the name that tells them apart.
- **The route is a turn, not a block type.** Once a reply is open, everything the agent adds
  goes inside it until a user message closes it — including the cards the host sends after a
  run ends. Routing by block type alone would put a checkpoint card after the `<details>`
  while its turn's next block went inside, and the transcript would read out of order.
- **A click pins a reply.** The next turn collapses the previous one, which is right for
  history and wrong for a reader who just opened a turn to read it. A click on the header
  marks the reply as the reader's; the automatic fold leaves it alone from then on. The same
  pattern as Thinking's `thinkPinned`, for the same reason.
- **The folded face is the conclusion.** A folded reply with only a name would make a saved
  session a list of identical rows. The header carries the answer's own first line — the line
  the end Summary already chose — and no new summary is generated for a turn without one.
- **The start dot is hollow.** The end dot is filled in the ending colour; the start dot is
  its ring in the same colour. The pair reads as brackets around the turn without a second
  colour entering the grammar, and the hollow form is already what an open tool row means.

## Implementation notes

### The wrapper and the route

`ensureReply()` builds `<details class="reply" open>` — a `<summary class="reply-head">` with a
`.start-dot`, the name `anvil`, a `.reply-hint` and the generated chevron, then a
`.reply-body`. The body is `display: flex; flex-direction: column; gap: var(--anvil-gap)`, so a
turn keeps the transcript's 12px rhythm; `.reply-body > *` joins the transcript's `flex: 0 0
auto` rule so no block inside a fold can be compressed.

`append` asks `targetFor(node)`. Off the main transcript a block still goes to
`active.container`, so a spawn card's child conversation is untouched. On the main transcript:
an open reply takes everything, and with no reply open only `inReply(node)` — a tool card, an
approval, an assistant round or a result note — creates one. Everything else (notices, notes,
compaction lines, command cards, session lines) stays in the transcript, because those are the
conversation's furniture rather than a turn of the agent.

Routing while open by "is a reply open" rather than by block type is what keeps the DOM in
order: the host sends the checkpoint, changes and fork cards *after* the run ends, and each
one belongs under the turn that caused it.

### The fold

`addUser` calls `closeReply()` before appending the message, so a user's message always sits
outside the turn it ends. `closeReply` leaves a reply with `data-pinned` open: the header's
click listener sets it on any click, so a turn the reader opened (or closed) by hand is not
folded by the next turn's arrival. A reply created by `ensureReply` is open, which gives the
rest of the behaviour for free — a replay closes each turn as its next user event arrives, and
the last turn is the only one left open.

`clearTranscript` resets `reply` to null along with the maps; the nodes go with the transcript.

An approval card does not go through `append` (it is appended to the transcript directly), so
that one route was taught the same target rule.

### The start marker and the folded face

The header is a flex row with 4px 6px padding, a 0.85em semibold line and a pointer cursor; the
start dot is an 8px ring (2px border in `--vscode-charts-purple`, the ending's colour) with
`margin: -1px`, so its centre is the rail's 9px and it covers the line the way the tool dot
does. Open, a generated 1px segment runs from just under the dot to the body, so the rail
begins at the marker rather than below it. The chevron is the Thinking row's `›`, rotated 90°
when open.

`markSummary` writes its title into the reply's `.reply-hint`. The stylesheet hides the hint
while the reply is open, where the end Summary says the same line in full. A turn whose run
did not end normally keeps an empty hint: nothing is generated for it.

A round's `.who` inside a reply body is hidden (`.reply-body > .msg.assistant:not(.summary) >
.who`), because the header already names the speaker for the turn; the summary's `.who` is
the end marker and keeps its flex rule.

## What was not walked

No real window here. The fold was not seen: the header's weight beside a tool row, a folded
column of titles in a saved session, and the scroll behaviour when a turn collapses above a
reader who is at the bottom are reasoned from the declarations. `display: none` on a closed
`<details>` is browser behaviour rather than a declaration, so find-in-page in a folded turn
is unchecked — and is a deliberate cost of folding, not an accident. The header's behaviour
under the focus view (which hides tool rows inside an open turn) and in high contrast (where
the hairline connector gets the rail's 60% foreground) were not looked at either.

## Non-goals

- A setting for the fold, a fold-all control, or per-round folding.
- Folding the spawn panes, the user's messages, or the command cards.
- A generated summary for a turn whose run did not conclude normally.
- A protocol change, a host change, a version bump, a branch, or a push.
