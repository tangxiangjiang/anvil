# p_0.46.3 — Plan review

**Status:** done (2026-10-20)
**Milestone:** [m_0.46_editor_polish.md](../m_0.46_editor_polish.md)
**Linked design:** [46-editor-polish.md](../../../design/v0.x/46-editor-polish.md) §5

## Goals

1. **The plan is a document.** A plan-mode answer opens in a read-only virtual document
   (`anvil-plan:`), separate from the scrolling transcript.
2. **Approval is explicit.** Approve switches back to the mode the session had before plan
   mode and sends one fixed instruction; reject stays in plan mode.
3. **Read-only means read-only.** Nothing in the document can execute, write, or post a
   message.

## Scope

New `editors/vscode/src/planDocument.ts`; `src/chatPanel.ts`, `src/extension.ts`,
`src/protocol.ts` (types only), `media/chat.js`, `media/chat.css`; tests; README.

## Tasks

1. **Provider.** `TextDocumentContentProvider` for `anvil-plan:`, registered on activate and
   disposed with the extension; content is the last assistant text of a plan-mode turn.
2. **Event.** `chatPanel` posts `plan` with the text and the run id when a plan-mode turn
   ends; the card offers "Open plan", "Approve and run", "Keep planning".
3. **Approve.** Remember the pre-plan mode, `applyOptions({permission_mode})`, then `prompt`
   a fixed sentence. Reject returns focus to the composer without sending anything.
4. **Commands.** `anvil.openPlan`, `anvil.approvePlan`, `anvil.rejectPlan` contributed and
   registered.
5. **Safety.** The document scheme is read-only (`FileSystemProvider` not registered; the
   document is content-only), rendering is `textContent`, and no command is reachable from
   the document text.
6. **Tests.** plan mode still withholds write tools; approve happens before any write; the
   provider is disposed with the panel; wire params pinned.

## Implementation notes

- **The plan is accumulated, not quoted.** A plan-mode turn can speak, call a read-only tool,
  and speak again, and the host has no "plan" object to read. The panel keeps the turn's own
  `assistant` events (a child's steps carry a `parent_tool_call_id` and are not the plan),
  splits them into paragraphs at each tool call, and joins them with blank lines. The result
  is sent as `plan` only when the turn ends, so the card never shows half a plan.
- **A plan belongs to a conversation.** The text is stored with the agent id that produced it.
  A tab can move to another agent, and approval into a conversation the plan did not come from
  would carry out a decision about somewhere else; such an approval is refused, and `/clear`
  drops the stored plans along with the conversation. The palette command reads the front
  document's `anvil-plan:` query when the plan is the active editor, and otherwise the front
  tab's newest plan for its current agent.
- **Approval is one sentence, exported once.** `PLAN_APPROVED_PROMPT` lives in `src/plan.ts`
  so the unit test and the integration test pin the same literal; the panel does not embed a
  second copy. The mode is applied before the sentence is sent, which is what the integration
  test checks over a real child (`session.resume` under the earlier mode, then `prompt`).
- **The document is content-only.** There is no `FileSystemProvider` for `anvil-plan:`, so the
  document is drawn by VS Code from text the extension holds; nothing in it can be edited,
  saved, or made to run. The provider is registered once in `activate` and disposed with the
  extension, and its map is bounded (16 documents), so an old plan renders empty rather than
  wrong.
- **What was not walked.** A reloaded webview does not redraw the plan card: the panel keeps
  the text, so *Open plan* and the palette commands still work and the plan is still in the
  transcript, but the three buttons have to be reached from the palette until the turn is
  replayed. A manual pass in a real window is still worth doing for that reload case.
