# p_0.46.27 — A dot that stays under the composer

**Status:** done (2026-10-21)
**Milestone:** [m_0.46_editor_polish.vscode.md](../m_0.46_editor_polish.vscode.md)
**Linked design:** [46-editor-polish.vscode.md](../../../design/v0.x/46-editor-polish.vscode.md) §30

## Goals

One defect, reported from a screenshot: a transcript row scrolled under the composer showed
its green state dot floating on the composer card, above the input.

Every dot in the transcript — a tool row's state dot, a reply's start dot, a summary's end
dot — is a positioned element with `z-index: 1`. That value is what makes the dot cover the
rail its own block draws, rather than being painted under it. But the block around the dot is
positioned with no stacking context of its own, so `z-index: 1` belongs to the root stacking
context — and the dock, which is positioned with `z-index: auto`, is painted below it. The
dot has always floated over the composer; scrolling a row under the dock is what makes it
visible.

## Scope

`editors/vscode/media/chat.css` (the dock's stacking order) and
`test/unit/chatLayout.test.ts`. No script, no protocol, no host, no setting.

## Tasks

1. **Give the dock a stacking order of its own.** `z-index: 2`, so the whole card — not just
   its opaque background — paints above every transcript dot.
2. **Keep the dots' own `z-index: 1`.** It is still what puts a dot over its block's rail;
   the fix belongs to the surface that floats above the transcript, not to the dots.
3. **Test the relationship, not the number.** The dock's `z-index` must be greater than the
   `z-index` of the three dot rules, so a future edit cannot reintroduce the order.
4. **Verify.** Compile, lint, the unit suite, the Go suite from Git Bash, packaging and the
   packaged smoke test.

## Decisions

- **The dock, not the dots.** Removing `z-index: 1` from the dots would put them under their
  own rail, which is the reason it is there. The card is the surface that is supposed to be
  on top; it should say so.
- **A small positive value, not a large one.** Nothing else in the document is above 1, so
  the dock only has to outrank the dots; a number like `1000` would suggest an ordering war
  that does not exist.
- **The test reads both numbers.** Pinning `.dock { z-index: 2 }` alone would pass a later
  change that raises a dot to 5; comparing the dock against each dot rule is what keeps the
  invariant true.

## Implementation notes

### The stylesheet

`.dock` gains `z-index: 2`, with the reason beside it. The three dot rules keep
`z-index: 1`: `.tool > summary::before` (the state dot), `.reply > .reply-head .start-dot`
and `.msg.assistant.summary > .who .end-dot`. Nothing else in the document declares a
stacking order, so the dock's only job is to outrank the dots; it is not the start of an
ordering scheme.

## What was not walked

No real window here. The report is a screenshot of a green tool dot over the composer; the
same mechanism applies to the reply's start dot and the summary's end dot, which were not
separately photographed. The fix is a stacking order, so its verification is the suite and a
reasoned reading of the CSS; the window is what confirms the card is fully opaque over a
scrolled row.

## Non-goals

- Changing the dots' size, colour or `z-index`, or the rail's drawing.
- Making the transcript's padding prevent rows from ever passing under the dock: the
  composer floats, and content scrolling beneath it is the design.
- A protocol change, a host change, a version bump, a branch, or a push.
