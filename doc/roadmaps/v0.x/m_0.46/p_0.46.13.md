# p_0.46.13 — A rail, coloured operations, and a name a reader knows

**Linked design:** [46-editor-polish.md](../../../design/v0.x/46-editor-polish.md) §16,

## Goals

p_0.46.10–p_0.46.12 made the transcript quiet enough to read. Run against a real
conversation, the reader named what was still wrong, and all four answers point at the same
place: a run of work is a sequence, and the row did not say what the sequence was.

1. **The steps are connected.** A call and a Thinking block are steps in one turn, but each
   dot floated on its own. A run of steps now carries a thin vertical line through its dots,
   as Claude's editor does. The line starts at the first dot, ends at the last, and ends at
   a paragraph: prose between two calls is not a step and the rail does not run through it.
2. **An operation has a colour.** The dot used to fade to muted when a call finished, which
   made the normal case the quietest thing on screen. A tool dot is green before, during and
   after the call; red when it failed; a green ring while its row is open. Only Thinking
   stays grey, because reasoning is not an operation.
3. **The operation is named, and named loudly.** The row showed the SDK's identifier —
   `read_file`, `edit_file`, `shell` — which is not a verb a reader knows. Every known tool
   gets a title (`Read`, `Edit`, `Bash`), an unknown one is de-slugged rather than shown raw,
   and the title is the body's full size, weight 600, in the foreground colour.
4. **The argument is part of the sentence.** `Read` alone does not say what was read. The row
   reads `Read   editors/vscode/README.md (lines 113–130)`: the path in the link colour, the
   line range muted beside it, and the path opens the file at that line. `Edit` carries its
   path, `Bash` its command, `Grep` its pattern. An edit's row keeps its comparison, and the
   `+n −m` that lived inside the diff becomes the line Claude's own transcript shows above
   it: `Added 1 line`.

## Tasks

1. **Titles.** Add the display-name map and `toolTitle(name)` in `chat.js`; use it in the
   tool row and in the approval card's heading and announcement.
2. **The detail.** Add `toolDetail(name, args)` returning the file, the line range, or the
   command/pattern as parts the summary can draw. `read_file` derives its range from the
   `offset`/`limit` the host actually accepts.
3. **The file link.** Draw a path as a `role="link"` span with its own click and keyboard
   handler, posting `openPath`; the handler stops the summary toggling. The extension opens
   the file at the line, and only when the path resolves inside the window's root.
4. **The rail.** Give a step row a `rail-up` / `rail-down` class from a `syncRail(container)`
   pass over the container's direct children; a `.tool::after` and a `.msg .think::after`

5. **The colours and the type.** The tool dot reads the editor's green in every state except
   failure and the open ring; the title is 1em/600/foreground; the path reads
   `--vscode-textLink-foreground` and the range is muted.
6. **The edit note.** Replace the diff's internal path line with `Added n line(s)` /
   `removed m line(s)` above the comparison, from the rows the diff already built.
7. **Tests.** Pin the title map, the detail shapes, the link's two sides, the rail's class
   pass and the edit note in source; keep the existing layout tests green.
8. **Verify.** Compile, lint and tests; the Go triple from Git Bash; VSIX packaging and the
   packaged smoke test.

## Decisions (before any change)

- **The rail belongs to a run, not to the transcript.** A line down the whole transcript
  would cross user messages and assistant prose, which are not steps. A wrapper around each
  run would have to be learned by the replay, the spawn scopes and the focus view; two
  classes per row, recomputed after an append, buy the same line with no new container.
- **Green says "operation", not "success".** The old green was a success colour and vanished
  when the call finished, which is backwards: the call is the event. Failure keeps red, the
  ring still says "open" or "result unknown", and only the colour of a working tool changed.
- **A display name is the webview's business.** The host and the SDK keep their names; the
  session, the rules and the tool definitions are not renamed for a screenshot. The map lives
  beside the row that draws it, and an unknown name degrades to words rather than to a crash.
- **The path is a link only where the row knows it is one.** Only a `path` argument becomes a
  link; a command, a pattern and a URL remain text. The webview refuses anything else, and
  the extension resolves again: relative paths under the chosen root, absolute paths only
  when they are inside it. A webview that posts a path it did not draw opens nothing.
- **The line range follows the host's own reading.** `offset` is 1-based and `limit` counts
  lines, so the row computes `offset … offset + limit − 1` rather than guessing a different
  convention. No range means no parentheses, not a made-up one.
- **The edit note moves out of the diff, not away.** The path is now in the row, where a
  reader looks first; the counts stay, one line above the comparison, because "how much"
  is the question the comparison does not answer at a glance.

## Implementation notes

### The title and the detail

`TOOL_TITLES` and `toolTitle(name)` sit next to `callHint`. A known name returns its title;
an unknown one replaces `_` with a space and capitalises the first letter, so `some_tool`
reads `Some tool` instead of disappearing. `toolDetail(name, args)` returns an array of
`{ kind, text }` parts — `file`, `meta`, `text` — which the summary appends as spans. A file
part is drawn by `fileLink`, which owns the `role`, the tab stop and both event handlers; the
rendered strings are still `textContent` through `el`.

### The rail

`syncRail(container)` walks the container's direct children. A `.tool` is a step; a `.msg`
contributes its direct `.think` children. Anything else flushes the current run. A `.msg`
whose body already has text flushes after its thinking, so prose ends the run. Each step in a
run of two or more gets `rail-up` and/or `rail-down`; a single step gets neither and draws
nothing. `append` calls it for the container it appended to; `addAssistantChunk` calls it when
the body first gains text, because that is the moment a Thinking-only message stops being a
step and becomes an answer. Spawn bodies are ordinary containers: a child's tools form their
own run inside the card.

The stylesheet draws `::after` at `left: 9px` — the summary's 6px padding plus half the 6px
dot. A step with only `rail-down` starts at 9px from its top (the dot's centre); only
`rail-up` ends 9px from its bottom; both span the row. The segment extends 10px past the row
on a side where the run continues; 10px on each side meets exactly across the 20px between a
transcript gap and a message's margin, and overlaps harmlessly across a 12px gap.

### The colours

The tool dot's `--dot` is `--vscode-testing-iconPassed`, falling back to
`--vscode-charts-green`, then `#3fb950`. `done` keeps the same green at a slightly lower
opacity rather than switching to muted; `failed` keeps the error colour; `stopped` and
`[open]` keep the inset ring, now drawn in green. High contrast still raises every dot to
opacity 1.

### The link

`fileLink(path, line)` posts `openPath` with the line only when one is known. The summary's
click is stopped and its default prevented, so following the path does not also open the row.
`chatPanel.openPath` accepts an absolute path or a root-relative one, normalises backslashes,
and then requires `path.relative(root.fsPath, uri.fsPath)` to stay inside the root. It opens
with `preview: true` and a selection at the call's first line; a missing file or a refused
path is silent, because the row only posts what it drew.

### The edit note

`renderEditDiff` still builds the rows and the cap; the old `.path` head is gone. The counts
it already computed become a `.note` above the comparison — `Added 1 line`, `Removed 2 lines`,
or both — and the path reaches the summary through `toolDetail`. The diff's two columns, its
line numbers, its backgrounds and the narrow fallback are unchanged.

## What was not walked

No real window here. The rail's meeting points in the gaps, the green against light, dark and
high-contrast themes, the link colour on a path that is also selected, and the line range's
fit at a narrow width should be looked at in a running panel. The link's open path is pinned
at the source level only; the file-open and the outside-root refusal are checked by reading
the resolver, not by clicking.

## Non-goals

- Renaming the SDK's tools, the rules they are written against, or the events on the wire.
- A per-tool colour palette; every operation is green and only the state changes the colour.
- Opening a path from anything other than an argument the row drew as a file.
- Changing the diff algorithm, the pairing, the cap or the narrow fallback.
- A version bump, a branch, or a push.
