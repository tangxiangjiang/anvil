# p_0.46.14 — One rail for a reply, a folded thought, output in a tab

**Status:** done (2026-10-20)
**Milestone:** [m_0.46_editor_polish.md](../m_0.46_editor_polish.md)
**Linked design:** [46-editor-polish.md](../../../design/v0.x/46-editor-polish.md) §17,
[35-vscode-extension.md](../../../design/v0.x/35-vscode-extension.md) (the chat view)

## Goals

p_0.46.13 joined adjacent steps, but the reader looked at the result and named three things
still missing. All three are about the same unit: what belongs to one answer.

1. **The rail is the reply's spine.** The line stopped at a paragraph, so a reply was several
   disconnected runs: two calls, an answer, six more calls. The rail now belongs to the whole
   assistant turn — from its first block to its last, across prose and Thinking alike, and
   ends only where the conversation changes hands (a user message, a notice, an approval).
   It is the first-level grouping of the reply; the steps are what hangs from it. Prose moves
   right of the line, so the line marks the answer without crossing it.
2. **A thought is folded.** Thinking is a summary row — grey dot, the word, and a chevron that
   turns when the row opens — with the reasoning underneath. It is collapsed by default and
   opens on click, as it already was, but the chevron says so before the reader tries. The
   body loses its own hairline: the rail is the one vertical line, and a second bar between
   the line and the text was noise.
3. **An operation's output is a tab.** Under a finished tool row, small grey text says how
   much came back — `3 lines of output` — and clicking it opens the full result in a read-only
   editor tab beside the conversation, titled `Grep output (z83pum)`. The tab is a virtual
   document supplied by the extension: nothing is written to disk, the text is never
   interpreted, and opening the same call again reveals the same tab rather than making a
   second. The row's own OUT pane is unchanged; the tab is for the output that does not fit
   in a card, and it carries what the host sent rather than the pane's display cap.

## Tasks

1. **The run is the reply.** Rewrite `syncRail`: a run is consecutive `.tool` and
   `.msg.assistant` children; `.msg.user`, a notice, an approval or anything else ends it.
   Prose no longer ends the run. Every block in a run gets `rail`, and `rail-up` /
   `rail-down` only where another block is on that side.
2. **Draw it once.** Move the segment to `.tool::after` and `.msg.assistant::after`; drop the
   `::after` on `.think`; the message's segment spans its whole height. Extend 10px from a
   tool row and 14px from a message, which meets across the 20px between a message and a row
   and the 28px between two messages.
3. **Make room.** Indent a railed message's `.who` and direct `.body` by 22px — the summary's
   padding, dot and gap — so prose begins where a row's name does. Thinking's summary keeps
   its own position, so its dot stays on the line.
4. **Fold the thought.** Add the chevron to the Thinking summary (CSS pseudo-element, no new
   markup), keep the dot grey, and remove the body's `border-left`.
5. **Count the output.** A `lineCount(text)` helper; `addToolResult` inserts a small grey
   `button.output-link` under the summary when the result has text, labelled
   `N line(s) of output`.
6. **Open the output.** The button posts `openOutput` with the call's display name, its tool
   call id and the full content. A new `ToolOutputDocuments` provider registers the
   `anvil-tool-output:` scheme, titles the document `<Tool> output (<suffix>)`, and reveals
   an existing tab for the same call. `ChatPanel` gains the message and the method; `Hub` and
   `extension.ts` carry the provider.
7. **Tests.** Rewrite the rail test for the reply-wide run; assert the folded Thought's
   chevron and grey dot; add output-note and provider tests, including that the URI is stable
   per call and that the title is safe as a path.
8. **Verify.** Compile, lint and tests; the Go triple from Git Bash; VSIX packaging and the
   packaged smoke test.

## Decisions (before any change)

- **The rail is the reply, not the step.** A line that breaks at prose answers "which calls
  ran together"; the reader asked which work belongs to one answer. The first question is
  already answered by the dot and the row; only the container can answer the second. So the
  unit is the assistant turn, and it includes the prose that used to break it.
- **The markup stays flat.** One wrapper per reply would be the obvious container, but the
  replay, the spawn scopes and the focus view each build transcript children independently;
  a wrapper would have to be taught to all three. Three classes per block and one pass after
  each append buy the same line.
- **The line draws on the block, not in the gap.** Each railed block owns its full-height
  segment and reaches into the gap only where the run continues. The extension differs by
  block kind (10px for a row, 14px for a message) because the gaps differ; both are larger
  than half the gap they must cross.
- **A one-block reply still has a rail.** The line is the reply's edge, not only a connector
  between dots. A short answer therefore reads as the agent's, not as another paragraph.
- **The output note is a caption, not a link.** It is secondary to the row, so it is muted,
  small, and uses the UI font rather than the row's mono; it underlines on hover and focus.
  It is a `button` outside the `summary`, so following it never toggles the row.
- **The output is a document the extension supplies.** A temp file would have to be cleaned
  up, could be edited, and would put model output on disk. A `TextDocumentContentProvider`
  serves read-only text under a scheme with no file system provider — the same property
  plans already rely on. The content is bounded in memory, and the URI contains the call id,
  so a second click is a reveal, not a duplicate.
- **The suffix comes from the call.** A random suffix would title two clicks two tabs; a hash
  of the tool call id is stable, short, and safe in a path. The document's identity also
  carries the full id, so a hash collision could only repeat a display name, not merge two
  outputs.
- **The tab gets the whole result.** The OUT pane keeps its 4000-character display cap and
  its "show all" button; the tab is the place for the rest, and it is what the user asked the
  row to open.

## Implementation notes

### The rail

`syncRail` walks a container's direct children. `.tool`, `.msg.assistant` and `.output-link`
join the current run; everything else flushes it. The caption is a member so the line does not
break around it. Each member gets `rail`; `rail-up` is set when it is not the first member and
`rail-down` when it is not the last. The classes are recomputed from scratch on every pass, so
a block that used to be last and no longer is loses `rail-down` on the next append. The
reading view does not re-run the pass: `hiddenInFocus` returns true for `tool`, `think` and
`output-link`, and the focus view's CSS hides exactly those three.

The stylesheet draws `.tool::after`, `.msg.assistant::after` and `.output-link::after` at
`left: 9px`, full height, 1px, in `--ui-hairline`, `display: none` until `.rail` is present.
A row's or caption's segment extends 10px on a continuing side; a message's extends 14px. The
transcript's 12px gap plus a message's 8px margin is 20px between a row and a message, and two
messages sit 28px apart (12px gap plus two 8px margins); 10 + 14 and 14 + 14 meet both exactly.

Prose is padded by 22px — 6px summary padding plus the 6px dot plus the 10px gap — which is
where a row's name starts. The Thinking summary keeps its own 6px padding, so its dot stays
at 9px and the line passes through it.

### The thought

The summary gains an `::after` chevron (`›`) after its label, with `margin-left: -6px` to
offset the flex gap; `[open]` rotates it 90°. The dot stays `--ui-muted` and is slightly
more opaque than before. The body keeps its 22px inset but loses `border-left`: the rail at
9px is the one line, and the old bar at 22px was a second, unrelated one.

### The output note

`lineCount(text)` drops trailing newlines, splits on `\n`, and counts; empty text counts as
zero and shows no note. `addToolResult` inserts a `button.output-link` as the `<details>`'s
next sibling — not a child, because a folded row hides its children and the caption has to be
readable while the row is closed — labelled `1 line of output` or `N lines of output`, with a
title that says it opens a tab. Its click posts
`{ type: 'openOutput', title, id, text }`, where title is the row's display name, id is
`tool_call_id`, and text is the untruncated result.

### The output tab

`src/toolOutput.ts` mirrors `planDocument.ts`, with the pure naming split into
`src/toolOutputName.ts` so unit tests can import it without the `vscode` module: a
`TextDocumentContentProvider` under `anvil-tool-output:`, a `Map` keyed by URI string,
bounded to 16 documents, and an `onDidChange` emitter for the `Disposable` contract.
`outputPath(tool, id)` sanitises the display name the way the plan title does (path
separators, control characters and query/fragment marks become hyphens; 40 characters);
`outputSuffix(id)` is six base-36 digits of an FNV-1a hash of the id; the path is
`/<title> output (<suffix>)`. The URI carries `?id=<encoded id>` so two calls that hash
alike still get two documents.

`open` copies the text in before revealing, opens with `preview: true` in the active column,
and returns the URI. `ChatPanel.openOutput` accepts only a non-empty string; the extension,
not the webview, decides the title. `extension.ts` constructs the provider beside the plan
provider and passes it through `Hub` to every panel.

## What was not walked

No real window here. The rail's continuity across a message's 8px margins and the transcript
gap, the 22px prose inset against a long line, the chevron's rotation in a narrow panel, and
the output note's muted grey in the light, dark and high-contrast themes should be looked at
in a running chat. The output tab's placement (a preview beside the chat) and behaviour when
the panel is in a side group are pinned at the source level only. A very large result is
passed through the webview and held in memory, but its rendering in the editor was not
measured; nor was the "same call clicks back to the same tab" behaviour clicked.

## Non-goals

- A wrapper element per reply, or collapsing a whole reply as one block.
- A protocol field for output, or asking the host for output again; the tab shows what the
  result event already carried.
- Writing output to a file, or making the tab editable.
- Changing the OUT pane's cap, its "show all" button, or the result text itself.
- A per-tool line count wording (`Read 18 lines`); the note is one phrase for every tool.
- A version bump, a branch, or a push.
