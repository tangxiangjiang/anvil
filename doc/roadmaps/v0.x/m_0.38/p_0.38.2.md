# p_0.38.2 — A tool card that opens the change it made

**Status:** done  
**Milestone:** [m_0.38_session_identity.md](../m_0.38_session_identity.md)  
**Linked design:** [38-session-identity-and-replay.md](../../../design/v0.x/38-session-identity-and-replay.md), [35-vscode-extension.md](../../../design/v0.x/35-vscode-extension.md)

## Goals

1. **Click a card, see the change.** A tool call that wrote or edited a file gets one
   affordance: open its change in VS Code's diff editor — the same surface the approval card's
   *Review in editor* button and the changed-files row already open.
2. **Every call that changed a file, not only the ones that asked.** A call that ran under
   `accept_edits`, under `bypass`, by an `allow` rule, or with no permissions file at all must
   be reviewable. The one that prompted already has a diff in front of it.
3. **One implementation for the live card and the replayed one.** The card's change is derived
   from the call's own arguments, which is the only source a replayed call has — so p_0.38.3
   inherits this phase's work instead of duplicating it.
4. **A true diff when one is available.** The change tracker already holds the pre-image of a
   file this turn touched; when it does, the review is that image against disk, which is the
   diff the approval showed.

## Scope

`editors/vscode/src/` (a new `editDiff.ts`, plus `chatPanel.ts` and one added surface in
`review.ts`; `protocol.ts` is untouched), `editors/vscode/media/` (`chat.js`, `chat.css`), and the
tests and docs.

## Tasks

1. **`src/editDiff.ts`** (new, imports no `vscode`, unit-testable like `sessionList.ts`) —
   `reviewOf(name, args)` returns a descriptor of the change a call carries: both sides for
   `edit_file`, the new body for `write_file`, the patch text and its file headers for
   `apply_patch`, and nothing at all for a call that changes no file. Malformed arguments
   return nothing; the function does not throw.
2. **The card** — `media/chat.js` renders a review button for a call the descriptor covers. It
   is a **sibling** of the card's `<summary>`, never a wrapper, so the card's own collapse
   keeps working; it is built with `createElement` and `textContent`.
3. **The routing** — `reviewCall` joins the panel's inbound union; `openCallReview` sits beside
   `openReview` and `openChangeReview` and maps the descriptor onto `PreviewDocuments`
   (`openPreview`, `openAgainstDisk`, `openDeleted`), preferring the change tracker's pre-image
   when it has one.
4. **A review is a record, not a request.** Unlike the approval card's, this button answers
   nothing, is not tracked as a pending decision, and is not closed when the run ends.
5. Tests and docs.

## Tasks as delivered

Six details the task list does not carry, and one acceptance item that needed saying better.

- **Two functions, not one, and the split is what makes the choice testable.** `reviewOf` reads
  what the call carried; `planReview(review, preImage?)` decides which surface shows it — the real
  diff against disk, the memory diff of a replacement, or a patch's own text. Task 3 folded both
  into `openCallReview`, and the consequence of doing it that way is that the *decisions* would
  live in a method that needs an extension host. Split, the whole selection is a pure function
  with a unit test per outcome, and `openCallReview` is left with the part that genuinely needs a
  window: calling the four opener methods. (`planReview` also takes the pre-image as a parameter
  rather than reading the tracker, which is what keeps "which turn's pre-image" out of the
  derivation.)
- **The click carries the call, not just its id.** The panel keeps no copy of what it has already
  sent to the tab, and retaining every call's arguments so a click could look one up would mean
  holding a session's worth of file bodies for as long as the tab lives. So the card keeps
  `{runId, name, args}` for exactly the calls it will offer a review for — a *reference* to the
  arguments already rendered in the card's own IN pane, not a copy — and hands them back with the
  click. The id travels too, for the panel's log line when there is nothing to review.
- **The decision stays on the extension side, where a module can be read.** The renderer cannot
  `import` `editDiff.ts`, so it is not the renderer that decides which tools change a file: the
  panel answers that at the `tool_call` event (`reviewable`) and the card stores facts only when
  told to. A second list of tool names in `chat.js` is a list that goes stale the first time one
  is renamed, and the drift would be silent; `toolCardReview.test.ts` pins the two lists against
  each other so it cannot be.
- **The answer is given in one place, where every event is posted.** `onEvent` and (from
  p_0.38.3) the replay both go through `postEvent`, which is what computes `reviewable`. A second
  caller that posted a tool call directly would be a card with no way into its change, and the
  forgetting would be invisible; the test asserts the listener routes through it.
- **Pre-images are kept with the run that took them.** The changed-files list computes a
  pre-image per path at the moment of the call, and a *later* turn's pre-image shown under an
  older card's button would read as that call's edit — one turn's change attributed to another's
  call. `lastChanges` is therefore `{run, files}` and `preImageFor` refuses a run id that is not
  the stored one, which also settles the mid-turn case honestly: a click on the live turn's own
  card, before its `done` has landed, has no pre-image yet and falls back to the arguments.
- **The fallbacks say what they are.** With no pre-image, an `edit_file` shows the two sides the
  call itself named — its `old_string` against its `new_string`, which is the replacement and not
  a claim about the file; a `write_file` shows the body against an
  empty side, and its title says `(the body this call wrote)` rather than implying the file was
  empty. `apply_patch` spans files and has no single "before", so it opens as its own text — a new
  `PreviewDocuments.openText`, the one surface this phase adds — named `<file>.diff`, or
  `patch.diff` when its headers name fewer or more than one file, matching what the approval card
  already does with a patch.
- **Said better:** acceptance item 8 read as "the button posts a `reviewCall` carrying the tool
  call's id". It carries the id *and* the facts the card was built from, for the reason above —
  and a `reviewCall` remains a record rather than a request: it answers nothing, is not tracked
  with the pending approvals, and does not close when the run ends. The test asserts the review
  path never touches the map the approvals are closed through.

## Non-goals

- Attaching a preview to `tool_result`, or any other host change. The SDK computes a preview
  only where it is about to ask, so a host-supplied one would exist exactly when the user had
  already been shown it.
- A review for a shell command's redirected write. The change tracker cannot see it.
- An inline diff inside the card, a diff of the whole file after the fact, or a keybinding.
- Accepting, reverting or undoing anything from the review.
