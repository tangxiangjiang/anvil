# Milestone 0.54 — Durable agent runs

**Status:** done
**Product version:** 0.52.25

Make an agent run reconstructible after a host or editor restart by defining an ordered event
journal, durable task semantics, and a VS Code reconciliation path. Durability means recovering
recorded state and reconnecting to work that is still owned by a live host; it does **not**
pretend that Anvil can recover control of an arbitrary OS process after that process or its
supervisor has disappeared. The design is chapter
[54](../../design/v0.x/54-durable-agent-runs.vscode.md).

## Goals

1. Give every persisted run event a stable sequence and journal contract.
2. Define the persistence boundary: task handles remain host-local, while a run whose owner is
   lost becomes durably `interrupted`.
3. Rehydrate VS Code from durable state, then reconcile it with the current host.
4. Treat each user-visible implementation batch as one VS Code patch bump from the then-current
   `editors/vscode/package.json`; milestone 0.54 is a roadmap version, not a plugin version.

## Ordering

p_0.54.1 establishes the replay boundary and ordering. p_0.54.2 defines why task handles are not
persisted and how their owner run records the loss. p_0.54.3 consumes both contracts and therefore
runs last.

## Overall acceptance

1. Journal tests prove strictly increasing, duplicate-free sequence numbers across append,
   restart, truncated-tail recovery, and both supported stores.
2. Task-boundary tests prove a restarted host imports no task handles, sends no signal to a
   guessed PID, and marks an unfinished run from a lost host `interrupted`.
3. VS Code integration tests reload a fixture with an active run, replay it once, reconcile
   against the host, and render the same final task/run state after a second reload.
4. `cd source && go test -count=1 ./...` and `cd editors/vscode && npm test` pass.
5. Before each user-visible delivery, a test reads the current extension version, verifies an
   exact `+1` patch bump, and checks all synchronized shipped-version declarations.

## Non-goals

- Recovering, signalling, or claiming ownership of an OS process when no live Anvil supervisor
  can identify and control it.
- Cross-machine run migration, distributed consensus, or exactly-once external side effects.
- Session full-text search, structured plan approval, or worktree workers.
