# p_0.53.1 — Capability profiles and adaptive thinking

**Status:** planned

## Goals

Make model request behavior derive from an explicit capability profile, including support for
adaptive thinking, instead of model-name guesses or one provider-wide default.

## Scope

- Define a capability profile for reasoning modes, effort support, output bounds, and relevant
  provider request variants.
- Resolve profiles from model configuration and carry the effective profile to request building.
- Emit adaptive thinking and its effort field only for models whose profile declares support.
- Preserve legacy/default thinking behavior for profiles that require it and unchanged requests
  when no capability is configured.
- Surface invalid profile combinations as configuration errors.

## Tasks

- [ ] Define profile schema, defaults, validation, and configuration resolution.
- [ ] Integrate profile-driven request construction in supported adapters.
- [ ] Add adaptive-thinking and legacy request fixtures.
- [ ] Add migration/compatibility and invalid-profile tests.

## Acceptance

- [ ] Table-driven tests cover absent, non-reasoning, legacy-budget, adaptive-thinking, and
  effort-capable profiles.
- [ ] Provider fixtures assert adaptive requests contain the design-specified fields and omit
  legacy budget fields; legacy fixtures assert the inverse.
- [ ] An absent profile produces the documented compatibility behavior without model-name
  substring inference.
- [ ] Invalid combinations fail before a provider request is sent and identify the conflicting
  capabilities.
- [ ] Run `cd source && go test ./...`.

## Non-goals

- Discovering capabilities by probing a provider during a user request.
- Exposing reasoning content or signed provider state to the UI.
- Model selection or pricing policy.
