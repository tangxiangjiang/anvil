## 一、系统定位

本系统是一套以 **AI 为执行主体、人为审核与兜底** 的软件开发流水线工具。

调度与协作域（Clusters）：**Scheduler → Workspace → Project → Workers**。Workspace 用 Token 收编多台 Dev Node；**Project** 是交付单元（需求→设计→路网→测试）；**Worker** 是某分支的工作副本，可并行多个。

核心目的：

> **给 AI 树立边界——什么能干、什么不能干、按什么规格干、什么必须人接、什么条件才算完成，全部固化在 Graph 里。**

Graph 不是给人随便看看的图表，而是同时具备四重含义：

- **任务流转图**
- **责任分配图**
- **AI 边界图**
- **规格图**

---

## 二、核心概念

| 概念 | 含义 |
|---|---|
| **ADR** | Architecture Decision Record；在本系统中指以 Milestone 为单位的技术决策 + 执行规格 + sample 文档 |
| **Graph** | 自动生成、不可编辑、只读的任务状态追踪图（Roadmap Graph） |
| **AI assist** | 每个环节都有 AI 参与；AI 是协作者，不是拍板者 |
| **status** | 图上唯一可操作的写入口 |

---

## 三、层级结构

```
大版本号（顶级结构 / 总纲）
  ├── 该版本真实的软件总体架构
  ├── 版本整体说明描述
  └── Milestone × N（里程碑）
        ├── 总概括：需求要什么、完成样式是什么样
        ├── ADR × N（决策 + 规格 + sample + 承载力 / 冗余）
        └── Version × N（最小执行单元；AI 生成代码，人 review）
                └── Graph：串成开发流水线（图纸）
```

### 各层职责

| 层级 | 内容 | 负责人 | 管理层级 | AI 角色 |
|---|---|---|---|---|
| **大版本** | 总纲、软件总体架构 | 部门经理 | 顶级指挥层 | 辅助架构提案 |
| **Milestone** | 需求总概括、完成样式 | 总监 | 战役层 | 辅助拆分 |
| **ADR** | 决策、规格、sample、承载力 / 冗余 | 小组长 | 战术层 | 辅助写决策 / sample |
| **Version** | 最小执行单元 | 程序员 | 战斗层 | 辅助编码 |

---

## 四、权责链

```
部门经理：拍大版本（总纲 + 总体架构）
  → 总监：拆 Milestone
      → 小组长：拆 ADR
          → 程序员：review AI 生成的 Version + 兜底
```

核心原则：

> **文档层级 = 管理层级 = 决策权层级 = 负责人层级。**  
> 四者对齐，自上而下拆解，每层只管下一层。

---

## 五、任务流转形态

整个设计流程是 **任务流转形态**：

```
需求
  → 部门经理：拍大版本（总纲 + 总体架构）
      → 总监：拆 Milestone
          → 小组长：拆 ADR
              → 程序员：review Version + 兜底
                  → 执行 → 产出代码
```

每一层都把 **上一层的产出物当作任务**，加工后再交给下一层。

流转特征：

1. **有向、逐级、不可越级**
2. 每层都是 **接收 → 加工 → 交付**
3. **状态可追踪**
4. **回流机制**：执行中发现上层问题，逐级回流，不越级

## 六、人的角色

人最终保留三件事：

| 人的活 | 性质 | AI 参与度 |
|---|---|---|
| **审核数据** | 判断 | AI 生成，人审 |
| **处理高难度代码** | 兜底 | AI 干不了，人接 |
| **集成测试** | 启动 + 监管 + 终审 | AI 写脚本，人执行监管 |

核心：

> **AI assist，人拍板，产出可追溯。**

程序员的角色从「写代码的人」变成 **「review + 兜底改 AI 处理不了的代码」**。

## 七、AI 边界

### 能力边界：什么 AI 能干

- **生成**：大版本提案、Milestone 拆分、ADR、Version 代码、测试用例、bug 修复建议
- **执行**：结构化、补全规格、判定 unit / smoke、归类 bug
- **写脚本**：auto test 流程脚本

### 权限边界：什么 AI 不能干

- 不能拍板（四层拍板权都是人）
- 不能 close 节点（close 条件是集成测试通过）
- 不能改 Graph 结构（只读）
- 不能越过审核关卡流转
- 不能自己启动集成测试

### 兜底边界：什么必须人接

- AI 处理不了的代码
- AI 判定不了的测试
- AI 出的候选 → 人拍板
- 集成测试的启动、监管、判定、close

### 规格边界：AI 按什么干

- 每个节点的 **输入 / 输出 / 正确标准**
- 每层交付物格式（必须结构化）
- 每步的验收条件

## 八、状态机

### 节点状态

```
未开启 → 开启 → 进行中 → 待审核 → 审核
                                    ↓
                              开发完成（还不是 close）
                                    ↓
                         ┌──── 测试 + fix 循环 ────┐
                         │  buglist → feedback      │
                         │      ↓                   │
                         │    fix → unit / smoke    │
                         │      ↓                   │
                         │   通过？否 → 回循环       │
                         └──── 是 ──────────────────┘
                                    ↓
                              集成测试 ──失败──→ 回循环
                                    ↓ 通过
                                节点 close
```

### 关键约束

> **节点 close 的必要条件 = 集成测试通过。**

- 开发写完 ≠ close
- unit / smoke 通过 ≠ close
- buglist 清空 ≠ close
- 只有集成测试通过才能 close

### status 是唯一写入口

| 可操作 | 不可操作 |
|---|---|
| status（节点状态） | 节点本身 |
| 工作流节点开启 / 审核 / 完结 | 节点关系 |
| | 节点负责人 |
| | 图结构 |

status 的**合法迁移路径由流程定义**，人只在允许的选项里选。**close 的触发权归人**，AI 无权限。

## 九、测试环节

### 全景

```
unit / smoke       ← AI 全包（生成 case、执行、判定）  量大
    ↓
集成测试            ← AI 写 auto test 脚本
                        人启动 + 监管
                        人判定 + close               量小但关键
```

### unit / smoke

**工作量最大**（海量 case、海量测试数据），但规格明确、可判定，由 AI 全包：

- AI 生成测试用例
- AI 执行测试
- AI 判定通过与否

**三要素**（每个测试必须有）：

| 要素 | 含义 |
|---|---|
| **输入是什么** | 测试的前置数据 / 状态 / 依赖 |
| **输出是什么** | 预期产出 / 可观测结果 |
| **正确标准是什么** | 判定通过与否的准则 |

### 集成测试

**工作量最小，但最关键**，半 AI 化：

```
AI 写 auto test 流程脚本
    ↓
人启动 auto test
    ↓
人监管测试流程
    ↓
人判定结果 / 决定 close
```

守住的底线：

1. 脚本由 AI 写，但**人审脚本**（测得够不够、断言严不严）
2. **启动权归人**（启动 = 进入终审）
3. **监管不是看热闹**（盯流程、异常、结果可信度）
4. **判定和 close 归人**（AI 只能给原始输出，不能替人下结论）

### buglist → feedback

- bug 不是孤立列表，要**挂回产生它的节点**
- 开发人员能在图上直接看到「我哪个节点被反馈了」
- feedback 是 buglist 到节点图的**回流通道**
- bug 是图上的**新节点**，走流转：bug → 指派 → 修复 → 验证 → 关闭

## 十、Graph 设计

### 定位

| 属性 | 含义 |
|---|---|
| **自动生成** | 不需要人建图，由前面结构化产物推导 |
| **不可编辑** | 图是产物 / 视图，不是数据源；数据源在前面各层 |
| **任务状态追踪** | 图上反映每个任务节点当前状态 |

### 生成方式

```
Requirement → 大版本规划 → Design → Milestone → Version
                                                    ↓
                                        自动生成 Roadmap Graph
```

前提是前面每一层的产物都**结构化**，系统才能自动抽关系、生成图。关系包括：

- **归属关系**：Version 属于 ADR 属于 Milestone 属于大版本
- **流转关系**：任务从谁交给谁
- **依赖关系**：Version 之间、ADR 之间的前后依赖
- **状态**：每个节点当前的流转状态

### 为什么不给编辑

- 图和数据源不一致，谁是真相？
- 有人绕过流程直接改图，等于绕过权责链
- 状态双写，对不上

> **改流程 → 改数据 → 图自动跟着变。图永远和真相一致，且无法被绕开。**

### 图上唯一可操作项

**status**：工作流节点开启 / 审核 / 完结。

## 十一、迭代

软件与建筑的关键区别：**迭代**。每个大版本，都是在前一个大版本基础上演进而来。

带来的性质：

1. **大版本号是「快照」**：记录演进到这一刻，系统整体长什么样
2. **ADR 有生命周期**：上个版本的 ADR，这个版本可能被取代或废弃
3. **Graph 是增量的**：在上一版基础上加节点、加边、改边
4. **总体架构会漂移**：大版本总纲要能反映「当前真实架构」

### ADR 跨版本管理建议

- ADR 带**创建版本号**和**状态**
- 被取代时，指向**取代它的新 ADR**
- 大版本总纲里，汇总「本版本生效的 ADR 列表」

### 两个轴

- **横轴：结构**　大版本 → Milestone → ADR / Version
- **纵轴：时间**　版本 1 → 版本 2 → 版本 3 …… 每版在前版上演进

Graph 是横轴的结构表达，迭代是纵轴的演进表达。

## 十二、与建筑设计的类比

| 建筑 | 本系统 |
|---|---|
| 甲方提需求：会展中心、功能、展厅布局 | 需求 |
| 设计院拆：整体结构、施工模块、材料、承载力、冗余 | Milestone → ADR → Version 的 Graph |
| 施工图 / 图纸 | Graph |
| 施工 | 写代码（AI 执行，人 review） |
| 成本预算 | **砍掉**（软件成本由人的决策和返工主导，无法按图纸算量） |
| 承载力上限、冗余 | **必须保留**（性能上限、容量、并发、容错、降级、备份） |

> **砍掉的是「钱」的维度，不是「约束」的维度。**

## 十三、复杂度判断

这套系统确实复杂，但是 **「真复杂」，不是「假复杂」**——每一项复杂都在解决一个真实存在的问题：

| 复杂点 | 解决的真实问题 |
|---|---|
| 分层 | 权责清晰，不越级 |
| 角色对应 | 每层拍板人明确 |
| status 单写入口 | 图和数据不双写、不脱节 |
| Graph 自动生成 | 不靠人画图，图永远和真相一致 |
| 测试 + fix 循环 | 真实开发就是反复修 |
| bug feedback 回图 | 问题不丢，能追到源头 |
| close = 集成测试通过 | 防止「开发写完就算完」 |
| 每环节 AI assist | 复杂度承担方从人变成人 + AI |

要警惕的：

1. 层级别再多了（四层够用）
2. 状态别膨胀（只保留流转必需的）
3. 回流路径要收敛
4. 工具别一开始就全做（分阶段落地）

## 十四、瓶颈与关键指标

编码不再是瓶颈，瓶颈转移到：

| 旧瓶颈 | 新瓶颈 |
|---|---|
| 写代码慢 | **review 慢** |
| 人不够 | **审核吞吐不够** |
| 实现难 | **AI 处理不了的部分难** |

关键指标：

- **review 吞吐**（每小时能审多少）
- **AI 一次通过率**（AI 产出多少人直接过）
- **兜底率**（多少代码需要人改）
- **回流率**（审核打回多少）

---

## 十五、一句话总结

> 本系统是一套 **AI 生成一切可生成的数据、人审核数据 + 兜底高难度代码 + 集成测试终审** 的软件开发流水线。Graph 自动生成、不可编辑，是任务状态追踪图，也是给 AI 立的边界。人最终保留三件事：**审核数据、处理高难度代码、集成测试（半 AI 化：AI 写脚本，人启动 + 监管 + 终审）**。节点 close 的唯一条件是集成测试通过。

**核心原则：AI assist，人拍板，产出可追溯。**
